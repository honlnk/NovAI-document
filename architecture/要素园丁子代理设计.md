# 要素园丁子代理设计（LLM Wiki 魔改）

## 记录时间

2026-09-23（v2：五项决策拍板 + Schema 层定稿）；2026-09-25（v3：注入边界收紧——ELEMENT.md 只注入园丁，且园丁只注入它）

## 状态

设计定稿，待立施工计划。本文档不做施工，Phase 1 另行立计划。

## 1. 背景

要素模块的「外壳」已就位：六类目录（characters / locations / entities / plots / timeline / worldbuilding）、五类 body 模板、LLM 提取管线、RAG 索引。缺的是「灵魂」——要素库的**持续维护机制**：同名合并、旧格式迁移、近名去重、跨章节信息归拢。

2026-09-23 调研了竞品 InkOS。它的解法是 delta 结算制：模型只产出 JSON 增量，代码层校验后不可变 apply，模型全程不碰要素文件。该方案为**无人值守量产**设计，与 NovAI「用户控制 AI 对小说的全部创作工作、没有 Agent 够不到的地方」的哲学相反——它把状态变化藏进代码黑盒。**已拍板：核心上不参考 InkOS。**

本文档记录新方向的设计：**LLM Wiki 魔改 + 委派式园丁子代理**。

## 2. 核心概念：要素库即 Wiki

把要素库对标一个 wiki 站：

| Wiki 概念 | NovAI 现状 |
| :-- | :-- |
| 词条页面 | 已有：每个要素一个 md 文件（frontmatter + 模板分节 body） |
| 搜索 | 已有：RAG 向量索引 |
| 交叉引用 | **已拍板要做（决策 5）**：素材→章节、素材↔素材两种；章节正文内不加链接。语法约定写进 `prompts/ELEMENT.md`，解析与 UI 渲染放 Phase 3 |
| 索引页 / 目录 / 最近变更 | 没有（Phase 3） |
| **园丁（WikiGnome）** | **没有——这就是灵魂** |

wiki 的运作哲学是「页面随便长，园丁定期修」。这个类比给出一个关键转折：

> **把「同名合并 / 近名去重 / 覆盖冲突」从代码问题，改写为园丁 Agent 的职责描述。**

此前暂缓这簇问题，是因为它们作为代码问题很难做对——机械合并丢信息，模糊合并会误伤。但园丁用语义判断做合并、产出 diff 由用户确认，正是这类问题的正确解形态。写入路径因此可以保持简单（现状覆盖写可以容忍），治理交给园丁。

## 3. 架构：委派式子代理，不是第二个常驻 Loop

### 3.1 主从模型（决策 1 已拍板：委派式）

- **创作 Loop = 主 Agent**：地位不变，是用户对话的唯一入口。
- **园丁 = 子代理（subagent）**：主 Agent 通过委派工具把整理任务交给它；它跑完返回结构化汇报，不占主 Loop 的上下文。

为什么不做成平级的「两个常驻 Loop」：

1. 并发协调成本高——两个 Loop 同时写文件，改动归属、确认卡片、文件锁都是新问题。
2. 委派式完全复用现有串行执行模型，园丁的工作时段与主 Agent 天然互斥（主 Agent 等它返回）。
3. 主上下文不被记账工作污染——只有结构化汇报回流。

常驻想象中的「随叫随到」由入口补足：Phase 2 加快捷入口（快捷键 / 一键按钮）触发委派，后面很多功能都可以复用这种形态。

### 3.2 dsh subagent 形状 → NovAI 落点

dsh（deepseek-harness）有完整的 subagent 能力族（`packages/subagent/`），当年的 Loop 重构刻意未引入。本轮按「抄内核形状，不抄框架」的老原则映射：

| dsh 形状 | NovAI 落点 |
| :-- | :-- |
| provider registry（`ctx.subagents`，多后端共存） | 简化为单一 in-process provider；不要注册表抽象，直到真有第二后端 |
| spawn-in-process（全新子代理） | 园丁一次性任务：「整理第 N 章涉及的要素」 |
| ~~continuable children（可续命子代理）~~ | **已拍板移出路线图（决策 2）**：每次都是全新上下文；机构记忆由 `prompts/ELEMENT.md` 承载（见 §7） |
| toolFilter（运行层强制工具面） | 园丁工具白名单：ListDirectory / FindFiles / ReadFile / RagSearch 全项目可读；CreateFile / EditFile 仅限 `elements/` 与 `prompts/ELEMENT.md` 之外的范围（见 §7）；无 DeleteFile（删除走回收站留给用户） |
| persona（专职系统提示词） | 园丁角色定义（精简版，工作守则读 Schema 文件），见 §4 |
| outputSchema（结构化返回） | 园丁汇报：动了哪些文件、合并/迁移了什么、存疑项清单（交用户拍板） |
| agentOptions（模型覆盖） | 默认继承主 Agent 模型，设置页可单独配置（决策 4，覆盖项在 Phase 2） |
| subagentCatalog（子代理编目投影） | 聊天区把园丁的工作呈现为嵌套任务组（复用 TurnProcessGroup 折叠形态 + DiffLines 面板） |
| send_message / interrupt_agent / list_agents | 后期。第一期只要委派与打断（复用现有停止机制） |

明确不引入：进程外后端（ACP / Codex / Claude Code）、多层嵌套委派（深度写死 1）、dsh 的 Cordis 依赖注入框架。

施工参考（dsh 源码，按「抄形状不抄框架」读）：

- `packages/subagent/subagent/src/child-agent.ts`：子代理组装——委派深度预算、模型路由继承与覆盖（换模型清掉父路由 reasoningEffort 这类细节）
- `packages/subagent/subagent-spawn-in-process/src/index.ts`：后端薄壳——capabilities 声明制，请求了不支持的能力响亮报错，绝不静默降级
- `packages/subagent/tool-subagent/src/index.ts`：模型侧工具——输入 `{ description(3~5 词短标签), prompt }`；工具描述必须写明「子代理看不到这段对话，prompt 必须独立完整」（providerWording）

### 3.3 委派工具形态

主 Agent 工具清单新增一个委派工具（名字候选 `DelegateToGardener`），输入为 `{ task, scope? }`：

- `task`：自然语言任务，如「整理第 12 章涉及的要素，重点核对云溪的人物卡」
- `scope`：可选，圈定文件范围，缺省全要素库

执行语义：主 Agent 调用 → 创建子代理运行（独立 model-view、独立压缩、共享项目 FS 与权限运行时）→ 子代理逐工具执行（写操作照常弹确认卡）→ 返回结构化汇报 → 主 Agent 把汇报消化后对用户总结。

## 4. 园丁职责定义（persona 草案）

决策 2 拍板「一次性、全新上下文」之后，园丁没有跨任务记忆，因此职责定义分两层：

- **persona（硬编码，几行）**：你是小说要素库的园丁。你维护 `elements/` 下的事实性文件，**从不修改 `chapters/` 正文**。随本提示词注入的 `prompts/ELEMENT.md` 是本书要素规范，严格遵守。
- **工作守则（在 Schema 文件里，用户可改）**：见 §7。园丁的提示词栈只有这两层，提示词家族其余文件不注入（见 §7.4）。

这样「园丁怎么干活」是项目级可调教的资产，硬编码只保留不可让渡的边界（不动正文）。

## 5. 用户可见性与控制（NovAI 哲学的落地处）

- **可见**：园丁的每一步工具调用在聊天区呈现为嵌套任务组（默认折叠成计数摘要行，展开可见工具行与 diff），与主 Agent 的工作同构。
- **可控**：园丁写文件走与主 Agent 完全相同的确认卡片 + diff 预览；拒绝即回灌子代理。用户随时可打断（复用运行停止机制）。
- **可审**：园丁的写入照常进 changeLedger 与写回面板，轮次归属标记为园丁。
- **可回退**：删除只进 `.novel/trash` 回收站的现状不变。

## 6. 决策点（2026-09-23 已拍板）

| # | 决策点 | 拍板结果 |
| :-- | :-- | :-- |
| 1 | 委派式 vs 常驻式 | **委派式**。常驻不做；Phase 2 加快捷入口（快捷键 / 一键触发委派），此形态后续可被很多功能复用 |
| 2 | 园丁身份是否持久 | **一次性、每次全新上下文**。continuable 持久子代理移出路线图；机构记忆由 Schema 文件承载（§7） |
| 3 | 确认闸口 | **默认继承主 Agent 档位**；Phase 2 在设置页提供园丁独立覆盖 |
| 4 | 园丁模型 | **默认继承主 Agent 模型**；Phase 2 在设置页提供园丁独立配置 |
| 5 | wiki 交叉引用范围 | **只做素材→章节、素材↔素材两种链接；章节正文内不加链接**。语法约定写进 `prompts/ELEMENT.md`（Phase 1 起文件即按约定积累），解析与 UI 渲染放 Phase 3 |

## 7. Schema 层：`prompts/ELEMENT.md`（要素库宪法）

### 7.1 定位

每个项目一份的要素库规范文件：**内置一套完整默认内容，但允许用户自行修改**。它是「整理规范作为可调教资产」（对齐产品愿景）的落地，也是决策 2 的逻辑闭环——一次性园丁没有积累，这份文件就是它全部的机构记忆。

### 7.2 位置与 UI

- 路径：`prompts/ELEMENT.md`——与 `system.md`、`NovAI.md`、`scenes/` 同族，提示词统一管理（2026-09-23 用户拍板，推翻此前 `elements/AGENT.md` 的草案位置）。
- UI：ActivityBar 提示词分类面板（PromptList）新增「要素规范」分组，与系统提示词、项目总览、场景提示词并列第四组，点击可查看/编辑。

### 7.3 内置默认内容大纲

1. **六类目录职责与边界**：含 entities vs worldbuilding 的判断原则（规则体系归 worldbuilding，会被点名/持有/状态变化的具体东西归 entities）。
2. **命名规范**：一人一文件、一地一文件，文件名即要素名。
3. **frontmatter 维护规范**：tags 去重、`relatedChapters` 取并集不覆盖、`lastUpdatedChapter` 取最新。
4. **链接约定**（决策 5）：素材→章节写章节路径（`chapters/第NNN章-标题.txt`）；素材↔素材用 `[[要素名]]`；章节正文不写链接。
5. **园丁工作守则**：合并保留旧文件全部事实、新信息按模板小节归位、存疑不合并（列入汇报）、不删除文件（确需删除列入汇报交用户）。
6. **模板结构说明**：五类模板的分节名称与填写要求；模板正文仍是 core `templates.ts` 代码资产兼兜底（文件被清空或改坏时系统不裸奔），「模板本身项目化调教」留待以后演进。

### 7.4 注入机制（2026-09-25 拍板）

- **主 Agent：不注入。** 任何形式的默认注入都不做（含摘要注入）；`prompts/ELEMENT.md` 不属于主 Agent 的提示词栈。
- **园丁：只注入本文件。** 园丁的提示词 = 硬编码 persona + `prompts/ELEMENT.md` 全文，**提示词家族其余文件一律不进园丁上下文**（`system.md` / `NovAI.md` / `scenes/` 均不注入）——创作向规范与项目记忆对整理工作是噪音，且这样「调教园丁」的触点收敛为一份文件。
- **变更生效**：复用现有 system prompt 同会话刷新机制（hash 比对），文件变化后委派的下一轮自动反映。

### 7.5 初始化与补齐

- 新建项目：写入默认内容（与 `prompts/system.md` 的初始化同款）。
- 旧项目：打开 / 修复 / 恢复时补齐（沿用 `elements/entities/` 的目录补齐策略），不覆盖用户已修改的版本。

## 8. 分阶段路径

- **Phase 1（最小闭环）**：委派基建（工具 + 子代理运行壳 + 工具白名单）+ 一次性园丁 + `/整理要素` 斜杠命令 + 聊天区子代理任务组呈现 + `prompts/ELEMENT.md`（默认内容 + 初始化/补齐 + PromptList「要素规范」分组）。验收：用户发起整理任务，能看到园丁逐步工作、逐卡确认、最后收到结构化汇报。
- **Phase 2**：主 Agent 主动委派（创作中判断何时联系园丁）+ 快捷入口（快捷键 / 一键触发）+ 设置页园丁独立配置（确认闸口、模型）。
- **Phase 3**：链接解析与渲染（要素面板点击 `[[要素名]]` 跳转、反向链接）+ 索引页 / 最近变更视图 + 「每章写完后建议整理」触发评估（形态是建议，不是自动跑）。

## 9. 风险与代价

| 风险 | 对策 |
| :-- | :-- |
| token 成本上升（整理是额外的 LLM 调用） | Phase 2 园丁独立模型配置；委派式按需触发，不自动跑 |
| 园丁误合并 / 误改 | 确认卡片 + diff 预览 + 回收站三层兜底；守则铁律「存疑不合并」 |
| 子代理是新基建，工作量不小 | 当年刻意排除 subagent，这是新模块而非复活旧代码；Phase 1 按最小闭环控规模 |
| 与「/提取要素」流程职责重叠 | 划清：提取 = 从章节初次产出候选（现状保留）；园丁 = 对存量要素库的治理与维护。提取流的产物是园丁的原料 |
| Schema 文件被用户改坏 | `templates.ts` 代码兜底 + persona 硬编码边界（不动 chapters/）仍在；后期可加「恢复默认」 |

## 10. 明确不做

- 常驻并行双 Loop、子代理再嵌套子代理
- continuable 持久子代理（2026-09-23 拍板移出路线图）
- 进程外子代理后端（ACP / Codex / Claude Code）
- InkOS 式 delta 结算与 truth 文件黑盒
- 章节正文内加链接（决策 5 明确排除）
- 无人值守的自动整理（自动触发只在 Phase 3 评估，且形态是「建议」而非「自动跑」）
