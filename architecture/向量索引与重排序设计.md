# NovAI 向量索引与重排序设计

## 一、职责与范围

向量检索负责帮助创作主智能体查找**情节与时间线**中的相关事实，处理「之前主角失恋那段」「某条伏笔后来怎样了」等语义查询。

不同故事数据采用不同通道：

| 数据 | 上下文提供方式 | 是否进入向量索引 |
| :-- | :-- | :-- |
| 情节、时间线 | 语义检索与可选重排 | 是 |
| 人物、地点、实体、世界观 | 要素目录披露与按需加载 | 否 |
| 章节正文 | 文件导航与按需读取 | 否 |
| 提示词、项目配置 | 按职责读取或注入 | 否 |

检索由主智能体主动调用工具发起，结果作为工具消息进入模型视图。框架不会在每次生成前自动召回一批内容，也不会自动选取近期章节。

## 二、存储分层

| 层级 | 保存内容 | 作用 |
| :-- | :-- | :-- |
| 内容层 | 项目中的情节与时间线文件 | 可阅读、可编辑、可重新索引的事实来源 |
| 持久索引层 | 浏览器 IndexedDB 中的向量、检索文本、元数据与项目级索引状态 | 跨会话保留索引，避免每次打开项目都重新向量化 |
| 内存检索层 | 每个项目独立的 Orama 实例 | 在当前运行时执行向量相似度召回与条件过滤 |
| 会话运行层 | 当前查询、候选、重排结果与工具消息 | 服务当前创作任务，不作为长期事实来源 |

向量不写回故事文件。它体积大、可读性差，并绑定具体的 Embedding 模型、维度和检索文本模板，本质上是可重建缓存。

每条索引记录都能回溯到项目中的来源文件，并保存支持检索与维护的元数据：

| 元数据类别 | 内容 | 用途 |
| :-- | :-- | :-- |
| 身份与来源 | 项目、条目、文件路径、类型、名称 | 项目隔离、稳定更新和回到源文件 |
| 检索与展示 | 摘要、标签、检索文本、向量 | 召回、重排和结果展示 |
| 剧情关联 | 最后更新章节、相关章节 | 条件过滤与剧情定位 |
| 缓存维护 | 内容摘要、源文件时间、索引时间、模型、维度、文本模板版本 | 复用未变向量、检测配置变化和重建索引 |

浏览器持久层使用两个逻辑集合分别保存索引文档与项目级状态，并通过项目标识隔离不同小说的数据。内存索引在首次查询时可从持久层懒构建，构建或重建后与该项目的完整持久状态保持一致。

## 三、检索文本

Embedding 的输入不是随意的文件片段，而是统一组装的检索文本。它依次包含有值的类型、名称、摘要、标签、最后更新章节、相关章节，以及正文。

这种结构同时保留条目身份与完整语义：摘要用于轻量展示，检索文本用于向量化和重排，两者承担不同职责。

组装遵循以下规则：

- 空字段不占位，避免无意义文本干扰向量。
- 标签最多保留 10 个，相关章节最多保留 20 个。
- 正文去除首尾空白后保留，不用摘要替代完整条目内容。
- 检索文本模板具有版本号；模板发生不兼容变化时，需要重新构建索引。

## 四、索引构建

构建过程按以下步骤执行：

1. 收集项目内的情节与时间线文件，读取并解析要素内容。
2. 为每个条目生成检索文本，并计算用于缓存判断的内容摘要。
3. 内容、模型、向量维度和文本模板版本均未变化的条目复用旧向量，其余条目调用 Embedding。
4. 将当前文档与项目级索引状态写入 IndexedDB。
5. 增量构建时移除已不存在的来源条目，全量构建时先清空该项目的旧索引。
6. 根据当前完整文档集重建内存 Orama 实例。

仅更新时间戳而不改变实际内容的文件，不会因此重复请求 Embedding。全量重建不复用旧向量，用于彻底消除模型或索引结构变化造成的兼容性问题。

## 五、向量召回

一次检索按以下顺序执行：

1. 主智能体给出语义查询，并可以指定数量及类型、标签、章节等过滤条件。
2. 查询文本经当前项目配置的 Embedding 模型向量化。
3. Orama 在对应项目的内存索引中执行向量召回。
4. 标量条件由索引过滤；标签在召回后进行精确校验，必要时扩大初召数量，避免中文分词差异漏掉候选。
5. 返回带有来源路径、摘要、标签、剧情关联和相似度得分的候选。

粗召回的任务是尽量保留相关候选，而不是决定最终写作上下文。默认采用向量检索，不叠加全文关键词混合召回。

查询向量与索引维度不一致时，检索返回空候选，不把不兼容的向量混合计算。索引不存在或没有文档时，同样返回空结果，由主智能体结合索引状态决定是否重建或改用其他工具。

## 六、Rerank 精排

Rerank 是可选的第二阶段排序器，独立于对话模型与 Embedding 配置。启用后，它接收查询与粗召回候选，按相关性重新排序并保留指定数量的结果；未启用时，粗召回结果直接进入后续工具结果处理。

| 组件 | 职责 |
| :-- | :-- |
| Embedding | 将条目与查询转换为同一向量空间 |
| Orama | 找出候选并应用过滤条件 |
| Rerank | 对候选做更精细的相关性排序 |
| 主智能体 | 判断结果是否足以支持创作，必要时继续读取源文件或查询 |

Rerank 只负责文本候选排序，不生成故事正文，也不替代主智能体的语义判断。返回结果仍保留来源文件与摘要等信息，便于模型理解并采取后续动作。

## 七、索引状态与重建

项目级索引具有以下状态：

| 状态 | 含义 |
| :-- | :-- |
| 空 | 尚未建立索引 |
| 构建中 | 正在建立索引 |
| 可用 | 当前索引可正常检索 |
| 部分过期 | 相关源文件已变化，索引尚未同步 |
| 重建中 | 正在执行全量重建 |
| 错误 | 最近一次构建失败 |

相关要素写入后，系统会将索引标记为过期并刷新工作区状态。用户在状态入口主动触发重建，可以选择完整索引或指定来源范围；重建不会由 Agent 在后台静默发起。

以下变化需要特别处理：

| 变化 | 处理方式 |
| :-- | :-- |
| 文件新增、修改或删除 | 重建时同步对应文档，删除失效条目 |
| 仅内容未变 | 复用已有向量 |
| Embedding 服务、模型或维度变化 | 全量重建，避免混用不兼容向量 |
| 检索文本模板升级 | 全量重建 |
| 构建中断或请求失败 | 保留错误状态与信息，允许用户重试 |

索引不可用时不会阻塞其他创作工具。主智能体仍可读取要素和章节，但语义检索结果需要结合索引状态理解。

## 八、可观察性与协作

检索结果通过 Agent 的工具轨迹进入聊天界面，用户可以看到主智能体发起了检索以及返回了哪些候选；需要核对事实时，可以继续读取结果指向的项目文件。

索引状态在工作区持续可见，使用户能够区分「没有相关内容」和「索引为空、过期或构建失败」。向量与缓存留在浏览器内部，项目目录中的故事文件仍保持人类可读。

这套设计的核心边界是：**语义检索负责找到可能相关的情节线索，项目文件负责提供事实，主智能体负责决定在创作中如何使用。**
