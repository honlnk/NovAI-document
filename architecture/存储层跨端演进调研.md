# 存储层跨端演进调研

> 调研日期：2026-11-23。本文是调研记录与方向性结论，不是施工计划；短期内不安排动工。外部环境类结论（浏览器与跨端框架的支持状态）有时效性，动手前应重新核实。

## 一、调研背景

NovAI 目前是纯浏览器应用，所有对小说项目的文件访问都建立在 File System Access API 之上——这是一套只有 Chromium 内核浏览器完整提供的能力，也是应用目前要求用户使用 Chrome / Edge 的根本原因。

远期计划是把 NovAI 做成手机和电脑上的 App。届时文件访问不再依赖浏览器能力，而存储层（项目文件访问 + 浏览器侧各类数据）希望抽成与界面、引擎平级的独立包，按运行环境装配不同实现。

本次调研回答三个问题：

1. 文件访问能力在各运行环境里到底长什么样，抽包是否必要；
2. 各类存储数据现在的分布与对浏览器的耦合程度；
3. RAG 向量缓存将来要不要换数据库（例如 SQLite）。

## 二、现状盘点：数据都放在哪

应用的全部持久化数据分四类：

| 数据类别 | 存放位置 | 内容 | 性质 |
| :-- | :-- | :-- | :-- |
| 项目文件 | 用户自选目录（经文件访问 API） | 章节、要素、提示词、计划、配置、会话、日志、回收站等全部业务正本 | 事实来源 |
| 浏览器数据库 | IndexedDB，共四个库 | 最近项目的目录句柄与计数、RAG 向量缓存、正文编辑草稿、看板卡片草稿 | 辅助数据，可重建或可牺牲 |
| 浏览器键值存储 | localStorage，六处 | 工作区界面状态、匿名身份、时间线/关系草稿、设置页签记忆 | 轻量界面状态 |
| 应用私有文件系统 | OPFS | 生产代码未使用（仅测试配方在用） | — |

架构上有两个有利条件：

- 业务正本全部在项目文件里，浏览器侧存储只承担缓存、草稿与界面状态。抽包不涉及迁移业务数据，浏览器侧数据丢了也能重建或接受损失。
- 界面层从一开始就只能通过引擎的服务层访问存储，没有直接读写。抽包的手术面集中在引擎内部，不波及界面。

主要负债是**目录句柄概念的渗透**：引擎内部约十五个模块的接口直接以「目录句柄」为参数传递，不只文件系统模块本身，还包括智能体的溢出存储、日志、看板目录、账本、技能发现和多类工具。这是未来抽包时真正的工作量所在——需要把接口语义从「传句柄」降级为「项目根 + 相对路径」，让句柄退回浏览器实现内部的细节。

## 三、跨环境事实

### 3.1 文件访问能力（2026 年时的支持状态）

| 环境 | 目录/文件选择器 | 应用私有文件系统（OPFS） |
| :-- | :-- | :-- |
| Chrome / Edge 桌面 | 完整支持 | 支持 |
| Firefox | 不支持（官方立场为反对，预计不会提供） | 支持 |
| Safari（含 iOS） | 不支持（官方立场为反对） | 支持（iOS 15.2 起，可写流较晚补齐） |
| Android 系统 WebView | 新版本提供，但要求宿主应用主动转发选择回调；且实测缺陷多：无原子写、无重命名、另存为不能新建文件 | 支持 |
| iOS WKWebView | 不支持（与 Safari 同引擎） | 支持 |
| Tauri 移动端 | 明确不支持文件夹选择器 | 视方案而定 |

结论：**App 化后 iOS 上文件访问 API 整体不可用**，Android 上依赖壳的实现且坑多。这不是体验差异，是核心功能死亡——抽包（为 App 环境提供另一套文件访问实现）是刚需，不是优化。

### 3.2 WebView 存储可靠性

跨端框架（以 Capacitor 官方文档为代表）明确警告：iOS 上 WebView 的 localStorage 与 IndexedDB 必须视为**临时数据**，设备存储紧张时会被系统回收；Android 上可通过持久化存储申请降低风险。

对 NovAI 的具体影响：RAG 向量缓存被清除意味着下次打开项目要重新调用 Embedding 服务重建索引——**重新花一遍钱**。草稿备份类数据被清除则是丢未保存的编辑。因此 App 环境里，这两类数据应落到 SQLite 或系统偏好存储，而不是 WebView 的浏览器存储。

### 3.3 浏览器端 SQLite 的成熟度

截至 2026 年中的公开综述：浏览器内运行 SQLite（WASM 方案）的持久化能力**没有项目宣称达到生产级稳定性**，且普遍要求跨域隔离响应头、强制 Worker 化、接受单连接等限制；wa-sqlite 一类方案的高速技巧对 SQLite 扩展的兼容性存疑。这从外部印证了纯浏览器阶段继续使用 IndexedDB 的判断。

附带事实：向量检索扩展（sqlite-vec）在包括 App 原生环境在内的任何运行时都没有开箱即用路径，均需自定义构建。

## 四、方向性结论

1. **抽包必要性成立**，理由见 3.1。包的形状建议分两族能力：项目文件系统适配器（浏览器实现走文件访问 API，App 实现走应用沙盒目录），以及键值/数据库适配器（承接最近项目记录、RAG 缓存、草稿备份；浏览器实现用 IndexedDB 与 localStorage，App 实现用 SQLite 与系统偏好存储）。界面层的轻量状态（面板宽度、页签记忆等）不必进这个包。
2. **实现选择发生在装配期**：浏览器版与 App 版在启动时各装配各的实现，不需要运行时探测或动态切换机制。
3. **RAG 数据库的最终答案**：浏览器实现继续用 IndexedDB；App 实现用 SQLite（Capacitor 的社区 SQLite 插件是目前最成熟的跨端方案，加密与全文检索开箱即用）。换库的动机不是性能，而是 iOS 会回收 WebView 存储。检索本身继续在内存索引中执行，数据库只承担仓库角色，因此接口非常薄：全量读出、增量写入、清空、元数据——不依赖数据库的查询能力，也不必为向量检索扩展折腾自定义构建。
4. **一个先于技术的产品问题**：移动端没有「用户自选目录」这个概念。App 化后小说项目大概率住进应用沙盒目录，靠系统分享与导出和外界交换文件。「项目目录」的产品含义会在移动端改变，并反过来影响存储接口的形状（「授权根目录」的概念在 App 里变成「应用数据目录」）。动手设计接口前应先把这个问题想清楚。

## 五、现阶段唯一值得做的事

不动工。只有一件低成本、稳赚的事：**新代码避免让目录句柄继续扩散到新的接口签名**——新模块的接口用「项目 + 路径」表达，把句柄留在文件系统模块内部。这样未来抽包时的治理范围不再扩大。
