# 要素库设计理念：LLM Wiki 的服务对象反转

## 记录时间

2026-10-01（补录。要素体系与园丁的架构定稿于 2026-09-23，架构记录见《[要素园丁子代理设计](要素园丁子代理设计.md)》，但该文档从「要素库即 Wiki」的类比直接展开，未记录这套类比的源头与反转动机。本文按设计者的口述整理补记，作为要素体系的世界观源头。）

## 一句话

NovAI 的要素体系是对 Karpathy「LLM Wiki」方案的魔改：**把 Wiki 的服务对象从人类反转为 AI**。

## Karpathy 的 LLM Wiki 原案

原案运行在 VibeCoding 工具（Claude Code 这类 agent 工具）上，三个组成部分：

| 概念 | 含义 |
| :-- | :-- |
| Raw Sources | 外部来的原始文档——新闻、博客等未经整理的原料 |
| Schema | AGENTS.md / CLAUDE.md 或其他 SKILL——规范不另起炉灶，就是 agent 的指令与技能文件 |
| The Wiki | AI 依据 Schema 从 Raw Sources 整理出来的、**人类可读、方便查阅**的笔记内容 |

原案的目的是**让 AI 直接服务人类**：替人把杂乱的原文消化成易查的笔记。The Wiki 是给人看的。

## NovAI 的反转

角色不变，读者对调：

| 概念 | Karpathy 原案 | NovAI |
| :-- | :-- | :-- |
| Raw Sources | 新闻、博客等外部文档 | 小说章节原文（**给人看**） |
| Schema | AGENTS.md / CLAUDE.md / SKILL | `prompts/ELEMENT.md` |
| The Wiki | 给人看的笔记 | 要素文件 `elements/`（**给 AI 看**） |
| 服务关系 | AI 服务人类 | **AI（要素整理子智能体）服务 AI（创作主智能体）** |

## 为什么反转：服务的对象不同

Karpathy 的方案是通用知识管理：人要读原始材料太累，所以让 AI 替人整理。NovAI 面对的不是知识管理，而是长篇小说创作，它有三个绕不开的事实：

1. **小说必然是长期项目**——不可能一个会话从头写到尾。
2. **AI 的记忆有上限**——会话结束即失忆，跨会话不会自发留痕。
3. **翻原文的成本随篇幅指数增长**——如果小说达到几百万字，仍以翻阅过往章节原文的形式继续创作，检索与上下文的花费将是一个天文数字。

因此要素库对 NovAI 而言不是「方便人查阅的笔记」，而是**给 AI 的跨会话长期记忆**：把小说中的一切——人物、地点、实体、时间线、情节、世界观——存成结构化、可检索的 Wiki，让创作主 Agent 在任何新会话里都能快速查阅小说的任何情节与设定，而不必回读过往章节。原文保持为人类读者服务，Wiki 为 AI 服务，两者各司其职。

## 与要素整理子智能体的关系

这套理念的日常执行者是**要素整理子智能体**（要素园丁）——即 Wiki 世界里的 WikiGnome：页面（要素文件）随便长，园丁按 Schema（ELEMENT.md）定期修。委派架构、工具白名单、Schema 宪法等落地设计见《[要素园丁子代理设计](要素园丁子代理设计.md)》。

Wiki 的检索层由 RAG 向量索引承担（见《[向量索引与重排序设计](向量索引与重排序设计.md)》）。
