# 要素库设计理念：面向 AI 的长期记忆

## 理念来源

NovAI 的要素体系借鉴了 Karpathy 的「LLM Wiki」方案，并反转了 Wiki 的服务对象：**从方便人类查阅，转向帮助 AI 持续理解一部长篇小说。**

原案包含三个部分：

| 概念 | 含义 |
| :-- | :-- |
| 原始材料 | 新闻、博客等未经整理的外部文档 |
| 整理规范 | 智能体的指令与技能文件 |
| Wiki | AI 按规范整理出的、便于人类阅读的笔记 |

NovAI 保留「原始材料—整理规范—结构化知识」的关系，但改变了读者和服务关系：

| 概念 | NovAI 中的对应物 | 主要服务对象 |
| :-- | :-- | :-- |
| 原始材料 | 章节正文 | 人类读者与创作智能体 |
| 整理规范 | 项目内的要素规范文件 | 要素管理员 |
| 结构化知识 | 人物、地点、实体、情节、时间线与世界观等要素文件 | 创作主智能体，也可由用户直接阅读与编辑 |

这套理念中的核心协作不是「AI 替人整理资料」，而是**负责维护要素的 AI，为负责创作的 AI 维护长期记忆**。

## 为什么长篇小说需要独立记忆

长篇小说创作有三个基本约束：

1. **创作跨越多个会话。** 人物关系、地点状态和情节伏笔都需要跨会话延续。
2. **模型上下文有限。** 会话历史不能无限增长，也不能把整部小说长期塞入每次请求。
3. **回读原文有成本。** 随着篇幅增加，仅靠逐章翻找设定会越来越慢，也难以稳定发现相关内容。

要素库把散落在章节中的关键事实整理为可定位、可维护的项目文件。创作智能体在新会话中可以先查阅这些记忆，再决定是否需要回读章节原文；用户也能在外部编辑器中直接查看和修正同一份事实。

因此，要素库不是章节的摘要替代品，而是与章节分工协作的记忆层：章节保留完整叙事、语气和细节，要素保存便于持续维护的故事事实。

## 记忆的维护与使用

要素管理员按照项目内的要素规范整理文件，创作主智能体负责在实际写作中使用这些事实。两类角色共用同一套 Agent 运行时，但拥有不同的工具范围和职责边界。

不同信息采用不同的提供方式：

| 信息 | 提供方式 | 设计理由 |
| :-- | :-- | :-- |
| 人物、地点、实体、世界观 | 主智能体先看到稳定的要素目录，再按需批量加载完整内容 | 数量有限、结构稳定，需要尽量避免漏掉关键设定 |
| 情节、时间线 | 通过语义检索召回相关条目 | 随章节持续增长，适合处理含义模糊的剧情查询 |
| 章节正文 | 通过文件导航与读取工具按需查阅 | 保留完整原文，不进入要素向量索引 |

要素目录只承载名称、类型与稳定摘要等身份信息；易随剧情变化的状态主要由创作过程中的消息和文件更新承接。这样既能控制上下文成本，也避免目录因每章变化而频繁失效。
