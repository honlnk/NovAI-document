# Element 要素体系优化计划

## 记录时间

2026-06-09

## 文档目的

本文档用于规划 NovAI 后续对 `elements/` 要素体系的结构优化。

目标不是修补单个测试项目，而是为正式开发提供一套更稳定、可扩展、适合长篇小说创作的要素文件组织方案。

## 背景

当前 NovAI 的标准项目结构已经包含：

```txt
elements/
├── characters/
├── locations/
├── plots/
├── timeline/
└── worldbuilding/
```

这套结构能覆盖人物、地点、剧情、时间线和世界观规则，但真实长篇创作中还会出现大量“非人物、非地点、但需要长期追踪”的实体，例如：

- 武功
- 武器
- 坐骑
- 丹药
- 信物
- 法器
- 秘宝
- 特殊书籍
- 机关器具

这些内容与人物、地点一样，具有稳定名称、状态、来历、持有者、首次登场章节和后续变化。如果没有独立分组，容易被混入 `worldbuilding/` 或 `plots/`，导致检索和维护都变得混乱。

## 核心结论

后续建议在标准项目结构中新增：

```txt
elements/entities/
```

`entities/` 用于存放“非人物、非地点的具体实体”。

不建议使用单一的 `objects/` 分组作为总称，因为“武功”“秘术”“坐骑”并不都适合称为 object。`entities` 更接近“故事中可被独立追踪的实体”这一语义。

## 优化后的目录结构

建议标准项目结构调整为：

```txt
elements/
├── characters/       # 人物
├── locations/        # 地点
├── entities/         # 具体实体：武功、武器、坐骑、丹药、信物等
├── plots/            # 剧情事件块
├── timeline/         # 时间线阶段
└── worldbuilding/    # 世界观规则、制度、体系、门派设定
```

各目录职责如下：

| 目录 | 存放内容 | 示例 |
|:--|:--|:--|
| `characters/` | 人物角色 | 云溪、鸿影、裴行舟 |
| `locations/` | 可反复出现的地点 | 武当山、玄岳门、鸿家庄 |
| `entities/` | 非人物非地点的具体实体 | 青霜剑、太乙玄门剑、乌云踏雪、九转回春丹 |
| `plots/` | 独立剧情事件块 | 鸿家庄灭门之夜、清虚真人留婴 |
| `timeline/` | 按阶段拆分的时间线 | timeline-01-缘起.md、timeline-02-幼年.md |
| `worldbuilding/` | 抽象规则和体系 | 大靖王朝、武当派、内功境界、江湖规矩 |

## `entities/` 与 `worldbuilding/` 的边界

`worldbuilding/` 放抽象规则、体系、制度。

例如：

- 武功境界如何划分
- 武当派修行体系
- 大靖王朝制度
- 江湖门派格局
- 丹药炼制规则

`entities/` 放具体可追踪实体。

例如：

- `太乙玄门剑.md`：一门具体武功
- `青霜剑.md`：一柄具体武器
- `乌云踏雪.md`：一匹具体坐骑
- `九转回春丹.md`：一种具体丹药
- `鸿夫人的凤头钗.md`：一个具体信物

判断原则：

如果它是“规则、体系、类别”，放入 `worldbuilding/`。

如果它是“故事里会被点名、被持有、被使用、状态会变化的具体东西”，放入 `entities/`。

## `entities/` 文件建议模板

```md
# 实体名称

## 基本信息
- **类型**：武器 / 武功 / 坐骑 / 丹药 / 信物 / 法器 / 书籍 / 其他
- **首次出现**：第XXX章
- **当前状态**：待补充

## 简介
- 用一到三句话说明该实体是什么，以及它在故事中的基本作用。

## 外观或表现
- 若是武器、物品、坐骑，记录外观、材质、颜色、特征。
- 若是武功、秘术，记录施展效果、气势、招式表现。

## 来历
- 记录来源、制造者、传承、获得方式或背后故事。

## 当前归属
- **持有者 / 使用者**：待补充
- **相关人物**：待补充
- **相关地点**：待补充

## 能力或用途
- 记录功能、效果、限制、代价、使用条件。

## 剧情关联
- 记录相关剧情块、章节和伏笔。

## 状态变化
- 按章节记录获得、转移、损坏、失去、升级、封印等变化。
```

## 其他要素类型的模板优化方向

### `plots/`

剧情块应按“事件”拆分，不应默认生成一个总的 `剧情大纲.md`。

建议命名：

```txt
plot-001-鸿家庄灭门之夜.md
plot-002-火中拾婴.md
plot-003-玄岳门遇裴行舟.md
```

建议字段：

- 所属章节
- 剧情类型
- 核心事件
- 关键细节
- 登场人物
- 情感落点
- 暗线铺垫
- 关联要素

### `timeline/`

时间线应按故事阶段拆分，不应默认生成一个无限增长的 `时间线.md`。

建议命名：

```txt
timeline-01-缘起.md
timeline-02-幼年.md
timeline-03-收徒.md
```

建议要求：

- 必须包含明确的故事内时间
- 可以使用架空朝代和年号
- 单个时间线文件不宜过大
- 一个大故事阶段对应一个时间线文件

### `characters/`

人物文件后续应增加更适合生成约束的字段：

- 称呼规则
- 年龄阶段
- 与关键人物的关系
- 行为边界
- 当前状态
- 首次登场章节
- 相关剧情块

### `locations/`

地点文件应明确：

- 空间位置
- 可见性和可达性
- 与其他地点的距离关系
- 首次出现章节
- 相关剧情块

这可以避免出现“山上是否能看见山脚建筑”这类空间逻辑问题。

## Agent 行为要求

后续 Agent 在创建或整理要素时，应遵守以下规则：

1. 人物一人一文件，放入 `characters/`。
2. 地点一地一文件，放入 `locations/`。
3. 具体物品、武功、坐骑、丹药、信物等放入 `entities/`。
4. 剧情按事件拆块，放入 `plots/`。
5. 时间线按故事阶段拆分，放入 `timeline/`。
6. 抽象规则、门派制度、世界观体系放入 `worldbuilding/`。
7. 不把剧情总纲当作剧情块直接写入 `plots/`。
8. 不把具体实体混入 `worldbuilding/`。
9. 修改章节后，如果影响人物、地点、实体、剧情或时间线，应主动提示或同步相关要素。

## 实施计划

### Step 1：项目初始化结构调整

在新建小说项目时，默认创建：

```txt
elements/entities/
```

同时确保文件树和扫描逻辑能展示该目录。

### Step 2：类型定义与扫描适配

将 element 类型扩展为：

```ts
type ElementType =
  | 'character'
  | 'location'
  | 'entity'
  | 'plot'
  | 'timeline'
  | 'worldbuilding'
```

相关能力需要同步适配：

- 文件扫描
- 要素解析
- 要素写入
- RAG retrieval metadata
- UI 分组展示
- 检索过滤条件

### Step 3：要素模板接入

为不同要素类型准备默认 Markdown 模板。

最低优先级模板：

1. `entity`
2. `plot`
3. `timeline`
4. `character`
5. `location`

### Step 4：Agent Prompt 更新

更新内置 Agent 系统提示词和工具使用策略，让模型在创建要素时知道：

- 哪些内容应该放入 `entities/`
- 剧情块如何拆
- 时间线如何拆
- 何时应更新已有要素而不是创建重复文件

### Step 5：真实项目迁移策略

对已有项目不强制迁移。

建议提供软策略：

- 新项目默认创建 `entities/`
- 打开旧项目或恢复上次项目时，如果缺少 `elements/entities/`，可在项目修复或检查时补齐
- 不自动移动旧文件
- 后续可提供“整理要素结构”的 Agent 指令，由用户确认后迁移

## 优先级

高优先级：

- 新增 `elements/entities/`
- 扩展 element 类型
- 更新要素扫描和 RAG metadata
- 更新 Agent 创建要素的默认策略

中优先级：

- 为 `entities/`、`plots/`、`timeline/` 建立模板
- 为人物和地点补充更强约束字段

低优先级：

- 自动迁移旧项目
- 完整要素整理 UI
- 复杂的要素关系图谱

## 验收标准

当前落地状态：

1. 新建项目、打开/修复项目、恢复上次项目都会补齐 `elements/entities/`。
2. `ElementType` 已包含 `entity`。
3. 规则型要素提取可以将武器、武功、丹药、信物等写入 `entities/`。
4. `entities/` 文件可参与要素解析、RAG metadata、检索过滤和 Agent `RagSearch` 工具结果。
5. UI 内容面板已展示实体提取数量。
6. 项目检查会识别缺失的要素子目录，旧项目不会因缺少 `entities/` 而报错，修复或恢复时会补齐目录。

后续仍待补齐：

完成后应满足：

1. 剧情块默认按事件拆分，而不是写成单个总纲。
2. 时间线默认按阶段拆分，而不是写成单个总文件。
3. 为 `entities / plots / timeline / characters / locations` 补齐更稳定的默认模板。
4. 后续可提供“整理要素结构”的 Agent 指令，由用户确认后迁移旧文件。
