### 完成 RAG 索引状态栏 + contentHash 增量重建（worktree `honlnk/rag-status-bar`）

把 RAG 索引状态/重建入口从设置页移到主工作区底部常驻状态栏，要素写入后由事件总线自动反映 stale，用户点击状态栏才重建；重建时用 contentHash 短路，未变文件复用旧向量。

**问题**：索引状态此前藏在 SettingsModal 的「向量索引」卡片里——设置页是放一次性配置的地方，用户配完就不常进；但索引会随每次要素写入变 stale，是高频变化的运行态。把运行态塞进配置页，导致「写完要素 → 打开设置 → 找卡片 → 点重建」这条动线和创作流割裂。同时 ProjectView 的 stale 提示是硬编码的乐观 toast（假设写入必 stale），且无增量能力——手动重建走全量，对所有要素重新 Embedding。

**实现**：
- **事件总线 `index-events.ts`**：基于 EventTarget，独立于 AgentUiEvent（后者是 Agent Loop 专用通道，而索引变化来自要素写入、手动重建等多条非 Agent 路径）。`markProjectIndexStale`/`buildProjectIndex` 写完 meta 后 `dispatchIndexChange`，`onRagIndexChange` 带 projectId 过滤。app 层经 `rag-service.subscribeIndexChange` 透传订阅。
- **contentHash 增量短路**：`buildProjectIndex` 循环内先算 contentHash（口径对齐 writer 的 `normalizeForComparison`，把 `updatedAt:` 行归一为占位符，这样「只刷新 updatedAt」不会让 hash 变化），与旧文档的 contentHash + embeddingModel + embeddingDim + embeddingTextVersion 比对，全一致则复用旧 vector 跳过 `createEmbedding`。增量场景下旧文档 sourcePath 不在本次范围的调 `removeDocuments` 清理（此前要素删除无人处理）。
- **rag-service**：`rebuildIndex(projectId, sourcePaths?)` 有 sourcePaths 则 `incremental-update`、无则 `manual-rebuild`；新增 `subscribeIndexChange`。
- **app 层**：`useIndexStore` 持有响应式 indexMeta，`init` 订阅事件 + 首次 inspect，`dispose` 退订；`IndexStatusBar.vue` 底部常驻，健康度指示点（ready 绿/stale 琥珀/error 红/building 蓝转圈）+ 状态文案（`索引就绪 · 156 项`），stale/error 可点击重建，hover 显示构建时间/错误；`ProjectView` 根容器改 `flex flex-col` 包一层挂状态栏，去掉要素写入的 stale toast；`SettingsModal` 移除索引卡片及相关逻辑（约 -90 行）。

**关键设计决策**：
1. **触发方式选「仅标 stale + 一键重建」而非写入后自动重建**：自动重建每次写要素都触发 Embedding 调用，用户可能没察觉在花钱；改为状态栏常驻显示过期、用户点一下才重建，控制权完全在用户。
2. **contentHash 口径排除 updatedAt 行**：要素文件每次写入都刷新 updatedAt（writer.ts），若 hash 含该行则短路永远失效。对齐 normalizeForComparison 后，「只改 updatedAt」不触发重算。
3. **事件总线独立于 AgentUiEvent**：索引变化路径多（要素写入 / 手动重建 / Agent 写要素），强行塞进 Agent Loop 专用通道会覆盖不全且耦合。

**测试**：新增 `indexer.test.ts`（6 例：全量不短路 / 增量短路 / updatedAt 不误触发 / 正文变化重算 / 模型变化重算 / 删除清理）与 `index-events.test.ts`（3 例：同项目投递 / 跨项目过滤 / 退订）。全量 121 测试通过，typecheck + build 干净。

**与计划的偏差**：无。

### 完成 Agent 控制能力 Step 1（结构化文件变更结果）（`949d540`）

对应 [Agent 控制能力补强计划](../plans/Agent控制能力补强计划.md) Step 1，在 worktree 上开发后合回 `honlnk/dev` 推送。

**问题**：`agent-service.collectChangedFiles` 原先用 `isSuccessfulToolResult` 正则（`^(已读取|已修改|已新建|已将|已查看|已在)`）从工具结果中文文本反推文件变更，而写工具的 output 本就携带结构化路径——被 `formatResult` 压成文本后丢失。工具措辞一变，右侧面板「自动打开变更文件」就会失效。

**实现**：让工具层显式声明变更，一路结构化透传。

- `core/tools/types.ts`：新增 `FileChange` 类型，`ToolDefinition` 增加可选 `extractFileChange(output)` 方法。
- 4 个写工具各实现 `extractFileChange`（CreateFile→created / EditFile→updated / RenameFile→renamed / DeleteFile→deleted 含 trashPath），每个 3 行。
- `core/agent/messages.ts`：`AgentToolResultMessage` 增加可选 `fileChange?` 字段。
- `core/agent/tool-execution.ts`：成功执行后调用 `extractFileChange` 挂到返回消息和 `tool-result` 事件；失败时不挂。
- `core/services/agent-service.ts`：`collectChangedFiles` 改读 `message.fileChange`，**删除** `isSuccessfulToolResult`/`extractTrashPath`/`collectToolResultTextById`/`toChangedFile` 共约 70 行文本反推逻辑。
- `core/chat/session.ts`：`lastWrittenPath` 从「按工具名分支读 `event.call.input.path/toPath`」改为读 `event.fileChange`（新增 `resolveWrittenPath` 辅助函数）。
- 测试：`file-tools.test.ts` +5（写工具 extractFileChange 输出 + 只读工具无该方法）；新增 `tool-execution.test.ts`（成功透传 / 只读 undefined / 失败 undefined）。

**意义**：消除「changedFiles 依赖工具措辞、不稳定」风险；更关键的是它是 Step 2（写入确认 + diff 预览）、Step 3（暂停/确认/拒绝）的地基——确认请求可直接基于结构化 `fileChange` 生成。改动全部在 `packages/core`，与 R6（`packages/app`）零冲突。

**与计划的偏差**：无。计划即「写工具返回结构化变更，service 层不再文本推导」，实现完全对齐。`session.lastWrittenPath` 的结构化改造是计划外顺带修复的同类脆弱点。

### 完成 Agent 控制能力 Step 2/3（写入前确认 + 暂停/确认/拒绝 + 旧残留清理）（`0707809`/`b0651e7`）

对应 [Agent 控制能力补强计划](../plans/Agent控制能力补强计划.md) Step 2/3。**确认策略经用户确认为「每次写操作都确认」**（最安全）。

**功能实现（`0707809`，+461/-6，16 文件）**：

- **问题**：此前写工具（CreateFile/EditFile/RenameFile/DeleteFile）直接执行，用户在文件被改前完全看不到、拦不住，是 Agent 工作流最大的信任风险。
- **机制**：写工具执行前暂停，展示预览，用户确认才写入，拒绝则回灌模型让其调整。
- **core 层**：`ToolDefinition` 新增可选 `buildConfirmation(input)`，4 个写工具各自从 `validatedInput` 构造 `WriteConfirmation`（edit/create 带完整文本用于 diff，rename/delete 仅路径级）；`tool-execution` 在 `tool.core.run` 前拦截写工具，调 `confirm` 回调等待决定，拒绝时不执行 run 并返回结构化拒绝结果回灌模型（让模型自然调整而非硬中止），确认中断（停止）按拒绝处理；`tool-orchestration`/`query`/`session` 透传 `confirm`；`agent-service` 新增确认注册表 `confirmationMap` + `respondConfirmation(confirmationId, accepted)`，`confirm` 回调发 `confirmation-required` 事件并 `await` UI 响应，出错/停止时 `rejectPendingConfirmations` 清理未决确认。
- **app 层**：chat store 加 `pendingConfirmation` + `confirmWriteTool`/`rejectWriteTool`；新建 `WriteConfirmationCard.vue`（抄 `ExtractionFlowPanel` 预览样式），按 kind 渲染 create 内容预览 / edit old→new diff / rename from→to / delete 路径说明；ChatPanel 在消息列表与输入框之间挂载卡片。
- **测试**：tool-execution +4 个确认用例（接受执行 / 拒绝不执行 / 只读工具不触发 / 确认中断按拒绝）。

**关键设计决策**：
1. **拒绝不终止 Agent**：拒绝作为 tool result 回灌模型，让其自然调整（改路径或向用户解释），符合 Agent 协作模型，而非硬停。
2. **确认与停止正交**：等待确认期间用户仍可点停止（confirm 抛错按拒绝处理，query Loop 的 abort 检查接管）。
3. **预览数据来自 validatedInput**：EditFile 的 oldText/newText、CreateFile 的 content 都在校验后的 input 里，直接生成 diff，不额外读盘。

**旧残留清理（`b0651e7`，-529 行）**：删除 `confirmPendingFileChange`/`discardPendingFileChange`/`createPendingFileChange`/`callTool`/`loadRecentChapters`/`flattenChapterPaths` 及 `analyzeTurnMode`/`buildUserPrompt` 等 helper（约 390 行）+ 整个 `chat/tools.ts`（旧 `ToolDefinition.call` 体系，零外部引用）+ `types/chat.ts` 的 `PendingFileChange`/`ToolRuntimeContext`/旧 `ToolDefinition` 类型与 `pendingFileChange`/`lastTaskType` 字段。这些是早期方案的死代码，新确认流程完全替代。净效果：功能 +460 行、死代码 -529 行，代码总量反降。

**意义**：补齐 Agent 写入链路的核心信任环节，写工具不再是黑箱；与 Step 1（结构化变更）形成闭环——Step 1 让工具声明「我要改什么」，Step 2/3 让用户「在改之前决定准不准」。

**与计划的偏差**：Step 2/3 计划本作为两个独立 Step，实际同一批次落地（同一提交 `0707809`），因为暂停机制（Step 3）是确认请求（Step 2）的交互下半场，分开做会卡住 Agent Loop。确认策略「每次都确认」是实施时经用户选定的，计划文档原本未限定。

### 扩展 Claude Code 风格项目文件工具

本轮围绕“受控文件工具，而不是通用 Bash”继续升级 Agent 工具体系。

当前 Agent 可调用的项目文件工具已扩展为：

- `ListDirectory`：查看项目内某个已存在目录的直接子项，替代 `ls` 场景。
- `FindFiles`：按 glob 路径模式查找文件，替代 `Glob / find` 场景。
- `ReadFile`：读取 `.md / .json / .txt` 文件，支持行号输出、`offset / limit`、大文件完整读取限制、空文件与越界提示。
- `EditFile`：精确替换已有文件片段，强化了空 `oldText` 防误写、重复文本消歧、引号风格兼容与更明确的错误提示。
- `CreateFile`：只创建不存在的新文件，父目录自动创建，目标已存在时拒绝覆盖并引导改用 `ReadFile -> EditFile`。
- `RenameFile`：重命名或移动单个文本文件，源文件必须存在，目标文件不能存在，目标父目录自动创建。
- `DeleteFile`：将单个文本文件移入 `.novel/trash` 回收站，不直接永久删除。

同时移除了旧 chat 工具体系中的 `Bash` 占位实现与类型残留。NovAI 后续不再开发通用 BashTool，而是继续用专用工具覆盖小说项目需要的文件操作场景。
