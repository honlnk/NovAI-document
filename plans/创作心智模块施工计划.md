# 创作心智模块施工计划：伏笔追踪 + 全本节奏卡

> 状态：设计定稿，待施工
>
> 背景：见《[NovAI 市场定位与痛点分析](../product/NovAI市场定位与痛点分析.md)》§5.1。伏笔与节奏是长篇连载最容易翻车、且市面产品都没稳定解决的两大痛点，是 NovAI 建立品类定义权的机会方向。
>
> 本文档由《伏笔追踪一等公民化计划》与《全本节奏卡结构化计划》合并而成，作为统一施工依据。

## 一、核心设计判断

### 1.1 创作心智 ≠ 历史记忆

NovAI 的信息架构分两层：

| 层级 | 目录 | 职责 | 写入时机 | 写入者 | 读取者 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **AI 的历史记忆** | `elements/` | 事实的记录，被动沉淀 | 写完章节后 | 要素管理员（AI 自动） | 主 Agent（写时查） |
| **作者的创作心智** | `plans/`、`foreshadowing/`、`rhythm/` | 意图的登记，主动驱动 | 写章节之前 | 作者为主，主 Agent 协助 | 主 Agent（写前必读）+ 作者（看板） |

关键区分：要素管理员的工作方式是"概括、合并、精简"——这对历史记忆是对的，但对创作心智是灾难。设定账本管"是什么"，伏笔账本管"欠了什么"，两本账不能混。

因此伏笔和节奏卡独立存放，**只对主 Agent 开放，要素管理员不可见**。

### 1.2 伏笔与节奏的同构

两者都是"作者对自己的承诺"：

| 维度 | 计划 | 伏笔 | 节奏卡 |
| :--- | :--- | :--- | :--- |
| 本质 | 作者打算做什么 | 作者欠读者什么 | 作者打算让读者怎么感受 |
| 状态 | 收集箱/计划中/进行中/已完成/已搁置 | 已埋/推进中/已收/已放弃 | 规划中/已写/偏差 |
| 时间感 | 什么时候做 | 什么时候收 | 什么时候该高/该低 |
| 视图 | 看板 | 看板 | 看板 |

UI 复用计划板骨架（看板 + 侧栏详情 + 拖拽），详情面板扩展字段。

### 1.3 伏笔是坏账预防

调研发现的三种坏账：

| 翻车类型 | 病因 |
| :--- | :--- |
| 忘还的 | 第 80 章随手埋的，写到第 300 章早忘了 |
| 还得太小的 | 账本上勾掉了，但读者觉得"就这？" |
| 临时补写的 | 写到第 300 章需要伏笔，回第 80 章补一句 |

核心病理：**作者的记忆按章组织，读者的记忆按账组织，两套索引不一样。** 伏笔功能的核心价值不是"记下来"，而是"在该收的时候提醒"。

### 1.4 节奏卡是失控预防

调研发现的三种翻车：

| 翻车类型 | 病因 |
| :--- | :--- |
| 流水账 | 连续 5 章主角都在升级、收货、被人夸，没有冲突 |
| 情绪过山车 | 连续 10 章压抑 → 突然一章大高潮 → 又突然日常 |
| 章末无钩 | 每章结尾都是"他躺在床上睡了"，读者留存率掉 |

核心病理：**AI 每次只看"这一章要写什么"，看不到"这一章在整本书的什么位置"。** 节奏卡的核心价值不是"记下来"，而是"在写之前告诉 AI 这一章该是什么温度"。

### 1.5 节奏 ≠ 时间线

节奏以**章节号**为度量单位（读者翻页的次数），关心读者情绪曲线；时间线以**故事内时间**为度量单位，关心事件先后与因果。两者独立，但可交叉引用（如"时间跳跃章往往是节奏呼吸口"）。节奏卡不承担时间线功能。

## 二、文件结构

```
我的小说/
├── chapters/
│   ├── 第一卷/
│   │   ├── 第001章-XXX.txt
│   │   └── ...
│   └── 第二卷/
├── elements/              ← 要素管理员可整理
├── plans/                 ← 计划（已有）
├── foreshadowing/         ← 伏笔（新增，主 Agent 专属）
│   ├── F-001-旧照片之谜.md
│   ├── F-002-母亲的沉默.md
│   └── ...
├── rhythm/                ← 节奏卡（新增，主 Agent 专属）
│   ├── R-001-第001章节奏.md
│   ├── R-002-第002章节奏.md
│   └── ...
├── prompts/
├── novel.config.json
└── .novel/
```

- 一条伏笔/节奏卡一个 Markdown 文件，文件名带 ID 前缀（与章节命名风格一致）
- ID 由系统生成，作者不可改；名称可改，文件名同步
- 伏笔可跨章，节奏卡**一章一卡**（与章节一一对应，不合并、不拆分）

## 三、伏笔格式

### frontmatter

```yaml
---
id: F-001
name: 旧照片之谜
status: developed
planted_at: 第一卷/第012章
payoff_window: [第二卷/第080章, 第二卷/第090章]
related_characters: [主角, 研究员K, 母亲]
related_entities: [旧照片]
related_chapters: [第一卷/第028章, 第一卷/第051章]
is_red_herring: false
resolved_at: null
abandoned_reason: null
---
```

字段说明：

| 字段 | 必填 | 说明 |
| :--- | :--- | :--- |
| id | 是 | 系统生成，格式 `F-XXX` |
| name | 是 | 作者可改 |
| status | 是 | 见下方"状态机" |
| planted_at | 是 | 埋设章节，完整路径（`卷/章`） |
| payoff_window | 建议 | 预计回收窗口，**区间**而非单点（连载节奏会调整） |
| related_characters | 建议 | 关联角色 |
| related_entities | 可选 | 关联物品 |
| related_chapters | 自动 | 暗示历史，每次再提及的章节列表 |
| is_red_herring | 可选 | 是否故意误导（红鲱鱼） |
| resolved_at | 完结时填 | 实际回收章节 |
| abandoned_reason | 放弃时填 | 放弃原因，避免日后误以为漏写 |

### 正文

```markdown
## 读者视角（当时可见事实）

主角在旧书店发现一张褪色的照片，照片里有一个跟他长得一模一样的人。
他随手塞进口袋，没多想。

## 作者真相

主角不是父母的亲生儿子——他是那个研究员的复制体。
```

**读者视角与作者真相必须分开记。** 这是伏笔系统最核心的字段：作者知道钥匙的最终用途，不代表第 9 章的主角也知道。

### 状态机

#### 默认 4 状态（UI 看板列）

| 状态 | 含义 |
| :--- | :--- |
| 已埋 | 第一次出现在正文，还没暗示过 |
| 推进中 | 有过暗示或发展，还没到回收窗口 |
| 已收 | 已回收 |
| 已放弃 | 作者主动放弃（有原因记录） |

#### 完整 6 状态（frontmatter 存储）

| 状态 | 英文 | 含义 |
| :--- | :--- | :--- |
| 埋入 | planted | 第一次出现 |
| 暗示 | hinted | 后续章节不引人注目地再碰一下 |
| 发展 | developed | 开始产生实际剧情影响 |
| 揭晓 | revealed | 真相大白 |
| 解决 | resolved | 影响收尾 |
| 放弃 | abandoned | 刻意不收 |

**可配置**：用户在项目设置里选 4 状态或 6 状态，UI 看板列数随之变化。frontmatter 始终存 6 状态精确值。

## 四、节奏卡格式

### frontmatter

```yaml
---
id: R-083
name: 第083章节奏
status: planned
chapter_ref: 第二卷/第083章
volume: 第二卷

# 计划值（作者/AI 规划时填写）
planned_conflict: 3
planned_mood: 温馨
planned_hook: 无
planned_payoff: 收获
planned_characters: [主角, 师妹]
planned_note: "大高潮后的喘息章，回家吃饭、整理战利品、闲聊"

# 实际值（写完后回写）
actual_conflict: null
actual_mood: null
actual_hook: null
actual_payoff: null
actual_note: null

# 偏差标记
deviation_flag: false
deviation_note: null
---
```

字段说明：

| 字段 | 必填 | 说明 |
| :--- | :--- | :--- |
| id | 是 | 系统生成，格式 `R-XXX` |
| name | 是 | 作者可改 |
| status | 是 | 见下方"状态机" |
| chapter_ref | 是 | 关联章节，完整路径（`卷/章`） |
| volume | 是 | 所属卷 |
| planned_conflict | 是 | 计划冲突强度，1~10 |
| planned_mood | 是 | 计划情绪基调，见下方"情绪基调枚举" |
| planned_hook | 是 | 计划章末钩子类型，见下方"钩子类型枚举" |
| planned_payoff | 是 | 计划爽点类型，见下方"爽点类型枚举" |
| planned_characters | 建议 | 计划出场主要角色 |
| planned_note | 建议 | 自然语言补充（"大高潮后的喘息章"） |
| actual_conflict | 写后回写 | 实际冲突强度 |
| actual_mood | 写后回写 | 实际情绪基调 |
| actual_hook | 写后回写 | 实际章末钩子 |
| actual_payoff | 写后回写 | 实际爽点类型 |
| actual_note | 写后回写 | AI 对本章节奏的自评 |
| deviation_flag | 自动 | 计划与实际偏差是否超阈值 |
| deviation_note | 自动 | 偏差说明 |

### 正文

```markdown
## 节奏意图

大高潮（第 82 章悲壮决战）之后必须让读者喘口气。
本章写主角回家吃饭、跟师妹闲聊、整理战利品。
不要战斗，不要冲突升级，不要新悬念。

## 上下文衔接

- 上一章（第 82 章）：冲突 9、悲壮、情感爆发
- 下一章（第 84 章）：计划冲突 4、轻松、悬念

## 作者备注

（自由文本，作者记录任何想法）
```

**节奏意图与上下文衔接必须分开记。** 前者是"本章要什么温度"，后者是"前后章的温度差"——AI 需要同时看到两者才能判断"本章是不是该降温"。

### 状态机

| 状态 | 英文 | 含义 |
| :--- | :--- | :--- |
| 规划中 | planned | 本章还没写，节奏卡只有计划值 |
| 已写 | written | 本章已写，实际值已回写，偏差在阈值内 |
| 偏差 | deviated | 实际值与计划值偏差超阈值，需要作者注意 |

### 偏差判定规则

| 维度 | 偏差阈值 | 说明 |
| :--- | :--- | :--- |
| 冲突强度 | 计划与实际差值 ≥ 3 | 计划 3 实际 7 = 偏差 |
| 情绪基调 | 计划与实际不一致 | 计划"温馨"实际"悲壮" = 偏差 |
| 章末钩子 | 计划"无"实际有，或计划有实际"无" | 有无之间的翻转 = 偏差 |
| 爽点类型 | 计划与实际不一致 | 计划"收获"实际"无" = 偏差 |

**可配置**：用户在项目设置里选偏差阈值（默认冲突差值 3）。`deviation_flag` 由系统在回写实际值时自动计算，作者不可手动改。

### 枚举值定义

#### 情绪基调（mood）

| 值 | 说明 |
| :--- | :--- |
| 压抑 | 主角处于困境，读者感到憋屈 |
| 紧张 | 冲突正在升级，读者屏息 |
| 悲壮 | 有代价的胜利或牺牲 |
| 轻松 | 日常、幽默、无压力 |
| 温馨 | 情感暖色，人际亲密 |
| 悬疑 | 信息不完整，读者好奇 |
| 爽感 | 主角占优，读者畅快 |
| 恐怖 | 威胁迫近，读者不安 |
| 悲伤 | 失去、离别、遗憾 |
| 平静 | 过渡、铺垫、无强烈情绪 |

#### 章末钩子类型（hook）

| 值 | 说明 |
| :--- | :--- |
| 悬念 | 提出一个问题，不回答 |
| 危机 | 主角面临新的威胁 |
| 反转 | 读者预期被打破 |
| 情感爆发 | 强烈的情绪冲击 |
| 揭秘 | 部分真相揭露 |
| 无 | 章末收束，无钩子 |

#### 爽点类型（payoff）

| 值 | 说明 |
| :--- | :--- |
| 升级 | 主角能力/境界提升 |
| 打脸 | 反派被惩治/轻视者被震慑 |
| 收获 | 获得物品/资源/信息 |
| 情感 | 人际关系推进（友情/爱情/亲情） |
| 揭秘 | 读者获得新的信息优势 |
| 无 | 本章无明确爽点 |

## 五、Agent 工具

### 伏笔工具（主 Agent 专属，要素管理员不装配）

| 工具 | 用途 | 装配时机 |
| :--- | :--- | :--- |
| ForeshadowingList | 列出/筛选伏笔（按状态、章节窗口） | 始终 |
| ForeshadowingRead | 读单条（**不含作者真相**） | 写正文时 |
| ForeshadowingReadForPlanning | 读单条（**含作者真相**） | 规划阶段 |
| ForeshadowingCreate | 新建伏笔 | 写后同步 |
| ForeshadowingUpdate | 更新状态/追加暗示/标记回收 | 写后同步 |
| ForeshadowingDelete | 删除（走回收站） | 作者明确要求 |
| ForeshadowingCheck | 高层：返回"第 N 章该收哪些伏笔" | 写前主动调用 |
| ForeshadowingSync | 高层：通读本章，提案伏笔变更 | 写后主动调用 |

### 节奏卡工具（主 Agent 专属，要素管理员不装配）

| 工具 | 用途 | 装配时机 |
| :--- | :--- | :--- |
| RhythmList | 列出/筛选节奏卡（按状态、卷、章节范围） | 始终 |
| RhythmRead | 读单条（含计划值与实际值） | 始终 |
| RhythmCreate | 新建节奏卡 | 规划阶段 |
| RhythmUpdate | 更新计划值或回写实际值 | 写后同步 |
| RhythmDelete | 删除（走回收站） | 作者明确要求 |
| RhythmCheck | 高层：返回"第 N 章的计划节奏 + 前后章节奏" | 写前主动调用 |
| RhythmSync | 高层：通读本章，回写实际值并评估偏差 | 写后主动调用 |
| RhythmCurve | 高层：返回指定章节范围的节奏曲线数据 | 作者查询时 |

### 真相字段的权限设计

可见性不是 UI 问题，是数据流问题。模型读到的是 md/json，防线必须在工具读取时做字段过滤。

采用**双工具方案**：

- 写正文时主 Agent 只装配 `ForeshadowingRead`（永远不含真相）
- 规划阶段才装配 `ForeshadowingReadForPlanning`（含真相）

这是**装配层面的权限**，模型无法越权。不采用"显式参数"方案（模型可能误传 `includeTruth: true`）。

## 六、写前/写后工作流

### 写第 N 章前

1. Agent 接到"写第 N 章"指令
2. 主动调用 `ForeshadowingCheck(chapter: N)` → 返回"以下伏笔预计在本章回收"
3. 主动调用 `RhythmCheck(chapter: N)` → 返回"本章计划节奏 + 前后章节奏"
4. 两者结果合并注入规划上下文（伏笔只含读者视角）
5. 写作时提示"本章可考虑回收 F-007，读者目前知道的是 XXX；本章计划冲突 3、情绪温馨、章末无钩，上一章冲突 9、悲壮——请降温"

### 写完第 N 章后

1. Agent 调用 `ForeshadowingSync(chapter: N)` → 提案伏笔变更
2. Agent 调用 `RhythmSync(chapter: N)` → 回写实际节奏 + 偏差评估
3. 两者提案合并给作者审阅，**作者批准后才落盘**

### 回收当量评估

调研最有洞察的一条：**"最弱的还账形式是解释。"** 一次够分量的回收，至少要给足三样之一：

- **改变**：局面变了，有人的立场变了，有条路打开了
- **代价**：真相出来的同时有人失去了什么
- **重新解释**：让读者此前读过的一批内容忽然有了另一层意思

`ForeshadowingSync` 在标记伏笔"已回收"时，必须回答"这次回收给了哪一样"。一样不占的回收，提案时标注"这次回收只是解释，当量偏弱"。

### 节奏曲线查询

作者问"最近节奏怎么样"时：

1. Agent 调用 `RhythmCurve(range: "最近 20 章")`
2. 返回每章的计划值与实际值列表
3. Agent 用自然语言总结："最近 5 章冲突强度持续 7 以上，建议安排一章低强度呼吸口"

## 七、UI 设计

### 侧边栏

新增"伏笔"和"节奏"入口，与"计划"平级。

### 看板视图

- 伏笔：列数可配置（默认 4 列，高级 6 列）
- 节奏：**三列**（规划中 / 已写 / 偏差）
- 卡片可拖拽改状态
- 伏笔"该收了"高亮：自动筛选 `payoff_window` 包含当前最新章号的伏笔
- 节奏"偏差"列自动高亮：凡 `deviation_flag = true` 的卡片自动进入此列，不可手动拖出

### 卡片展示

**伏笔卡片**：伏笔名、埋设章节、回收窗口、状态标签。

**节奏卡片**：章节名、计划冲突强度（数字 + 颜色：1~3 绿色、4~6 黄色、7~10 红色）、计划情绪基调标签、计划章末钩子标签；如果已写：实际值与计划值的对比（一致则绿色勾，偏差则红色警告）。

### 详情面板

**伏笔详情**：埋设章节、回收窗口、关联角色、关联物品、读者视角（直接显示）、作者真相（直接显示，标注"作者视角"）、暗示历史时间线、回收当量评估。

**节奏详情**：关联章节（只读）、计划值编辑区（冲突强度滑块、情绪/钩子/爽点下拉、出场角色多选、节奏意图文本框）、实际值展示区（只读）、偏差说明、上下文衔接（上一章/下一章节奏摘要）、作者备注。

### 章节侧栏

- 显示"本章相关伏笔"和"本章节奏卡"，**实时计算**（根据 frontmatter 反查），**不写入章节文件**。
- 章节文件保持纯净，伏笔和节奏系统对章节是只读引用。

### 卷级筛选

节奏看板顶部提供"按卷筛选"下拉，默认显示当前最新卷。

## 八、要素侧的双向链

章节文件不带伏笔/节奏字段，但**要素文件可以登记关联伏笔**：

```yaml
# elements/characters/林远.md
---
name: 林远
related_foreshadowing: [F-001, F-003]
---
```

这样从人物视角能看到"他牵动了哪些伏笔"，而章节文件不被污染。

## 九、与章节文件的关系

伏笔和节奏卡**都不写入章节文件**。章节文件保持纯净（纯 txt），伏笔和节奏信息只存在于各自目录。

选择独立目录而非章节 frontmatter 的理由：

1. 章节文件格式不变（纯 txt），不引入 frontmatter 解析复杂度
2. 伏笔/节奏卡与章节通过 `chapter_ref` 字段关联，不污染章节内容
3. 章节侧栏实时计算反查，与要素的"本章相关"同一模式

## 十、代码复用约定

伏笔与节奏卡共享同一套"看板卡片"交互骨架。施工时必须最大化复用计划模块已有代码，避免三份平行实现。

### 10.1 复用策略：泛化而非复制

计划模块（`core/plans/`）的代码按三层拆分：

| 层 | 文件 | 复用方式 |
| :--- | :--- | :--- |
| **通用底层** | frontmatter 解析/序列化、排序、冲突检测、回收站 | 上提到 `core/card-board/`，三个模块共用 |
| **领域类型** | `types/plans.ts` 中的 PlanCard、PlanStatus、PlanError | 泛化为泛型 `CardBoard<TStatus>`，各模块声明自己的状态枚举 |
| **业务逻辑** | 工具 schema、写前/写后钩子、偏差判定 | 各模块独立实现，不共享 |

### 10.2 必须上提共享的代码

以下代码与"计划"业务无关，任何看板卡片模块都需要：

| 代码 | 当前位置 | 泛化方式 |
| :--- | :--- | :--- |
| frontmatter 拆分与解析 | `core/plans/parser.ts` 的 `splitFrontmatter`、`parseFrontmatterLines` | 抽到 `core/card-board/parser.ts`，纯函数无业务依赖 |
| 时间/排序值规范化 | `core/plans/parser.ts` 的 `normalizeTime`、`normalizeOrder` | 同上 |
| 内容 hash 计算 | `core/util/hash.ts` | 已共享，不动 |
| 回收站路径生成 | `core/fs/trash.ts` | 已共享，不动 |
| 同列排序算法 | `core/plans/identity.ts` 的 `sortPlanCards`、`nextOrderInColumn`、`orderAfter` | 泛化为泛型，状态字段由调用方传入 |
| 冲突检测逻辑 | `core/plans/store.ts` 的 hash 比对 + PlanConflictError | 泛化为 `CardBoardConflictError`，错误消息由调用方定制 |
| 文件重命名逻辑 | `core/plans/store.ts` 的 `resolveRenamedPath` | 泛化：文件名模式由调用方传入 |
| 目录扫描骨架 | `core/plans/catalog.ts` | 泛化：目录名和文件过滤规则由调用方传入 |

### 10.3 各模块独立实现的代码

以下代码与具体业务强相关，不共享：

| 代码 | 原因 |
| :--- | :--- |
| 状态枚举与看板列定义 | 计划五列、伏笔四列（可配六列）、节奏三列，完全不同 |
| 卡片字段 Schema | 计划只有正文，伏笔有 frontmatter 字段，节奏有计划值/实际值双轨 |
| Agent 工具 | 工具名称、schema、权限档位、写前/写后钩子完全不同 |
| 详情面板字段 | 计划只有正文编辑，伏笔有埋设章节/回收窗口/关联角色，节奏有滑块/下拉/对比展示 |
| 写前/写后工作流 | 计划没有，伏笔有 Check/Sync，节奏有 Check/Sync/Curve |
| 偏差判定逻辑 | 节奏卡独有（冲突差值 ≥ 3、情绪不一致、钩子翻转、爽点不一致） |
| 枚举值校验 | 节奏卡独有的枚举体系 |

### 10.4 泛化时机

**在伏笔施工的第一阶段顺手完成泛化**，不单独开前置计划。理由：

1. 泛化工作量小（主要是把写死的字符串参数化），不需要独立门禁
2. 伏笔施工时直接基于泛化后的骨架写业务代码，避免先写一遍再返工
3. 节奏卡施工时直接复用伏笔已经泛化好的骨架

具体做法：

1. 把 `core/plans/parser.ts` 中业务无关的函数抽到 `core/card-board/parser.ts`
2. 把 `core/plans/identity.ts` 中排序相关函数泛化到 `core/card-board/ordering.ts`
3. 把 `core/plans/store.ts` 中冲突检测、回收站、重命名逻辑泛化到 `core/card-board/store.ts`
4. `types/plans.ts` 中的 PlanCard 泛化为 `CardBoardCard<TStatus>`，PlanStatus 保留为计划的类型别名
5. 计划模块改为引用泛化后的代码，行为不变（现有 699 个测试必须全绿）
6. 伏笔模块基于泛化后的骨架实现自己的业务逻辑
7. 节奏卡模块直接复用泛化后的骨架

### 10.5 前端复用

| 代码 | 复用方式 |
| :--- | :--- |
| `stores/plan.ts` 的保存/防重/草稿/冲突逻辑 | 泛化为 `stores/card-board.ts`，状态定义由调用方注入 |
| `components/plan/PlanBoardPanel.vue` 的看板骨架 | 泛化为 `components/card-board/BoardPanel.vue`，列定义和卡片渲染由调用方注入 |
| `components/plan/PlanDetailPanel.vue` 的详情面板骨架 | 泛化为 `components/card-board/DetailPanel.vue`，字段区由调用方注入 |
| `components/plan/board-reorder.ts` | 泛化为 `components/card-board/board-reorder.ts`，纯函数无业务依赖 |

### 10.6 与伏笔的协同点

节奏卡和伏笔在写作循环里共享同一个"写前规划上下文注入"和"写后提案审阅"的 UI 入口。施工时需要在 Agent Loop 的写前/写后钩子里**同时装配两个模块的工具**，而不是分两次注入。

## 十一、施工阶段划分

### 阶段一：代码泛化 + 伏笔基础

1. 代码泛化：frontmatter 解析、排序、冲突检测、回收站、重命名、目录扫描上提到 `core/card-board/`
2. 计划模块改为引用泛化后的代码（现有测试全绿）
3. 伏笔文件格式与 frontmatter 解析器（基于泛化骨架）
4. ForeshadowingList / Read / ReadForPlanning / Create / Update / Delete 六个基础工具
5. 工具装配规则（主 Agent vs 要素管理员）

### 阶段二：伏笔 UI + 写前/写后集成

1. 看板视图（基于泛化后的 `components/card-board/BoardPanel.vue`）
2. 详情面板（基于泛化后的 `components/card-board/DetailPanel.vue`，扩展伏笔专属字段）
3. 章节侧栏"本章相关伏笔"（实时计算）
4. 要素文件 related_foreshadowing 字段支持
5. 项目设置"伏笔状态模式"配置项（4 状态 / 6 状态）
6. ForeshadowingCheck / Sync 两个高层工具
7. 写前/写后工作流集成到 Agent Loop

### 阶段三：节奏卡基础

1. 节奏卡文件格式与 frontmatter 解析器（基于 `core/card-board/` 骨架）
2. RhythmList / Read / Create / Update / Delete 五个基础工具
3. 偏差自动判定逻辑
4. 枚举值校验（情绪/钩子/爽点的合法值检查）

### 阶段四：节奏卡 UI + 协同集成

1. 看板视图（三列，基于 `components/card-board/BoardPanel.vue`）
2. 详情面板（扩展字段：滑块、下拉、多选、对比展示）
3. 章节侧栏"本章节奏卡"（实时计算）
4. 项目设置"偏差阈值"配置项
5. RhythmCheck / Sync / Curve 三个高层工具
6. 写前/写后工作流集成到 Agent Loop（与伏笔共享注入/审阅入口）
