# 生成链路多协议适配计划（anthropic / gemini / openai-responses）

## 记录时间

2026-09-24

## 背景与定位

设置页自《设置页优化计划》起支持四档协议选择（`openai` / `openai-responses` / `anthropic` / `gemini`），但仅停在配置层：拉模型列表与测试连接多协议可用（`models-client.ts`），**生成链路（Agent Loop / 流式 tool_calls / 要素提取 / 压缩摘要）只实现 openai 兼容协议**（`agent/llm.ts` 固定请求 `/chat/completions`；`AgentLlmInput` 无 protocol 字段，设置页选的协议根本传不到生成层）。用户选 anthropic / gemini 后能拉列表、能测试连接通过，但真正写作走不通。《当前进度》「待开始 → LLM 协议扩展」已预留本计划位置。

参考系为 DeepSeek Harness（dsh）的 llm 分层（`packages/llm/`）：**provider 中立词汇 + 适配器接缝 + 线协议实现**。关键调研结论：

- dsh 的 Agent 循环只认识中立消息/内容块/流事件词汇（`dsh-llm` 包），每个 provider 路由一个适配器把线格式翻译进中立词汇；
- dsh 自己不手写 anthropic/gemini 线协议，而是外包给 `@earendil-works/pi-ai` 库（多 provider 目录 + 线协议实现），`llm-pi-ai` 适配器只做事件翻译；
- **pi-ai 搬不了**：Node-only（传输层用 Node 内置模块 + 五个云 SDK，无 browser 导出条件），dsh 自己的 webworker 运行时都把它整体 stub 掉（`notImplementedFail`）——dsh 的浏览器部署同样没有多协议。NovAI 是纯浏览器应用（直连 fetch + DEV 代理），线协议适配器必须自写 fetch + SSE，好在 openai 一档已有同款模式（`agent/llm.ts`），其余协议照此平行新增；
- pi-ai 的各协议实现源码（纯 JS 可读）作为线格式参考资料对照，不装依赖。

## 已拍板决策

### 用户已拍板（2026-09-24 对话确认）

1. **三协议全做**：anthropic + gemini + openai-responses 一次收尾，不拆两期。
2. **思考流 UI 一并做**：聊天区做折叠式思考过程展示（连 DeepSeek 的 reasoning_content 也从未展示过，本期补上）。
3. **真机验证按 DeepSeek 支持面走**：用户在 `~/note/test-novel` 配置了 DeepSeek key。经查证 DeepSeek 官方支持 openai 兼容与 **Anthropic 兼容端点**（`https://api.deepseek.com/anthropic`），因此 openai（回归）与 anthropic 两档真机可测；gemini 与 openai-responses DeepSeek 不支持，本期以 wire-level mock 测试兜底，待用户有 key 再补真机。

### 方案设计拍板（本计划定稿即生效，审阅时可推翻）

4. **分层照 dsh 裁剪，不引入 pi-ai**：
   - 中立词汇沿用现有 `AgentMessage`（本就 provider 无关），只扩两处：`AgentLlmEvent` 增 `reasoning-delta` 事件；`AgentAssistantResponse` 与 assistant 消息持久化增可选 `reasoning?: string` 字段。dsh 的块级 `StreamChunk` 词汇（块索引 / usage / block-start-end）不搬——NovAI 的 UI 消费不到，保持最小词汇。
   - 适配器接口 `ProtocolAdapter`：负责 URL 解析、鉴权与浏览器头、请求体构造（中立消息 → 线格式）、SSE 解析（线事件 → 中立事件）、工具调用累积、错误分类。openai 适配器整体继承现有实现（含非流式 fallback 与 tool-call 容错诊断）；其余协议首版**不做**非流式 fallback。
   - 协议表分发：`{ openai → OpenAiChatAdapter, anthropic → …, gemini → …, 'openai-responses' → … }`，W1 先注册 openai 一档，其余波次补齐。
5. **finishReason 归一化**：`'stop' | 'tool_calls' | 'length'` 三值（anthropic `end_turn→stop`、`tool_use→tool_calls`、`max_tokens→length`；gemini `STOP→stop`、`MAX_TOKENS→length`、其余归 error；responses `completed→stop`、`function_call→tool_calls`）。wire 原文进 diagnostics。`query.ts` 的判定逻辑不变。
6. **anthropic `max_tokens` 必填**：适配器缺省 8192（压缩摘要路径显式传值不受影响）；openai-responses 映射 `max_output_tokens`；gemini 映射 `generationConfig.maxOutputTokens`。
7. **请求不回传 reasoning（只收不发）**：各适配器构造请求时丢弃历史消息里的 reasoning 内容。anthropic 侧不开 `thinking` 参数（不开就不触发「思考块必须回传」约束）；gemini 侧若线格式在 functionCall part 上带 `thoughtSignature`，适配器将其存进 `AgentToolCall` 可选附加字段随消息持久化，后续请求原样拼回（规避 Gemini 2.5 函数调用思考签名校验），不进 UI 不进工具 schema。
8. **要素提取同链受益**：`llm/client.ts::streamChatCompletion` 薄化为协议层入口（单一入口、随 protocol 分发），删除其 openai 直连实现；`elements/extractor-llm.ts` 自动跟随协议。FIM 输入补全（`completion-client.ts`，DeepSeek 专用）不动。
9. **思考流 UI 形态拍死**（用户可见）：
   - 流式中：assistant 消息顶部「思考中…」折叠块自动展开，实时滚动显示 reasoning 文本；**正文 text-delta 开始输出后自动收起**；
   - 收起态与历史消息：显示「已深度思考（N 字）」，点击可展开/收起，历史默认收起；
   - 思考文本按纯文本 `whitespace-pre-wrap` 渲染（不走 markdown 渲染器），字号小于正文、灰色调；
   - 无 reasoning 的消息（含全部旧会话）完全不渲染该块，旧行为零变化。
10. **协议链路**：`novel.config.json llm.protocol`（已存在）→ services `LlmConfigView`（已有 protocol 字段）→ `ChatTurnInput.config.llm` → query → `AgentLlmInput.protocol`（新增，缺省 `'openai'`）。设置页 UI 零改动（协议选择已存在）。
11. **测试模式**：沿用 `vi.stubGlobal('fetch')` + 手写 SSE fixture 的 wire-level 单测（每适配器三类断言：请求构造、SSE 全事件路径、错误分类），不引 MSW 等新依赖。
12. **CORS/直连**：anthropic 适配器请求带 `anthropic-dangerous-direct-browser-access: true`（对齐 models-client 现状）；全部适配器统一走 `shared.ts` 的 `appendProxyHeader`（DEV 代理已协议无关）。`api.deepseek.com/anthropic` 的浏览器 CORS 行为未知，W2 真机时验证；不通则按降级方案处理。
13. **`llm.ts` 对外签名不变**：`streamAgentCompletion(input, onEvent)` 签名与返回值不动（`query.ts` / `compaction.ts` 零改动），只换内部分发；改动全部收在 core 内部，app 侧除思考流外零感知。

### 2026-09-24 W3 gemini 适配器完工（`64b4a7f`）

**验收结论**：`pnpm test` 406 项全绿（新增 6 项 wire 测试）+ `pnpm typecheck` 干净。按计划本协议无真机 key，全部以 wire mock 兜底，进未验证清单待用户有 Gemini key 后按 W2 同款步骤复核（真机回归手段见 W1 偏差 2）。

**偏差记录**：

1. **finishReason 推导修正**：初版直接映射线上 finishReason，wire 测试抓出 gemini 语义细节——函数调用轮的线上 finishReason 也是 `STOP`（gemini 无独立原因码），直接映射会把工具轮归一成 stop。修正为「有函数调用即 tool_calls」按实际内容推导（Agent 循环以 toolCalls.length 分支，语义不受影响，但 finishReason 诊断与 parse-warning 判定需要正确值）。
2. **安全类中止按错误收场**：计划写「SAFETY 等 → error」，实现为抛错（消息含原始 finishReason）——NovAI 的 finishReason 词汇无 error 值，错误必须走事件/异常通道；安全类中止通常无可用内容，静默截断成「成功」会误导。
3. **thoughtSignature 落点**：按决策 7 存进 `AgentToolCall.thoughtSignature` 可选字段随 assistant 消息持久化，gemini 适配器构造后续请求时原样回传（wire 测试断言回传）；其余适配器与 UI 不感知。
