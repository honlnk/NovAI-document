# 关系图谱设计构想

> 状态：设计构想，已完成第一轮方向讨论；第十节八项事项已在[关系图谱施工计划](关系图谱施工计划.md)定稿并开工施工，正式施工以该计划为准。
>
> 本文记录关系图谱的产品定位、数据边界与交互方向。

## 一、要解决的问题

人物关系目前散落在人物卡片的自然语言描述中，适合阅读，但不适合确定性查询。随着人物、势力、地点、实体和事件增加，作者与智能体都需要回答：

- 两个人物目前是什么关系，双方对彼此的认知是否一致？
- 某个人物隶属于哪个势力，某件物品当前归谁所有？
- 当前场景中的出场人物之间有哪些既有关系？
- 哪些事件推动了某项人物关系的变化？
- 删除或修改一个要素后，哪些关系会受到影响？

关系图谱的目标不是把人物卡中的关系段落换一种写法，而是为项目建立一层可查询、可维护的结构化连接。

## 二、产品定位

关系是**项目级关系账本**，不是与人物、地点等并列的普通要素分类。

- 人物、地点等要素回答“这是谁、这是什么”。
- 关系回答“这些要素之间如何连接”。
- 关系数据存放在 `elements/` 根目录，不放入某个现有要素子目录。
- 关系不进入稳定要素目录披露，也不进入语义索引；智能体通过专用查询工具获得确定性结果。
- 左侧工具栏提供独立图标，点击后打开关系图弹窗，不使用右侧边栏承载。
- 画布与智能体工具操作同一份关系数据，不分别维护两套事实来源。

关系账本负责已经成立或需要明确登记的结构化连接。未来关系规划与作者真相是否进入同一账本，以及相应的正文可见性边界，留待后续设计，不在第一阶段假定已经解决。

## 三、数据范围与模型方向

### 3.1 任意要素都可以成为关系节点

第一版覆盖人物、地点、实体、情节和世界观，时间线中的事件也可以作为关系节点。节点通过要素文档或事件账本中的稳定标识引用，不以名称作为主键，也不在关系中复制完整内容。时间线本身是事件的集合与时间视图，不作为某种旧时间线要素整体进入关系图。

现有要素文档已经具有标识字段；时间线设计同时区分逻辑事件标识与时间标记标识，关系只引用前者。正式设计时需要核验各类标识的全局唯一性、改名稳定性、跨类型唯一性和历史项目兼容策略，不能直接假定现有标识已经满足长期引用要求。

### 3.2 关系同时保留结构与描述

每条关系至少需要表达：

- 关系连接的两个对象（要素或事件）。
- 关系方向。
- 关系类型，用于筛选和确定性查询。
- 自然语言描述，用于保留无法被枚举穷举的细腻语义。

关系类型不宜在第一版建立僵硬的封闭分类体系。人物关系之外，还应允许表达隶属、归属、位于等跨类型连接。人物参与事件、事件位于某地等事实优先登记在时间线事件账本中，关系账本引用事件表达其影响，不重复保存同一份事实。

### 3.3 有方向、非对称、允许多重关系

甲信任乙，不代表乙也信任甲。双向关系可以在界面上组合展示，但双方各自的认知与描述不能被迫合并为同一条文本。

同一对要素之间允许同时存在多种关系。例如两个人物可以同时具有血缘、公开合作与私下敌对关系；画布中的一条视觉连线不必然等于数据中的一条记录。

第一版优先保证当前关系的登记与查询。关系变化历史、不同人物视角、作者真相与故事内生效时间属于后续演进方向，需要与时间线统一设计，不在两个模块中分别创造互不兼容的时间字段。

## 四、存储与修改边界

第一版采用 `elements/` 根目录中的一个 JSON 文件保存全部关系。这是有意选择的简单起点，不是长期存储终局。

- 作者通过关系图维护，不依赖手工编辑 JSON。
- 智能体不获得该文件的直接写入能力，只能通过专用增删改查工具操作。
- 所有写入统一经过关系领域模块，负责节点引用、重复关系、自环和非法数据校验。
- 画布坐标作为展示状态保存，不参与语义检索和创作判断。
- 删除要素时必须处理相关关系，避免留下无法解析的悬空引用。
- 正式施工方案仍需覆盖人工编辑与智能体写入的并发保护、变更记录、错误恢复及外部修改后的刷新。

随着关系数量增长，单一文件的整体读写可能带来冲突范围大、差异难审查等问题。后续可以演进为更细粒度的记录存储，但对作者和智能体保持同一套数据库式操作接口。

通用文件工具必须把关系账本列为受保护数据，禁止模型绕过专用工具直接读写。专用领域服务仍需通过项目文件服务访问本地数据；界面不直接操作文件，底层写入必须携带预期内容版本，不能只靠界面状态防止人工与智能体互相覆盖。

## 五、公共地基与代码复用

关系与时间线都是“独立弹窗中的项目级结构化账本”，两者应复用弹窗、编辑体验、数据安全和稳定引用能力，但不应为了复用而合并领域模型或图形布局。

### 5.1 界面复用边界

| 能力 | 采用方式 | 不采用的方式 |
| :--- | :--- | :--- |
| 模态框外壳 | 复用现有通用模态框的遮罩、居中容器、尺寸、层级和关闭语义 | 不在关系和时间线中分别重写遮罩与弹窗容器 |
| 工作区弹窗骨架 | 建立一层轻量公共骨架，统一标题、操作区、主视图、内部详情、消息和滚动责任 | 不把设置页业务带入创作数据，也不为统一而重构设置页 |
| 保存与编辑反馈 | 复用现有保存状态灯、预览／编辑、正文表面、冲突和守护等公共控件与规则 | 不创造第二套状态灯、错误条和编辑控件 |
| 右侧详情布局 | 只复用其中已经独立的公共展示组件与交互原则 | 不复用整个右侧面板布局，不把关系或时间线迁入右侧边栏 |
| 左侧入口与图标 | 沿用设置、向量索引等动作型入口的接线和受控图标注册 | 不新增分类，不切换中间列表，不绘制独立的临时 SVG 图标 |

工作区弹窗骨架服务“图形主视图＋内部编辑详情”这一类界面，统一桌面与窄屏尺寸、主内容滚动、关闭收口、加载与空状态、错误和数据损坏提示。关系详情与后续事件详情都在这套骨架中维护。

### 5.2 保存与账本基础

近期正文与卡片改造已经建立可复用的保存事件序、内容版本校验、非阻塞冲突和守护能力。新功能应通过领域适配器复用这些成果，不另写一套自动保存或冲突状态机。

| 公共能力 | 统一职责 | 领域保留职责 |
| :--- | :--- | :--- |
| 账本加载与保存 | 格式版本、读取、校验、预期内容版本、原子写入、损坏与恢复提示 | 关系数据与时间标记各自的结构和合法性 |
| 保存会话 | 同键串行、写盘期间继续输入、关闭收口、普通失败、冲突代次与恢复 | 草稿形状、字段比较、写入操作和业务出口 |
| 变更通知 | 作者界面与智能体工具写入后刷新同一数据源 | 关系画布与时间轴各自的刷新和布局 |
| 写入边界 | 通用文件工具不得改写账本，专用工具与人工操作复用领域服务 | 关系与事件各自的权限和参数校验 |

这些公共机制只负责“安全地读写、保存和通知”，不包含关系路径、故事时间、区间配对或轨道计算。正式施工前需要核对现有保存会话与 JSON 账本的适配缺口，不能直接假定整套卡片保存流程无需调整即可套用。

### 5.3 稳定引用基础

关系第一阶段需要建立项目内的稳定引用索引，提供“标识 → 类型、名称、摘要、位置”的确定性解析。现有要素目录主要按名称服务渐进式披露，不能直接充当稳定标识引用服务。

- 统一处理重复、缺失和无法解析的标识，不把同名要素静默合并。
- 改名不改变既有关系引用；删除要素时明确呈现受影响关系并执行确定的处置。
- 引用解析面向后续时间线复用，未来可以加入事件标识，不建立另一套按名称关联的机制。
- 界面中的对象选择、搜索和引用展示建立在同一解析结果上。

## 六、智能体工具

基础维护能力包括列出、读取、新建、修改和删除关系。工具以稳定标识定位关系与节点，不向模型暴露可直接改写底层文件的通道。

除机械增删改查外，还需要面向创作意图的查询：

| 查询意图 | 返回内容 |
| :--- | :--- |
| 查询某对象的关系 | 与该要素或事件直接相连的关系、方向和对方摘要 |
| 查询两个对象之间的关系 | 两个要素或事件之间所有方向、所有类型的关系 |
| 查询当前场景的人物关系 | 仅返回当前相关人物之间的连接，避免整张图进入上下文 |
| 检查关系数据异常 | 重复、无效引用及可明确判定的归属冲突 |

关系路径、多度推演和复杂图算法不属于第一版必须实现的能力。第一版首先保证写到两个人物见面时，智能体能够准确取得他们已经登记的关系。

## 七、图谱交互

关系图采用可缩放、可平移的节点连线画布。`duet` 项目中的 Vue Flow 实现可作为交互与技术选型参考，但其静态角色关系模型和存储方式不直接照搬。

第一阶段需要支持：

- 按要素类型区分节点，并展示名称与必要摘要。
- 拖动布局、缩放、平移和坐标保存。
- 搜索节点、聚焦某要素的直接关系、按类型筛选。
- 新建、编辑和删除关系。
- 清晰展示有向关系及同一对节点之间的多重关系。
- 智能体修改后同步刷新画布。
- 删除要素时处理关联关系。

大型长篇项目不应默认把全部要素同时铺在同一张图上。默认展示有关系的核心节点，并提供搜索添加与筛选，避免节点规模增长后失去可读性。

## 八、实施先后与分阶段交付

先完成关系图谱，再实施时间线。关系可以先围绕现有要素建立完整能力，不需要等待事件账本；时间线完成后，再为关系增加事件节点及事件导致关系变化的能力。

| 阶段 | 交付内容 | 为后续保留的边界 |
| :--- | :--- | :--- |
| 公共地基与稳定引用 | 通用工作区弹窗骨架、账本读写与版本保护、AI 写入边界、稳定标识解析 | 不包含时间、区间或轨道语义，可供时间线直接复用 |
| 关系领域服务与工具 | 有向、多重关系的增删改查、基础查询和变更通知 | 事件节点暂不作为第一阶段验收前提 |
| 关系弹窗与画布 | 独立图标、关系图弹窗、搜索筛选、编辑详情、坐标保存及保存冲突体验 | 公共弹窗与详情反馈不包含关系专属判断 |
| 集成与验收 | 旧项目、重复或失效标识、要素删除、并发、窄屏和真实长篇规模 | 记录时间线可以直接复用的能力与仍需适配的缺口 |
| 时间线完成后的关系扩展 | 事件节点、事件引用与关系变化依据 | 不在第一阶段提前实现关系历史或时间推演 |

公共组件需要附契约测试，覆盖弹窗尺寸与滚动、关闭收口、保存状态、错误与冲突位置、项目切换隔离；稳定引用需要覆盖重复、缺失、改名与删除。新组件不得出现“如果是关系就怎样、如果是时间线就怎样”的领域分支。

## 九、与现有模块的边界

| 模块 | 职责 |
| :--- | :--- |
| 要素 | 描述人物、地点、实体、情节和世界观本身 |
| 关系 | 记录要素与事件之间已经登记的结构化连接 |
| 时间线 | 以事件为基本单位，记录故事内时间与顺序，为关系变化提供时间依据 |
| 伏笔 | 记录作者欠读者什么，以及何时需要回收 |
| 节奏卡 | 记录作者希望读者在每一章如何感受 |

关系和时间线共同构成结构化项目数据，但不吞并要素正文中的细节、评价、情感与叙事表达。

## 十、后续施工前必须定稿的事项

- 现有要素标识的全局唯一性与旧项目兼容策略。
- JSON 文件名称、关系标识、字段契约及非法数据处理。
- 有向关系与多重关系在画布上的具体呈现。
- 工具清单、读写权限、写入确认与变更记录。
- 要素删除、改名、类型变化时的关系联动。
- 人工画布编辑与智能体写入的并发保护。
- 关系历史、视角和真相可见性的分阶段边界。
- 真实长篇项目下的节点规模、筛选和性能验收。
