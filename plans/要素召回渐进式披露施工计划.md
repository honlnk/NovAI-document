## 文档性质

本文档是**施工计划**，是「要素召回机制重构」（决策 `docs/decisions/0007-要素召回机制重构-从RAG单通道到渐进式披露.md`）的落地执行依据。施工按 W1–W4 四个波次推进，每波带门禁；验收结论与偏差记录随施工追加在文末施工日志。

## 目标

把 characters / locations / entities / worldbuilding 四类要素的召回从「LLM 自主调 RagSearch」改为「渐进式披露」：

- **L1 目录**：所有要素的 `type + name + summary` 清单，作为 user 角色 reminder 紧跟 system prompt 注入，digest 驱动原位替换
- **L2 加载**：新增 `LoadElements` 工具，模型按需批量加载要素完整正文
- **RAG 收窄**：RagSearch 只检索 plots / timeline 两类，索引范围同步收窄

参考系：dsh `packages/skill/`（见决策 0007「参考系」一节）。

## 已拍板决策（施工不可更改）

> 完整论据见决策 0007。这里只列施工必须遵守的硬约束。

1. **目录只放稳定信息**：`type + name + summary`，**不含** `lastUpdatedChapter`、内容 hash、mtime 等任何版本标记。
2. **不做版本追踪、不做变更推送**：要素正文变了，不在历史里追加新 reminder，也不修改旧 tool result。模型靠历史消息追踪状态变化。
3. **目录消息结构**：user 角色 + `<system-reminder>` 包裹 + 紧跟 system（index 1）+ digest 驱动原位替换。完全复用 `syncNovaiReminder` 的既有模式。
4. **LoadElements 支持批量**：`{ names: string[] } → ElementContent[]`。
5. **RAG 收窄范围**：`elements/plots/**/*.md` + `elements/timeline/**/*.md`，其余四类从索引中移除。
6. **不做 @要素名 手势、不做 Router skill、不做 element-manager 工作流改动**。
7. **element-manager 提示词补强**：写 summary 时明确「只写稳定身份定义，不写随章节变化的状态」——这是目录 digest 稳定的前提。

## 范围外（本计划明确不做）

- chapters/*.txt 召回（现状如此，本计划不改）
- `@要素名` 输入框手势
- 变更推送机制（方案三）
- 版本号/hash 进目录（方案二）
- element-manager 子智能体内部流程改造
- RAG 算法本身的调优（rerank、chunk 切分策略等）

### W1 - core 目录扫描与 catalog 数据层（门禁全绿）

实现偏差：

1. `scanElementCatalog` 签名从计划的 `(tree: TreeNode[])` 同步纯函数改为 `(project: ProjectSnapshot) => Promise<ElementCatalogEntry[]>`——读文件内容（frontmatter 解析）需要项目 fs，tree 只给路径不含内容。
2. `ElementCatalogEntry` 比计划多一个 `sourcePath` 字段——W3 的 LoadElements 需要它定位文件（name 与文件名解耦）。sourcePath 不参与 digest：文件挪子目录不触发目录重发。
3. digest 用仓库既有 `hashContent`（FNV-1a）而非 dsh 的 sha256——与 `syncNovaiReminder` 系一致。digest 函数内部先按 `sortCatalogEntries` 归一排序再哈希：entries 数组重排不触发重发，「重排不变」成为函数自身保证而非调用方约定（开发中被测试抓到一次，收进函数修复）。
4. 计划留白的「summary 缺失兜底：用 name 或跳过该条」拍板为**用 name 兜底**——保持要素在目录可见（可被 LoadElements 召回），确定性召回优先。
5. 计划未提的 name 缺失：用文件名（去 `.md`）兜底，防单文件丢整个条目。

单测 8 条：四类扫描跳过 plots/timeline、排序稳定、name/summary 双兜底、单文件解析失败跳过、空目录、digest 敏感性/不敏感性/重排不变。

### W2 - 目录注入：reminder 模式复用（自动化门禁 + 真机验证均过）

实现偏差：

1. 接线点：计划写「在 `agent/query.ts` 的合适位置」；实际在 `chat/session.ts` 的 `runDriverTurn`——`syncNovaiReminder` 的现状调用点就在这里（计划「关键现状定位」表对它的定位已过时）。
2. 新增角色开关 `AgentRoleProfile.injectElementCatalog`（必填）：计划没有角色维度；10-22 落地的角色注册表机制把注入开关声明化，跟随现状——主角色 true，element-manager false（它用 FindFiles/ReadFile 直接管理要素，目录对它是噪音）。`roles.test.ts` 工具面断言同步。
3. `syncElementCatalogReminder` 签名带 `session`：digest 写入 `ChatSessionState.elementCatalogDigest` 持久化（同 NovAI reminder 做法），跨请求判定「已有 reminder 是否最新」。
4. `buildElementCatalogReminder` 加 `isUpdate` 选项：计划只定稿首注文案；更新版头部改「以下是最新的要素清单……取代此前任何版本」。
5. 空目录（entries 为空）不注入 reminder；四类要素全删空后旧 reminder 会残留——与 `syncNovaiReminder` 现状一致（跟随不修），残留场景由 LoadElements 的 notFound 结果自然纠正。

真机验证偏差：计划的「Network 面板看 messages[1]」改为读 `.novel/logs/agent.log.jsonl` 的 `agent_messages_debug` 事件（IAB 无 Network 面板，日志含每条消息 600 字预览，证据更硬）。观测 messages[1] 为要素清单 reminder（`<available_elements>` 含 9 条目）。
