# 创作计划板施工计划

## 文档状态

- 记录日期：2026-11-03。
- 当前状态：**已形成独立计划，尚未开工**。
- 本文档是创作计划板的独立设计与施工依据。动工前须获得用户批准；开工后将状态改为「进行中」，按阶段记录验收与偏差，完成后改为「已完成」。

## 背景与决策

早期 Agent Loop 重构曾把多步任务工具列为可选二期能力，用于帮助 AI 连续执行多项任务。该工具不符合小说创作的实际控制方式：故事推进由作者掌握，不需要 AI 为长期创作建立执行队列，也不需要以批量完成章节为目标。

**放弃多步任务工具，不保留为待启动功能。** 长期创作意图由项目级创作计划板承接。它是用户与 AI 共同维护的创作资产，不是 Coding Agent 的短期任务清单，也不是原工具换个界面继续实施。

## 产品定位

创作计划板是一个自由记录、长期维护的项目级面板：

- 记录准备安排的剧情、伏笔、灵感、待补设定和修改意图；
- 支持用户直接创建、编辑、整理和删除卡片；
- 支持 AI 在对话中查询和维护同一批卡片；
- 用看板状态帮助整理，不要求卡片在短期内完成；
- 不根据计划自动创作或批量推进故事。

大纲、要素和计划板在基础语义上各有分工：大纲描述故事的整体路径，要素保存故事设定与事实，计划板保存创作意图和备忘。**这些分工用于引导，不构成内容限制。** 用户可以在计划正文中写任何内容，不需要先分类，也不因内容适合其他模块而被拒绝。

## 设计原则

1. **正文自由**：只要求填写正文，不规定内容类型或写作模板。
2. **轻量结构**：只提供状态和排序，不引入项目管理字段负担。
3. **作者掌控**：计划不会自动成为剧情指令，AI 不因看板存在未完成项而主动执行。
4. **文件为事实来源**：卡片保存在本地项目文件中，面板与 AI 使用同一份数据。
5. **长期有效**：计划可跨会话、跨章节保留，可长期停留、反复修改或放弃。
6. **保持自由度**：不做内容合规审查，不强制关联章节、人物或要素。

## 数据与文件设计

### 存储方式

- 使用项目根目录下的 `plans/` 保存计划卡片。
- **一张卡片对应一个 Markdown 文件**，文件保存在该目录的直接子级。
- 正文是自由 Markdown 内容，元数据放在文件前置元数据中。
- 不引入数据库、索引文件或另一份看板状态副本。
- 计划目录是用户可见的创作资产，不属于应用内部目录。

### 卡片元数据

| 字段 | 含义 |
| :-- | :-- |
| `id` | 稳定标识，创建后不因正文或文件名改变 |
| `status` | `inbox`、`planned`、`in-progress`、`done`、`on-hold` |
| `order` | 同列内的排列顺序 |
| `createdAt` | 创建时间 |
| `updatedAt` | 最近一次内容或状态更新时间 |

展示标题取正文首个非空行，去除该行行首的 Markdown 标题标记；没有单独标题字段。正文可以编辑任意部分，标题变化不影响稳定标识。

文件名采用「计划-<创建时序号>-<稳定短标识>.md」，创建时确定，后续修改正文不重命名。创建时序号用于方便外部浏览，不代表剧情章节或优先级；删除卡片后允许序号不连续。

### 排序与外部编辑

1. 同列按元数据中的顺序值排列，顺序值相同再按创建时间和稳定标识排序，保证结果确定。
2. 拖放到空白位置时优先只修改目标卡片的列和顺序值；需要收紧间隔时，允许重排同列卡片，一次操作只重写实际受影响文件，不承诺始终只写一个文件。
3. 顺序值使用可插入间隔的数值，不要求每次拖拽都重写整列。
4. 外部编辑器修改正文或元数据后，重新扫描项目即可反映到看板；只读扫描不自动改写文件。
5. 缺少元数据的有效 Markdown 文件仍可读取和展示，默认进入收集箱。通过明确的修复操作补齐标识和必要字段，保留正文；AI 修复遵守现有写权限，手动修复由用户主动触发。
6. 非法状态在展示时回退为收集箱；非法时间不影响正文读取。修复元数据前保留原正文，不因格式问题删除卡片。
7. 同目录中的重复稳定标识必须在读取时报告并允许修复，不能静默将两张卡合并。

## 看板与交互

### 入口和布局

1. 主工作区一级导航在「提示词」之后、「设置」之前增加「计划」。
2. 进入计划时，看板使用中间主内容区，替换对话面板；现有分类导航保留。
3. 不把四列看板塞进窄侧栏，也不依赖打开右侧文件面板才能使用。
4. 分类面板显示计划入口、当前卡片数量和「新建计划」按钮；不再重复展示一块完整看板。
5. 从计划切回对话或其他内容分类时，恢复原对话及文件面板状态。
6. 桌面端优先支持完整看板；窄屏允许看板区域横向滚动，不新做整套移动端导航改造。

### 四列与已搁置状态

| 栏目 | 含义 |
| :-- | :-- |
| 收集箱 | 新产生的灵感、伏笔和备忘，尚未决定何时处理 |
| 计划中 | 已确定以后要做，当前没有着手 |
| 进行中 | 正在本次创作中处理 |
| 已完成 | 已落实，作为创作记录保留 |

「已搁置」不作为常驻第五列。看板顶部提供状态筛选，默认显示四个常驻栏目，可单独查看已搁置卡片。

状态只用于整理：卡片可以长期停留，可以重新打开，也可从任意状态移动到其他状态。不提供催办、逾期、工时、依赖或自动执行。

### 卡片与详情

1. 卡片默认展示正文摘要、更新时间和状态；摘要超出卡片高度时截断，完整内容在详情中查看。
2. 点击卡片打开右侧详情编辑区；不强制使用弹窗。
3. 详情只提供正文编辑框、状态控件和删除操作，不设置必填分类或关联字段。
4. 新建卡片默认进入收集箱；创建后打开详情供继续输入。
5. 拖拽卡片可改变栏目和同列顺序，同时提供状态控件作为不依赖拖拽的操作方式。
6. 删除卡片进入项目回收站，不直接永久删除；手动删除提供明确的确认提示，AI 删除沿用现有确认规则，避免误删。
7. 空状态直接提供新建入口，不展示示例计划或替用户预填创作意图。

### 保存与冲突

1. 新建、删除、状态和拖拽操作立即保存。
2. 正文编辑使用「保存」按钮；有未保存修改时显示明确标记，离开卡片前提示保存或放弃。
3. 保存期间禁用重复提交，失败时保留草稿并显示错误。
4. AI 或外部编辑器修改已打开卡片时，未在编辑中的视图重新读取最新内容。
5. 用户正在编辑时不用远端内容覆盖草稿；界面提示文件已有新修改，由用户选择重新读取或保留当前草稿。保存前发现文件已变化时阻止覆盖，并要求先处理冲突。
6. 多卡片操作中途失败时，保留已经成功落盘的结果并报告失败项，不假装整块看板已回滚。

## AI 工具

只向主智能体提供计划维护工具。要素管理员不拥有这些工具，避免偏离其要素维护职责。

| 工具 | 用途 | 输入与输出边界 |
| :-- | :-- | :-- |
| `ListPlans` | 查询计划摘要 | 可按状态筛选；返回稳定标识、标题、状态、顺序、更新时间和正文摘要，不返回全部正文 |
| `ReadPlan` | 读取一张计划 | 按稳定标识读取完整正文与元数据 |
| `CreatePlan` | 新建一张计划 | 必须提供正文，可指定状态；默认收集箱，默认排在目标列末尾；返回新卡片标识 |
| `UpdatePlan` | 修改正文或整理状态 | 按稳定标识定位；正文、状态、目标列位置分别可选；一次只更新提供的目标字段 |
| `DeletePlan` | 删除一张计划 | 按稳定标识定位，移入项目回收站 |

具体约束：

1. 更新正文采用完整正文替换；只改状态或顺序时不传正文，原正文保持不变。
2. 正文更新前必须通过读取计划获得当前版本；保存时校验文件未变化，防止覆盖用户或外部编辑器的修改。
3. 工具不接受项目绝对路径，不能将卡片写到计划目录之外。
4. 删除只能由用户明确要求触发，不因剧情变化或计划失效而自动清理。
5. 工具结果包含必要的卡片标识、状态和正文摘要，供后续调用和界面反馈使用。
6. 计划变更沿用现有工具调用轨迹、文件变更账本、差异展示和看板刷新机制。

### 使用边界

- 用户明确要求记录、修改、移动或删除计划时，使用相应工具。
- 对话中形成明确的后续创作意图时，可以创建计划；不把每段对话自动转成卡片。
- 写作、续写、修改或伏笔安排涉及已有计划时，先查询摘要，再读取相关卡片。
- 已有明确依据证明某项计划落实时，可以更新状态；不把作者的设想自动改写成确定剧情。
- 不因看板存在未完成项而主动执行，不为清空看板推进故事，不批量生成章节。
- 普通文件工具仍可读取和编辑计划文件；专用工具负责更安全的标识定位、元数据和排序操作，两者访问同一份文件。

## 上下文与检索

1. 不把全部计划正文自动注入每次模型请求。
2. 计划通过查询摘要和按需读取进入模型视图。
3. 计划目录不进入情节、时间线的语义向量索引。
4. 不为计划新增 Embedding、Rerank 或自动召回配置。
5. 项目结构说明增加计划目录的基本事实；工具说明负责介绍查询与维护能力，不添加自动推进或强制完成计划的原则话术。

## 权限与既有机制

1. 计划文件归入**素材类内容**，沿用现有五档写权限，不新增第六档。
2. 「仅审阅」和「章节内容」档下，AI 修改计划需要逐次确认；「素材内容」「章节与素材」「完全访问」档允许按计划文件的现有规则处理。
3. AI 新建、改变栏目或顺序、删除计划均按现有结构操作规则确认；只有不改变文件位置和存在性的正文、状态修改按素材内容规则处理。任何计划操作都不因使用专用工具而绕过确认。
4. 用户在计划面板中的直接编辑等价于其他内容面板的手动保存，不经过 Agent 写入确认；AI 工具写入仍进入会话变更记录。
5. 文件保护、读后写入、变更检测、回收站和文件树刷新沿用现有基础设施；缺失能力在共享服务中补齐，不建立平行实现。

## 服务与实现边界

1. 核心包增加与界面无关的计划领域：卡片解析、序列化、目录扫描、排序、读写和冲突检测。
2. 应用通过新增计划服务获取看板视图和执行操作，不直接读写项目目录，不导入核心内部实现。
3. 计划服务同时支撑手动面板和 AI 工具，确保元数据、排序和冲突规则只有一个事实来源。
4. 看板视图按项目标识和当前项目快照加载；切换项目时清理上一个项目的界面状态。
5. 看板列折叠、当前筛选和选中卡片属于界面状态，不写入计划文件；本期不做跨设备偏好同步。
6. 使用现有前端能力实现拖拽与编辑，不为此引入大型项目管理框架。
7. 项目视图、一级导航和服务出口属于共享区域；正式动工须取得用户对这些文件的修改批准。

具体模块和组件名称由施工方按现有代码结构确定，但不得改变上述产品交互、存储格式和权限边界。

## 分阶段施工与门禁

### 第一阶段：计划文件与领域能力

**任务**

1. 增加计划目录及卡片文件格式，覆盖创建、打开、修复和恢复项目。
2. 实现解析、序列化、稳定标识、状态、排序与温和补齐。
3. 实现计划查询、读取、新建、更新、删除、冲突检测和项目扫描。
4. 建立服务层看板视图和操作契约。

**门禁**

- 全量测试通过，全项目类型检查通过。
- 测试覆盖五种状态、空正文拒绝、标题派生、同列排序、跨列移动、删除回收站和非法输入。
- 测试覆盖旧项目无计划目录、外部新增文件、缺字段补齐、重复标识和外部修改冲突。
- 测试覆盖正文更新与状态更新互不误覆盖。
- 本计划记录验收和偏差；获准提交后补充实际提交哈希。

### 第二阶段：看板与手动编辑

**任务**

1. 增加一级导航、计划主视图、四列看板和已搁置筛选。
2. 实现新建、正文编辑、状态切换、拖拽排序、删除和刷新。
3. 实现保存状态、未保存提示、外部变化提醒和冲突处理。
4. 接入项目切换、文件变更与错误反馈。

**门禁**

- 全量测试、全项目类型检查与应用构建通过。
- 测试覆盖服务状态归并、拖拽后的排序保存、失败保留草稿和事件刷新顺序。
- 使用常驻测试项目 `~/note/test-novel`，通过现有开发服务 `http://localhost:5173` 真机验收，不另起开发服务器。
- 如内置浏览器无法授予目录权限，采用《真机测试 OPFS 仿真目录方案》；不得在仓库中复制真实密钥。
- 真机验证卡片创建、编辑、拖动、删除、重新打开项目、外部修改和窄屏使用。
- 本计划记录验收和偏差；获准提交后补充实际提交哈希。

### 第三阶段：AI 工具与上下文接入

**任务**

1. 向主智能体注册查询、读取、新建、更新和删除工具。
2. 接入权限、确认、文件变更账本与看板实时刷新。
3. 补充项目结构说明和工具使用规则。
4. 验证普通文件工具与专用工具操作同一文件时的一致性。

**门禁**

- 全量测试、全项目类型检查与应用构建通过。
- 覆盖各权限档位的计划修改、确认接受与拒绝、删除边界和要素管理员工具白名单。
- 在真实模型会话中验证：明确要求记录计划、查询并读取计划、修改状态、按用户要求删除。
- 验证没有计划时能够正常创作；存在未完成计划时不会自动续写或批量执行。
- 验证计划不进入语义索引，AI 操作后看板与文件变更展示同步。
- 本计划记录验收、偏差与未验证项；获准提交后补充实际提交哈希。

### 第四阶段：回归与结项

**任务**

1. 回归章节、大纲、要素和提示词的打开、编辑与文件变更，确保计划入口不破坏原有工作区。
2. 更新技术架构总览、UI 协作接口契约和当前进度。
3. 完成本计划状态、施工日志和未验证项收口。
4. 按计划领域与文件存储、看板界面、AI 工具三个逻辑单元分别提交。文档随结项统一提交，先提交文档子模块再更新父仓库指针；提交前取得用户批准，不执行推送。

**验收标准**

- 用户无需理解分类规则即可自由记录一条内容，并在看板中长期维护。
- 看板与项目文件内容一致，旧项目能温和获得计划能力。
- 手动编辑与 AI 工具不会互相静默覆盖，删除进入回收站。
- AI 能按用户意图维护计划，但不把计划当成自动执行队列。
- 所有自动化门禁通过，真机验证范围和未验证项均有明确记录。

## 数据兼容与旧机制去向

1. 新建项目创建空的计划目录，不生成示例卡片。
2. 旧项目打开、修复或恢复时温和补齐空目录；既有章节、要素、提示词和配置不迁移。
3. 已存在的计划 Markdown 文件保留正文，缺失元数据时先按默认状态展示，再由用户或经授权的 AI 明确修复；不把旧项目中的其他文档自动转换成计划。
4. 计划板是新增的创作资产，不替换大纲、要素、章节或会话。
5. 多步任务工具不再实施，也不需要删除既有代码或迁移数据；它从未进入 NovAI 实现。
6. 本期不替换通用文件读写能力；专用计划工具与通用文件工具共享同一项目文件事实来源。

## 明确不做

- 多步任务工具、短期执行清单、任务依赖、子任务和自动执行。
- 一键执行全部计划、自动批量创作或自动完成计划。
- 强制标题、强制分类、内容审查和固定写作模板。
- 章节、人物、要素的强制关联及复杂关系图。
- 截止日期、催办、工时、优先级和复杂项目管理工作流。
- 自定义栏目、多层级看板与跨项目共享计划。
- 计划向量索引、自动语义召回和计划全文常驻注入。
- 新权限档位、独立数据库或看板专用版本管理系统。

## 风险与控制

- **自由内容变得难找**：第一版用状态、摘要和排序缓解，不用强制字段破坏自由度；真实使用证明需要搜索或筛选时再另行立项。
- **外部编辑导致元数据不一致**：以文件为事实来源，温和补齐并检测重复标识，不以界面缓存覆盖文件。
- **拖拽重排产生大量变更**：采用间隔排序，仅重写受影响卡片，变更记录以实际写入为准。
- **AI 把计划当作必须执行的剧情**：通过工具说明与真实会话验收约束，不新增自动执行机制。
- **权限口径被绕过**：所有 AI 写入复用同一权限与确认链，计划面板的手动保存与 Agent 写入保持清晰区分。
