# 文件树与打开文件实时刷新计划

## 背景与问题

AI 运行期间，侧边文件列表与内容面板都不会实时反映文件改动，用户必须等整轮任务结束（文件树）或手动重新点击（打开的文件）才能看到新内容。

调查结论（2026-09-22，代码级确认）：

1. **文件树不实时刷新**：前端管线早已为实时设计——`ProjectView.vue` watch `chatStore.changedFiles.length` 触发 `refreshTree()`，`chat.ts` 的 `applyFileChangeRecord` 按实时合并实现；但 core 层 `agent-service.ts` 把所有 `file-changed` 事件攒到 `driver-finish` 收尾时才批量广播（`run-finish` 紧随其后），运行中途一条都不发。事件总线上数据实时可用（`session.ts` 的 changeLedger 在每次写工具成功后立即追加），只是没人中途广播。
2. **打开的文件不自动重读**：`projectStore.activeFile` 只有 `openFile`（用户点击）和 `saveFile`（用户手动保存）两个写入时机，`refreshTree()` 只更新树结构不重读内容，`file-changed` 事件也无人翻译成重读。即使修好问题 1，此问题依旧存在——两个缺口相互独立。

## 方案

### Step 1（core）：file-changed 改为运行中实时广播

`wakeSessionDriver` 的 `onEvent` 里，`{ type: 'message' }` 事件到达时按**账本高水位**（`ledgerBaseline` 起算的已广播计数）把 `event.session.changeLedger` 新增记录逐条转 `toFileChangeRecordView` 后广播 `file-changed`。依据：`session.ts` 中账本追加紧排在 tool-result `pushMessage` 之前，故 message 事件到达时账本必已含新记录。

删除 `driver-finish` 收尾时的 `file-changed` 批量广播循环（被实时广播替代）；`RunAgentTurnResult.turnChanges` 数据结构保留不动。

### Step 2（app）：内容面板按路径自动重读

- `chat.ts` 新增 `lastFileChange` ref（最近一条实时到达的 `FileChangeRecordView`），`file-changed` 分支写入，`selectSession` / `createNewSession` 时重置为 null。
- `utils/file-tree.ts` 新增纯函数 `resolveActiveFileReloadTarget(activeFilePath, change)`：updated/created 命中 path 返回该 path；renamed 命中 fromPath 或 toPath 返回 toPath；**deleted 返回 null 不重读**（重读必失败弹错误 toast，树刷新后列表里该项已消失，保留面板内容等用户自行切走）。
- `ProjectView.vue` watch `chatStore.lastFileChange`，命中时 `void projectStore.openFile(target)`。

### 已拍死的取舍（用户已确认）

**编辑模式遇 AI 同文件改动：不弹窗、不覆盖草稿。** `editDraft` 是 ContentPanel 本地副本，`activeFile` 替换不影响草稿内容；仅 `isDirty` 的比较基准随新磁盘内容变化（「未保存」标记语义仍正确：草稿 ≠ 磁盘最新）。用户保存时为 last-writer-wins。理由：编辑功能当前是占位功能，用户明确表态「按我的计划完善即可」；完整冲突提示 UI 留待编辑功能正式设计。

## 迁移条款

无持久化数据 / 配置 / 文件格式变化。事件时序变化（收尾批量 → 运行中逐条）对消费方的影响：`applyFileChangeRecord` 按路径去重 last-wins，逐条到达与批量到达结果一致；`run-finish` 仍整体覆盖权威清单，语义不变。附带收益：run-error / 被停止的轮次，此前已产生的改动现在也有事件广播（旧行为是报错即一条不广播，树停留旧状态）。

## 新旧机制替代表

| 旧机制 | 去向 |
| :--- | :--- |
| `driver-finish` 收尾批量广播 `file-changed` 循环 | **删除**，由 `onEvent` 高水位实时广播替代 |
| `RunAgentTurnResult.turnChanges` | 保留（run-finish 结果数据结构不变） |
| `changedFiles.length` watch → `refreshTree()` | 保留（树刷新入口不变，事件实时化后自然逐文件触发） |

## 明确不做清单

- 编辑模式 AI 改动冲突提示 UI（占位功能，待正式设计）
- 文件树局部增量更新（维持整树 `refreshFiles` 重扫）
- 会话切换时强制刷新树 / 重读内容
- ContentPanel 重渲染的滚动位置保持优化
- `file-changed` 事件节流 / 去抖（写工具频率低，逐条直达）

## 验收点

1. 【自动化】core：同一轮改 3 个文件，`file-changed` 事件在 `run-finish` **之前**逐条到达，且每条紧跟对应 tool-result 的 message 事件之后（事件序断言）。
2. 【自动化】core：run-error 中途失败，此前已落账的改动仍有 `file-changed` 广播。
3. 【自动化】app：`lastFileChange` 随每条 `file-changed` 更新；`resolveActiveFileReloadTarget` 四类改动的命中 / 不命中矩阵。
4. 【手动降级】真机跑一轮含新建文件的写作任务，观察树与内容面板是否运行中刷新。无真实 LLM 环境时以测试 1-3 + 代码走查兜底，列入未验证清单。
