# 角色注册机制施工计划

## 记录时间

2026-10-22 定稿。

## 文档性质

本文档是**施工计划**，落地「智能体即角色」的架构升级：把项目里的智能体从「一个主智能体 + 若干一次性子智能体」的星型结构，重构为「若干角色共存、统一注册、共用一套运行时核心」的角色机制。它是《要素管理入口重构施工计划》W4（直聊会话）的**前置地基**——入口重构须等本机制落地后再跑。

## 背景

### 现状：星型结构，子智能体是「一次性工具」

当前架构里只有主智能体是「真角色」，要素管理员是挂在主智能体身上的一个**一次性委派工具**：

- 主智能体握着全量工具 + `DelegateToElementManager` 委派工具，是默认对话对象。
- 要素管理员**不能被直接对话**，只能被主智能体以 `runElementManager` 一次性唤起：每次全新起一个 ModelView，跑完把最后一段汇报**文本**返回给主智能体，过程上下文当场销毁。**它不是会话**——无 sessionId、不落盘、不在会话列表。
- 委派过程中要素管理员的写操作，通过闭包穿透复用**主会话的确认链**弹确认卡（`createDelegateToElementManagerTool` 注入 `confirm`）。

这套结构的隐形天花板：子智能体被打死成 one-shot，无法追问汇报、无法持续管理、每加一个新角色都要重造运行壳。

### 目标：智能体即角色，统一注册

项目里住若干**角色**。角色 = 一个统一注册的智能体单元，声明自己的：身份、system prompt 装配、工具白名单、路径闸、专属约束文档、是否可被委派、独立配置块。所有角色**共用同一套运行时核心**（现有的 `runChatDriver`/`query` 循环），差异全部收进各角色的注册声明与少量特化代码。

- **主智能体**：权限最高的角色，默认对话对象，握全量工具，可委派其他角色。
- **要素管理员**：特化角色。它不是「主智能体减权限」，而是**拥有主智能体所没有的能力**——核心是 ELEMENT.md 这份 LLM WIKI Schema 约束。整理要素这事主智能体也能干，但要素管理员干得更好（被 Schema 约束、专精于此）。它**只能被主智能体委派**（委派是分工，主智能体把自己不如专才做好的事委托出去），**也能被用户直接对话**。

### 委派即会话（核心转折）

委派不再是一种特殊运行机制，而是「主智能体替用户向某角色发起一个会话」这个通用能力的用法。于是：

- **委派 = 创建一个真会话**：主智能体一派，新建要素管理员会话（有 sessionId、落盘、进会话列表、按角色分组），任务跑完会话**留存**，可打开看全过程、可进去继续追问（多轮）。
- **直聊 = 用户自己和该角色的会话**，同样落盘、可续。
- 主智能体委派时拿到的仍是**汇报摘要**（不污染主上下文），但底下跑的是一个持久化的真会话。

这直接化解了原 W4 纠结的「记忆边界」难题：记忆挂在**会话**上而非调用方式上。委派会话与直聊会话是两个独立会话，各自有上下文——「你刚才那次是主智能体派的工作单，在另一个会话里；咱俩这个对话里它没经手那件事」成为可解释的产品事实，而非失忆 bug。

## 已拍板决策（施工不可更改）

1. **统一核心，差异在特化**：所有智能体走同一套运行时核心（`runChatDriver`/`query`）；不同角色只有各自的特殊功能代码（约束文档装配、工具白名单、路径闸）。**统一的是注册机制与运行时骨架，差异化的是角色的能力声明（profile）**。

2. **不可让渡的边界**：统一注册 ≠ 所有角色用同一份配置。要素管理员之所以是要素管理员，靠三样不可让渡的东西——受限工具白名单（不碰 chapters/prompts）、elements/ 路径闸（运行层强制）、自己的 system prompt / Notes 铁律。这些收进角色声明，运行层强制，不依赖模型自觉。

3. **角色注册表**：core 引入角色注册表（Role Registry），每个角色声明上述能力面。第二个角色起，新增角色 = 写一份注册声明（纯增量），不动运行时核心。

4. **委派会话化**：`DelegateToElementManager` 从「调 `runElementManager` 拿汇报文本」重写为「创建并驱动一个要素管理员真会话，返回会话句柄 + 汇报摘要」。委派会话进会话列表、按角色分组、可看记录、可继续对话。

5. **确认链收进委派会话**：委派会话**不复用主会话确认链**（放弃穿透）。要素管理员在自己的会话里按自己的权限档位自弹确认卡。会话列表在该会话条目上做**待确认标记**（简单徽标，UI 优化留后续）。——决策依据：页面与开发简洁；既然委派会话已出现在列表，确认就该在那个会话里自己弹。

6. **会话列表组织**：所有会话进**同一个列表，按角色分组**（角色图标 + 分组头）。可查看某角色的全部会话、打开某会话的记录、在某会话里继续对话。

7. **首期范围**：地基 + 把**主智能体**与**要素管理员**两个现有角色都改写为注册角色跑通。机制先行，直聊/委派多轮作为机制之上的能力顺带解锁。不预留第三角色（第二个角色验证「加角色=纯增量」即可，第三个角色出现时再说）。

## 新旧机制替代表

| 旧机制 | 去向 | 说明 |
| :--- | :--- | :--- |
| 主智能体装配（`session.ts` 里硬编码的 system prompt + 全量工具 + 委派工具） | **重构为注册角色** | 主智能体成为注册表里权限最高的角色，装配逻辑从硬编码改为读角色声明 |
| `runElementManager`（一次性 ModelView，跑完即丢） | **重构为角色会话** | 不再是孤立函数，改为「以要素管理员角色驱动一个真会话」；复用统一运行时核心 |
| `createDelegateToElementManagerTool` 的「拿汇报文本」语义 | **重写** | 改为「创建并驱动要素管理员会话，返回会话句柄 + 汇报摘要」；内层 confirm 穿透注入**删除** |
| 委派过程复用主会话确认链（confirm 闭包穿透） | **删除** | 确认收进委派会话自己弹（决策 5）；`createDelegateToElementManagerTool` 的 `context.confirm` 注入链一并拆 |
| 会话列表单一平铺（只有主会话） | **重构** | 会话带角色字段，列表统一按角色分组 |
| 星型结构（主 + 一次性子） | **替换** | 角色共存、统一注册、共用运行时 |

## 迁移条款

**总原则：本机制未上过生产，不做任何兼容，彻底重构，不留历史包袱。**（与《要素管理入口重构施工计划》同一原则。）

1. **会话角色字段**：`ChatSessionState` 新增角色字段。现有 `.novel/sessions/` 下的旧会话**全部是主智能体会话**，加字段后自动归为主角色，语义天然正确，**无需迁移**。代码不写「为兼容旧会话」类注释——角色字段就是会话的固有字段。

2. **存量委派无会话**：旧架构下委派不产生会话（跑完即丢），因此**不存在「旧的委派会话」需要迁移**。升级后新派单才产生真会话。属于「天然无历史包袱」。

3. **`runElementManager` 的旧调用形态**：该函数是内部 API（非落盘数据），重构为角色会话后旧签名直接废弃删除，不留兼容封装。

4. **确认链穿透代码**：`createDelegateToElementManagerTool` 里 `confirm` 闭包穿透、`agentLabel` 改写那段，随决策 5 一并删除，不留死代码。

5. **顺势清理**：凡为兼容开发期旧形态而写的兜底（如 `normalizeSession` 里 `agentMessages → modelView` 迁移），在地基重构中一并评估删除；以「删掉后 test-novel 仍能正常打开」为界，越界的删除回退为保留并记偏差。

## 波次划分

> 顺序按「地基先行、风险递减中的依赖方向」排：W1 立地基（最高风险），W2 用「直聊」这个相对简单的角色会话形态验证地基，W3 啃最硬的委派会话化（此时要素管理员会话已被 W2 验证），W4 收口回归。

### W1 —— 角色注册表地基

**范围**：
- core 定义角色注册表（Role Registry）与角色声明类型：身份、system prompt 装配、工具白名单、路径闸、约束文档、可否委派、独立配置块。
- 主智能体改写为注册角色：现有 `session.ts` 里硬编码的装配（`buildAgentSystemPrompt` + 全量工具 + 委派工具 + NovAI reminder + 用户上下文包装）抽为「主角色声明」。
- 要素管理员改写为注册角色：`buildElementManagerSystemPrompt` / `buildElementSchemaReminder` / `createElementManagerTools`（白名单 + elements/ 路径闸）收进「要素管理员角色声明」。
- 运行时核心（`runChatDriver`/`query`）改为**按会话角色读声明装配**，核心循环只有一套。

**门禁**：`pnpm exec vitest run` 全绿 + `pnpm --filter @novai/core typecheck` + `pnpm --filter @novai/app typecheck` 绿。

**验收点**：
- 主智能体行为与重构前完全等价（同样 system prompt、工具面、注入）。
- 要素管理员被委派时行为与重构前等价（本波先保持委派一次性形态不变，只改装配来源——W3 才改会话化）。
- 注册表可列出两个角色；新增一个角色声明不需要动运行时核心。

### W2 —— 会话挂角色 + 直聊入口

**范围**：
- `ChatSessionState`/`SessionMeta` 加角色字段；`createChatSession`/`createSession` 支持指定角色（默认主角色）。
- 直聊会话装配：以要素管理员角色驱动会话——system prompt 用角色声明、ELEMENT.md 恒注入、工具面用受限白名单（**不含委派工具**，防递归）、用户消息走裸文本（不包主角色上下文）、不注入 NovAI reminder。
- 改动账本/事件流复用：事件标角色归属（`element-manager`），渲染层已有的嵌套任务组逻辑复用。
- UI：会话列表统一按角色分组（图标 + 分组头）；侧栏单击开通直聊入口（新建要素管理员会话并切换）；聊天页顶部角色横幅 + 输入框角色化 placeholder。

**门禁**：测试全绿（新增直聊会话装配测试）+ 双 typecheck 绿 + `pnpm build` 绿。

**验收点**：
- 侧栏单击新建要素管理员会话，列表按角色分组显示，顶部有横幅。
- 直聊发「整理整个要素库」，要素管理员直接读写 elements/（不经主智能体委派）。
- 直聊试图改正文被路径闸拒绝。
- 直聊多轮：第二轮追问能基于第一轮上下文回答（modelView 持久化生效）。
- 主会话行为完全不受影响。

### W3 —— 委派会话化（最硬一波）

**范围**：
- `DelegateToElementManager` 重写：从「调 `runElementManager` 拿文本」改为「创建并驱动一个要素管理员真会话」——生成 sessionId、落盘、进列表、按角色分组，任务跑完会话留存。
- 委派返回主智能体的仍是**汇报摘要**（不污染主上下文），但附会话句柄/标识。
- 确认链收进委派会话：要素管理员在自己会话里按自己权限档位自弹确认卡；**删除** confirm 闭包穿透注入。
- 会话列表待确认标记：委派会话有待确认写操作时，条目上显示标记徽标（简单实现，UI 优化留后续）。
- 委派会话可打开看全过程记录、可进去继续追问（多轮委派）。
- 旧的 `runElementManager` 一次性形态废弃删除。

**门禁**：测试全绿（新增委派会话化测试：会话创建、摘要返回、确认自弹、多轮续聊）+ 双 typecheck 绿 + `pnpm build` 绿。

**验收点**：
- 主智能体委派一次，会话列表出现新的要素管理员会话（按角色分组），可看全过程。
- 主智能体上下文里只有汇报摘要，无要素管理员过程消息。
- 委派会话里写操作自弹确认卡（agentLabel「要素管理」），不穿透主会话。
- 委派会话有待确认时列表条目显示标记。
- 在委派会话里继续追问「你为什么合并 A 和 B」，要素管理员基于该会话上下文回答。
- 主会话委派时的体验不劣于重构前（摘要仍可读）。

### W4 —— 收口回归

**范围**：
- 两角色全链路真机回归（用 `~/note/test-novel`，OPFS 仿真目录承载真实副本）。
- 文档同步：本计划施工日志补齐、`docs/project/当前进度.md` 更新角色机制形态、《要素管理入口重构施工计划》W4 标注「地基已就绪」。

**门禁**：测试全绿 + 双 typecheck 绿 + 生产构建绿 + 真机验收点全过。

**验收点**：
- 主智能体写作、委派、直聊三条链路在真实项目上全部跑通。
- 会话列表按角色分组、委派会话可见可续聊、确认标记生效。

## 明确不做清单（本期排除）

1. **第三角色**——本机制只验证「主 + 要素管理员」两角色；校对/世界观等后续角色出现时再加（届时应为纯增量注册）。
2. **跨会话共享记忆 / 工作日志**——委派会话与直聊会话是独立会话，各自隔离；「要素管理员操作流水日志」作为未来增强，本期不做。
3. **角色对用户自定义开放**——角色是产品内置，不做用户自定义角色 profile（对齐要素管理员升级讨论里「参考 ZCode 但不做用户自定义 profile」的决策）。
4. **待确认标记的 UI 精化**——本期只做简单徽标标记，美观优化留后续。
5. **DeleteFile 放开**——删除需求继续走汇报「建议删除」。
6. **ELEMENT.md 内容改写**——属 LLM WIKI Schema 内容问题，留下一轮。
7. **入口重构的其余波次（斜杠瘦身/删弹窗/提醒按钮）**——那是《要素管理入口重构施工计划》的事，本计划只做它的前置地基（即原 W4 直聊会话的地基 + 委派会话化）。
