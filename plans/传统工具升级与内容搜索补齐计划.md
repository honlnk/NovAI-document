## 一、背景与动机

项目早期刻意没有做内容搜索（grep）工具——决策 0002 明确「grep / rg 场景未来由 RagSearch 承担」。但两个变化让这个映射失效：

1. **2026-09-14 诊断已认定缺内容搜索**：「某人物在哪几章出现」是小说场景最高频的正文搜索需求，当时无任何工具能直接回答。
2. **2026-10-23 章节退出向量索引**：RagSearch 现在只覆盖 plots / timeline 两类要素，章节正文不在索引内。「grep 由 RagSearch 承担」的前提彻底不存在。

同时，EditFile 和 FindFiles 这两个「写完就放着」的传统工具，在真实使用中暴露了两个痛点和一组体验差距。参考系已从 Claude Code 切换到 DeepSeek Harness（决策 0005），本轮以 dsh 和 ZCode 的现行实现为参照。

### 痛点 1：空文件无法用 EditFile 写入

新建一个空文件后，想用 EditFile 往里写内容做不到——`findActualText` 找不到空串的匹配就抛错。没有「空文件特判」路径。

### 痛点 2：改过一次就要重新 ReadFile

每次 EditFile 成功后，`readFileStates.delete(path)` 把读取状态直接删掉。下次再改同一文件，`expectedState` 为 undefined，直接抛「必须先 ReadFile」——哪怕刚刚就是我们自己改的。浪费 token 和时间。

### FindFiles 与 dsh glob 的体验差距

| 维度 | dsh `glob` | NovAI `FindFiles` 现状 |
| :-- | :-- | :-- |
| 排序 | 按修改时间，最近改的排前面 | 按文件名字典序 |
| 超限行为 | 跨顶层目录轮转采样，完整结果落 spill 可取回 | 直接截断前 N 条，只有 `truncated` 标记 |
| 无 `/` 的模式 | `*.txt` 匹配任意深度 basename | 只匹配当前层 |
| 恢复路径 | 超限结果存 spill，告诉模型去哪读 | 无，模型只能自己缩小范围重试 |

## 二、固定设计决策

### D1：EditFile 空文件写入

参照 ZCode edit.ts:124-146 的空文件特判：

- `oldText = ""` 且文件不存在 → 报错（创建文件走 CreateFile，不用 EditFile）。
- `oldText = ""` 且文件存在且内容为空（`content.trim() === ''`）→ 允许，直接写入 `newText`，相当于「填充空文件」。
- `oldText = ""` 且文件存在且内容非空 → 拒绝，报错「文件非空，请提供要替换的原文片段」。
- 空文件写入**豁免读后写校验**（没有旧内容可保护），但仍走确认链。

### D2：EditFile 连续编辑免重读

参照 ZCode edit.ts:572-593 的 `updateReadFileStateAfterEdit`：

- **写完不删 readFileState，改为更新**：EditFile 成功后，把 `readFileStates` 中该文件的条目更新为刚写入的新内容（新 hash、新 lastModified、新 fileSizeBytes），标记 `sourceTool: 'Edit'`。
- **stale 判断改为 mtime + size 优先**：`assertFreshReadFileState` 目前用纯 `contentHash` 比对。改为：先比 `lastModified`（mtime 变新才判 stale）+ `fileSizeBytes`（大小变了才判 stale）；两者都没变 → 放行，不重新 hash。mtime 精度用整数毫秒（对齐 ZCode 的亚毫秒级处理）。
- **net 效果**：模型连续编辑同一文件时，只要文件没被外部改过，就不需要重新 ReadFile。只有外部修改（用户手动编辑、另一个工具写入）导致 mtime/大小变化时，才要求重读。

### D3：FindFiles 按修改时间排序

- 遍历文件时同时收集每个文件的 `lastModified`。
- 返回结果按 `lastModified` 降序排列（最近改的在前）。
- 同 mtime 时按路径字典序兜底（保证确定性）。

### D4：FindFiles 超限跨目录采样

- 当结果超过 `limit` 时，不再简单截断前 N 条。
- 参照 dsh `sampleAcrossTopLevel`：按搜索根下的顶层目录分组，轮转取样，保证每个子目录都有代表。
- 输出中标注「已在 N 个顶层目录中采样展示」。

### D5：FindFiles 超限落 spill

- 超限的完整结果（所有匹配路径）写入 `.novel/spill/find-files-<id>.txt`。
- 输出中附取回指引：「完整列表已存至 <path>，可用 ReadFile 分段取回」。
- FindFiles 加入 `SPILLABLE_TOOLS` 白名单。

### D6：FindFiles 无 `/` 模式匹配任意深度

- 当 `pattern` 不含 `/` 时（如 `*.txt`），匹配任意深度的 basename，而非仅当前层。
- 对齐 dsh glob 的行为：「A pattern with no "/" matches the basename at any depth」。

### D7：SearchFiles 工具参数形态

```
SearchFiles(
  query: string,         // 搜索词。默认字面匹配（非正则）
  path?: string,         // 搜索范围，默认项目根目录。常传 chapters/
  include?: string,      // 单个正向 glob 过滤文件名，如 *.txt。拒绝 ! 取反和逗号列表
  regex?: boolean,       // true 时 query 按 JS 正则解释。默认 false（字面匹配）
  contextLines?: number, // 匹配行前后各带 N 行上下文。默认 2，范围 0-5
  limit?: number         // 返回匹配数上限。默认 100，最大 500
)
```

**默认字面匹配是核心决策**：小说场景的主需求是「林婉儿在哪几章出现过」这类精确人名/词组搜索，正则对模型构造参数是负担。需要正则时显式开 `regex: true`。

**默认带 2 行上下文**：小说里光看「林婉儿」那一行往往不够，要看前后句才知道她在这章干了什么。这是和代码 grep 的关键差异。

### D8：SearchFiles 输出形态

参照 dsh `formatGrepMatches` 的按文件分组：

```
Found N matches

chapters/第003章-夜访.txt
Line 45: 林婉儿推门而入，神色慌张。
  44 | 门外传来急促的脚步声。
  45 | 林婉儿推门而入，神色慌张。
  46 | 「不好了，」她压低声音，「他们来了。」

chapters/第007章-对峙.txt
Line 12: ...
```

- 按文件分组，文件路径为组头。
- 每个匹配给行号 + 匹配行内容 + 前后 contextLines 行（带行号，用缩进区分上下文行和匹配行）。
- 单行超过 2000 字符截断（复用 ReadFile 的 `READ_MAX_LINE_LENGTH`）。
- 超过 `limit` 时截断并附「共找到 N 处匹配，已显示前 limit 处；完整结果已存至 <spill 路径>」。

### D9：SearchFiles 提示词描述

在 `prompt.ts` 的工具规则段新增 SearchFiles 条目（插入在 FindFiles 之后、LoadElements 之前），不改其他工具的现有描述。

**system prompt 工具规则段新增**：

```
- SearchFiles 用于按文件内容搜索：找到某个词、名字或句子出现在哪些文件的哪些行，返回匹配行及前后上下文。默认字面匹配；需要正则时设 regex: true。常用 include: "*.txt" 限定只搜章节。
```

**工具 description 字段**：

```
按文件内容搜索项目中的文本，返回匹配行及前后上下文，按文件分组。默认字面匹配；设 regex: true 启用正则。
```

### D10：SearchFiles 加入 spill 白名单

- SearchFiles 结果可能很大（搜索常见词时），加入 `SPILLABLE_TOOLS`。
- 超限时完整结果落 spill，上下文留预览 + 取回指引。

### D11：权限与路径边界

- SearchFiles 是只读工具，不进确认链，不产生文件变更。
- 路径边界复用 `assertReadableDocumentPath`（`.novel/` 禁读，`.novel/spill/` 放行）。
- `include` 参数校验对齐 dsh：拒绝空串、`!` 取反、逗号列表（`{a,b}` 花括号内的逗号允许）。
- 要素管理员白名单**不装配** SearchFiles（它只需要读要素文件，不需要全项目搜索）。

## 三、明确不做

1. **不动 ReadFile**——三道截断闸已对齐 dsh，无需改动。
2. **不动 ListDirectory**——薄工具，dsh 无对应物，保留现状。
3. **不动 RagSearch**——语义检索是差异化能力，本期只补精确搜索，不改 RAG 内核。
4. **不引入 rg 二进制**——纯浏览器环境，用 FileSystem API + JS 正则/字符串匹配实现。
5. **不做搜索索引**——小说项目体量小（几百章 × 几千字），全量扫描毫秒到秒级，不需要索引。
6. **不做 SearchFiles 的正则语法高亮 UI**——工具结果走现有 summarizeOutput 纯文本摘要即可。
7. **不做 SearchFiles 的大小写开关**——中文搜索大小写无意义；如需英文精确大小写匹配，用 `regex: true` 自行控制。
8. **不做文件内容变更监听驱动的搜索缓存**——全量扫描已够快，不引入缓存一致性复杂度。
9. **不推送远程仓库**。

## 五、新旧机制替代表

| 内容搜索 | 无工具（决策 0002 指定 RagSearch 承担，已失效） | 新增 SearchFiles 工具 |
