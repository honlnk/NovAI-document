## 1. 背景与动机

写小说的联网需求以「实体查询」为主：人物事迹、历史时间线、术语常识、ACG 设定。现有路径是两步——WebSearch 拿摘要列表 → WebFetch 抓某条全文。

而知识平台（维基/百科系）是**标题可寻址**的：条目名可直接拼进 URL。包一层「平台 + 条目名」的直达工具，一步拿到条目全文，省一轮工具往返，也把「该去哪查」从模型的默会知识变成显式可发现的工具能力。

实现形态（用户拍板）：NovAI 项目内维护一个 JSON 风格的平台映射常量，键 = 平台名，值 = URL 模板。后续加平台 = 加一行。

### 事实核查（2026-09-30，施工前完成）

- **网络可达性**：生产 linkseek 的 app 容器 `env/app.env` 配有 `HTTPS_PROXY=http://172.17.0.1:7890`，普通 HTTP 抓取（`/v1/fetch` 同路径，undici EnvHttpProxyAgent）走 mihomo 出境——**维基系在境内服务器可抓**；百度百科/萌娘百科为境内站直连。平台清单无网络硬伤。
- **条目寻址**：`{Question}` 实为「条目名」而非自然语言问题（`/wiki/岳飞` 命中、`/wiki/岳飞的生平` 404）。维基系用 `Special:Search?search=X` 自动跳最匹配条目兜住近似词。
- **进不了名单的平台**（原因落档，防止将来重复评估）：百度文库（ID 寻址 + 付费墙 + 强反爬）、知乎（问题页 ID 寻址，搜索页需登录）、搜索引擎 URL 模板（与 SearXNG 上游重复，且是重点反爬对象）。

### 平台扩展调研（2026-09-30，应用户要求对小说创作领域深度调研）

双通道验证：可达性用生产 linkseek 抓取链路（即 KnowledgeLookup 未来真实链路）+ 本机内置抓取交叉复核；发现类检索用内置搜索（当时 linkseek 搜索引擎侧故障，见下方运维插曲）。

## 2. 决策（拍死，无开放选择题）

1. **工具名 `KnowledgeLookup`**，输入仅 `{ platform, term }` 两个参数，无其它可选项。
2. **平台清单 v1 共 8 键**（见 §3，2026-09-30 扩展调研后定稿；占位符与入参统一叫 `term`，语义是「条目名」而非问题）。
3. **统一机制**：URL 模板渲染 + `provider.fetch`（`/v1/fetch`，`render:'auto'` 服务端质量门控自动升级渲染）。**无平台专用逻辑**——每个平台就是映射表里的一行模板。维基系四键（百科 zh/en、词典、文库）用 `Special:Search?search={term}`（MediaWiki 自动跳最匹配条目，兜住简繁/大小写变体），其余用条目直链。
4. **未命中判定（v1 最小集）**：`statusCode >= 400`，或维基 `finalUrl` 含 `Special:`（没跳转成条目 = 未命中）→ `found: false`，content 置为面向模型的引导文案（换条目名重试 / 改用 WebSearch）。其余平台的未命中页**不识别**，正文照发由模型自行判断（百科的消歧义/搜索页本身有信息量）。
5. **中文编码**：encodeURIComponent 且保留 `/`（MDN 嵌套路径 `Web/JavaScript/...` 的斜杠不能被编码）。
6. **截断**：复用 WebFetch 的 50,000 字符闸（从 `web-fetch.ts` 导出常量复用，不复制）。
7. **无抓取后端**（exa/perplexity）：抛与 WebFetch 相同的「linkseek 直连」引导文案。
8. **园丁白名单不加**：与 WebSearch/WebFetch 一致，园丁子代理不联网。
9. **系统提示词**：加一条工具使用指引（查人物/事件/术语优先用它），并把「外部内容不可信」条目扩到 KnowledgeLookup。

## 4. 工具契约

```ts
// 输入
type KnowledgeLookupInput = {
  platform: KnowledgePlatformName   // 平台表键，validateInput 校验枚举
  term: string                      // 条目名（非空，trim）
}

// 输出
type KnowledgeLookupOutput = {
  platform: string
  term: string
  url: string            // 模板渲染后的实际请求 URL
  finalUrl?: string      // 重定向链终点（未命中判定的依据）
  statusCode?: number
  found: boolean         // 见决策 4
  content: string        // found:false 时为面向模型的引导文案
  truncated: boolean
  renderedBy?: 'http' | 'browser'
  notice?: string
}
```

模型面 schema：`platform` 为 string enum（`Object.keys` 生成），`term` 为 string；description 写明「一步直达知识平台条目全文，查人物/事件/术语/设定优先于 WebSearch→WebFetch 两步」。

`formatResult`：命中 → `已查询 {platform}「{term}」` 头行 + 不可信数据前缀 + 正文（照 WebFetch 形态）；未命中 → 引导文案。

## 6. 验收点

单测（照 `web-fetch.test.ts` 的 mock `globalThis.fetch` 模式）：

1. validateInput：合法 platform + term（trim）
2. validateInput：未知 platform 拒绝，错误信息列出可用平台
3. validateInput：term 空串/非字符串拒绝
4. URL 构造：中文条目名正确编码（`岳飞` → `%E5%B2%B3%E9%A3%9E`）
5. URL 构造：MDN 斜杠路径保留、各段独立编码
6. 未命中（维基 finalUrl 含 `Special:`）→ `found:false` + 引导文案
7. 未命中（statusCode 404）→ `found:false`
8. 命中：`found:true`，content/renderedBy/notice 透传
9. 截断：超 50,000 字符截断并附提示
10. 无抓取后端（exa 档）→ 抛「linkseek 直连」引导文案

门禁：`pnpm test` + `pnpm typecheck`（core/app 双包）全绿。

在线抽查（真实链路，逐平台一次）：对 `/v1/fetch` 发模板渲染后的 URL（用户本地 linkseek dev 实例优先，其次托管实例），断言 HTTP 200 且正文含已知关键词（如 岳飞 / 山 / 岳阳楼记 / scp-173 / 东方Project / Array）。其中维基系四键 + SCP 依赖生产实例出境链路（mihomo），**若届时仍未恢复则该五项记入未验证清单，待恢复后补测**；百度百科/萌娘百科/MDN 不受影响。调研阶段已用生产渲染路径（百度百科）、生产普通抓取（萌娘百科）和本机内置抓取（维基词典/文库/SCP）各验证过一次。

UI 冒烟（可选，用户操作）：test-novel 项目（localhost:5173）里让 agent「查一下岳飞的生平」，观察其调用 KnowledgeLookup 并产出带来源的内容。

## 7. 迁移条款

新增工具，无存量数据/配置迁移。`AgentToolName` 联合类型扩张对旧会话消息向后兼容（旧数据仍是合法成员）。模型面多一个工具 schema，用户零配置，旧项目升级即得。

## 8. 明确不做清单

- 不做跨平台自动回退（zh 未命中自动试 en）——模型看到未命中提示自己会换平台重试，工具保持 dumb
- 不做维基 extract API 专用通道——统一走 HTML→Markdown，一条代码路径
- 不做 preferredSites 限定站搜索形态（`/v1/search` 服务端已支持该参数，本期不暴露）
- 不做用户自定义平台列表（无 UI / 无配置面）——代码常量，要加平台改代码
- 不做缓存与跨章节去重
- 不动 linkseek 仓库
- 不加园丁工具白名单
- 调研后排除的平台不评估第二遍（原因见 §1 排除表）：THBWiki、灰机 wiki、古诗文网、汉典、全历史、Komica/A岛、百度文库、知乎、搜索引擎模板
