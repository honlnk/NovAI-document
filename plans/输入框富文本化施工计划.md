## 背景与范围

### 为什么要做

《要素整理参数化与提取要素退役计划》W3 落地了「斜杠命令落文本」新范式：选中命令后 `/整理要素 ` 以**纯文本**落入输入框，可补参数后发送，发送链路按行首前缀拦截替换为驱动 prompt 全文。但输入框本体仍是原生 `<textarea>`——命令落进去后与普通文字毫无视觉区分，用户看不出哪段是命令、哪段是自己敲的参数。

本期把输入框从 textarea 换成 **Lexical**（headless 用法，与 DSH 同款），实现：

1. **`/命令` token 持久高亮**：完整匹配命令表的 token 着色显示，可编辑可删除，编辑到不再匹配即自动降回普通文字（DSH `TextRefNode` 方案，非 chip）。
2. **`@大纲名` token 输入态高亮**：手输完整大纲名时 token 着色（有效引用确认信号）；选中弹层项后的行为不变（删 token + 激活大纲）。
3. **GhostTextOverlay 平移**：FIM 行内补全的镜像叠层从对准 textarea 改为对准 contenteditable，顺带修掉「超 200px 内部滚动后错位」的存量 bug。
4. **全量行为等价平移**：命令菜单、@弹层、FIM 逐词采纳、Enter/IME 发送、自动增高、撤销——全部保持现有交互语义。

### 三路调研结论（事实依据）

- **DSH composer**（`/Users/honlnk/project/deepseek-harness/packages/client/ui-conversation/src/client/input/`）：Lexical 0.49.0 headless——`createEditor` 在外层 JS 创建，框架侧仅手动 `setRootElement`，**不用 `@lexical/react`**。这对 Vue 是关键利好：官方只有 React 绑定，headless 模式让 Vue 与 React 同等接入。高亮 = `TextRefNode extends TextNode` 的 `createDOM` 加 class + `@lexical/text` 的 `registerLexicalTextEntity`（编辑后不匹配自动降级）；识别规则是纯函数 `scanTextRefs`（`decorations.ts`）。设计弃用记录见 `.agents/notes/archived/architecture/2026-08-20-web-composer-lexical-editor.md`（textarea 三层镜像、手写 contenteditable、@lexical/react 各自为什么被否），施工前值得通读。
- **NovAI 现状**：输入框是 `ChatPanel.vue`（917 行）内的原生 textarea（`:830-840`），`inputText` 单一字符串贯穿六条链路（v-model、指令检测 `:492-519`、token 替换 `:441-459`、ghost 采纳 `:399-418`、发送展开 `:253-281`、草稿恢复）。组件层零测试；纯逻辑测试三个（slash-commands / keyboard / useInlineCompletion）。
- **dsh-input-assist**（`/Users/honlnk/project/dsh-input-assist/`，用户自研的 DSH 输入助手插件）：2026-09-20 已完成「镜像叠层对准 Lexical contenteditable」的真机适配（docs/17），**验证通过**（中文输入 → SSE 流式灰字对齐渐显、Tab 逐词采纳）。可移植三板斧：`copyMirrorMetrics` 15 项计算样式复制（`src/client.ts:643-672`）、`syncMirror` 渲染流程（`:705-735`，错字红字与 ghost 共用镜像层）、scroll/resize 捕获阶段同步（`:2245-2252`）。它是插件身份只能 DOM 外部探测；NovAI 是编辑器宿主，光标 offset 直接用 Lexical API，比它更干净。

### 明确不做（本期排除的诱惑项）

- **claim 进行中着色**（DSH 的 `claim-decor.ts`：命令刚落框等参数时的动态高亮）：不做。我们 W3 范式的「进行中」反馈已由参数弹窗承担，静态高亮足够；留三期与「输入框富文本其他增强」重议。
- **`@大纲` 留痕化**（选中后高亮 token 留在输入框里）：不做，选中行为维持「删 token + 激活大纲」。激活状态已有大纲 chip 展示，输入框保持干净。留痕化改变交互语义，若要做需单独立项。
- **错别字检查**：不施工。但 W2 的镜像层按「可叠加文中任意位置标红」设计（对齐 dsh-input-assist 的双用途镜像层），为其铺路。
- **键盘层迁移到 Lexical command 体系**：不做。Vue `@keydown` 挂在编辑器根元素上与挂 textarea 无差异，SlashCommandMenu/OutlineCommandPopover 的 expose 模式（moveUp/moveDown/confirm）原样保留，避免为迁移而迁移。
- **chip 化任何 token**：不做（DSH `ReferenceChipNode` 整条线不引入）。
- **多行/中段 ghost**：ghost 恒在文本末尾、点中间即丢建议——维持现状语义（dsh-input-assist 同款约定）。
- **GardenerTaskDialog 内部 textarea**：弹窗内的任务描述文本域不动。
- **引入 `@lexical/react`**：Vue 项目，不装 React 绑定。

## 已拍板决策（本计划定稿即生效，审阅时可推翻）

### D1 编辑器选型：Lexical headless，版本对齐 DSH

- 依赖：`lexical`、`@lexical/plain-text`、`@lexical/text`、`@lexical/history`（运行时），`@lexical/headless`（测试）；版本 `^0.49.0` 对齐 DSH 实锁版本。
- 接入模式照 DSH `runtime.ts`：composable 内 `createEditor` + `setRootElement`，`registerPlainText` + `registerHistory(1000ms merge)`；Vue 组件只做挂载与样式。
- 粘贴由 `registerPlainText` 规范化为纯文本（自动满足「粘贴不引入富文本」）。

### D2 文本桥：编辑器是唯一真值，`inputText` 降级为投影

- 新建 `useComposerBridge`（composable，随编辑器实例创建）：
  - `draft: Ref<string>`——`registerUpdateListener` 内做纯文本投影（段落 join `\n`）写入，**替代现有 `inputText`**；
  - `setDraft(text)`——整串写回（清根 + 按行建段落），光标置末，用于命令落文本、采纳补全、清空、草稿恢复；
  - `caretOffset(): number` / `setCaretOffset(n)`——Lexical Selection ↔ 纯文本偏移双向映射（段落间 `\n` 计一位）；
  - `insertAtCaret(text)` / `replaceTokenBeforeCaret(regex, replacement)`——`replaceTokenAtCursor`（`ChatPanel.vue:441-459`）的编辑器版。
- ChatPanel 内所有**读** `inputText` 的链路（发送、`detectCommands`、园丁残留检查 `:579`）改读 `draft`，逻辑零变化；所有**写**链路改走 `setDraft`/`insertAtCaret`。
- caret 映射为纯逻辑，用 `@lexical/headless` 在 vitest 单测（多段落、空文档、光标在段首/段尾/段间换行处）。

### D3 高亮方案：TextRefNode 着色（非 chip），lexicon 两源

- `TextRefNode extends TextNode`，`createDOM` 加 class（主色文字，不加背景框），`isTextEntity(): true`；`registerLexicalTextEntity` 注册，编辑后不匹配自动降回普通 TextNode——照 DSH `text-ref.ts` 结构。
- 识别纯函数 `scanTextRefs(draft): {start, end, kind}[]`：正则 `/(^|\s)([/@])([^\s]*)/` 扫描（不跨 `\n`），`/name` 后必须紧跟空白或结尾（DSH `SLASH_TOKEN_END_RE` 同款），name 精确匹配 lexicon 成员才高亮：
  - `/` 命令：lexicon = `SLASH_COMMANDS` 的 label 集（`/整理要素`、`/生成项目记忆`）；
  - `@` 大纲：lexicon = `props.outlines` 的大纲名集（动态，变化时重扫）。
- headless 单测覆盖：完整匹配高亮、`/整理要素x` 不高亮、非行首不高亮、`x/name` 不高亮、`/整理要素。` 不高亮、编辑降级、lexicon 变化重扫。
- 高亮 span 与镜像层共存前提：着色只用 color（不改字号/字体/字重），镜像层度量不受影响（W2 验收项）。
- 序列化不变：TextRef 是字面文本，纯文本投影自然包含 `/整理要素 ` 原文，`expandSlashCommand`（`slash-commands.ts:57-73`）**零改动**，store/core 发送链路零改动。

### D4 GhostTextOverlay：保留镜像叠层（方案 b 定案）

- 平移：覆盖层挂载宿主从 textarea 改为编辑器根元素（同容器 `absolute inset-0`），继续共享 `.chat-input-base` 度量；`.chat-input-base` 的宿主类同步挂到编辑器根（`style.css:63-87` 归并调整）。
- 度量健壮化（W2 主体）：移植 dsh-input-assist `copyMirrorMetrics` 的 15 项计算样式复制 + `box-sizing: border-box`，替代「共享 class」的隐式约定；Lexical 段落 `<p>` 与镜像层 `margin` 归零对齐。
- 滚动同步（修存量 bug）：镜像层 `overflow:hidden`，编辑区滚动时同步 `scrollTop/scrollLeft`；监听 `window scroll（capture）+ resize` 重同步（dsh-input-assist `client.ts:2245-2252` 同款）。
- FIM 采纳：`acceptNextSegment` 改为 `insertAtCaret(segment)` + `setCaretOffset` 前移（写编辑器模型，保留 undo 历史；dsh-input-assist 的 `setDraft` 整串替换是插件无奈之举，宿主身份不需要）。
- 调度层 `useInlineCompletion` 不动（prefix/suffix 改从 `draft` + `caretOffset()` 取）。

### D5 键盘与 IME：保留 Vue keydown 层，补 composition 监听

- `handleKeydown`（`ChatPanel.vue:287-369`）继续挂在编辑器根元素，五层优先级（Tab/Esc 补全 → 园丁 Esc → 斜杠菜单 → @弹层 → 发送）结构不变。
- Enter 语义：菜单开着走菜单 confirm；否则 Enter=排队、Ctrl/Cmd+Enter=插话、Shift+Enter=换行（换行经 Lexical `insertNewline`，preventDefault 原生行为）。`keyboard.ts` 纯函数不动。
- IME 增强：现 `isImeComposing`（isComposing || keyCode 229）之上，补 `compositionstart/compositionend` 监听 + compositionend 后 10ms Safari 保护窗（DSH `keymap.ts:47-81` 同款三条件），组字中 Tab/Esc/Enter/菜单导航全部放行。
- 占位符：textarea `placeholder` 属性换 CSS 方案（空段落 `:empty::before` 或 data-placeholder + `attr()`），文案不变。

### 修复批：输入框不可编辑真机缺陷（2026-10-07，用户真机报告）

**症状**：用户真机（dev server 项目工作台）点击输入框无法进入输入状态，整体不可用、无法键入任何内容；刷新不恢复。

**根因**：Lexical 0.49 契约——`setRootElement` 只接管事件与渲染，**从不设置 `contenteditable` 属性**（dsh `ComposerContentEditable.tsx:40` 注释明说，其绑定层负责渲染可编辑性）。W1 迁移时宿主 div 未带该属性，Lexical 挂载后元素仍不可编辑；且全程零报错（`data-lexical-editor` / 事件监听 / 状态层全正常）。三波门禁均未拦下：headless 单测不渲染 DOM，模块冒烟只验了编译供给与状态层，`contenteditable` 恰在盲区交叉点上。

**定位过程**：browser-use 检查实况（`contentEditable: "inherit"`、`hasAttribute: false`、`innerHTML` 空）→ 刷新排除 HMR 残留 → 页面内手动 mount 复现（draft 投影正常 + DOM 静默不接管，无报错）→ 读 `setRootElement` 源码（确无 contenteditable 赋值，只设 `data-lexical-editor` 与行内样式）→ dsh 对照定案。

**修复**：`useComposerBridge.mount()` 内统一 `el.contentEditable = 'true'`（挂载即隐含可编辑，未来复用桥不再踩坑；对齐 dsh「绑定层负责可编辑性」的单一写者原则）。

**验证**：dev server 真机——`contentEditable: "true"` + `isContentEditable: true`；focus 进入输入态；`execCommand insertText` 走原生编辑链键入「测试输入第二段」，Lexical 正常渲染 `<p><span data-lexical-text>`；占位符消失、发送按钮解禁（onTextChange → Vue 响应式链贯通）；刷新后空态复原。门禁 548 测试 + typecheck 复跑绿。

**遗留教训**：headless 测试与「模块可加载」冒烟都替代不了 contenteditable 属性级的真机断言；后续若再有编辑器宿主类迁移，验收清单应含「元素属性 + focus + 原生输入链」三件套。
