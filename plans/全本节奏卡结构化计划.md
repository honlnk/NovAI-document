# 全本节奏卡结构化计划

> 状态：**已合并** — 本文档内容已并入《[创作心智模块施工计划](创作心智模块施工计划.md)》，作为统一施工依据。本文档保留供回溯参考，不再独立维护。
>
> 背景：见《[NovAI 市场定位与痛点分析](../product/NovAI市场定位与痛点分析.md)》§5.1。单章 AI 写得还行，连起来不像一本书——连续多章无冲突、章末无钩、情绪曲线失控，是长篇连载的隐形杀手。市面没有任何产品把"全本节奏"做成一等公民功能。
>
> 与伏笔的关系：两者同属"作者的创作心智"（写前规划，主 Agent 写前必读），与"AI 的历史记忆"（elements/，写后沉淀）分属两个层级。节奏卡与伏笔共享同一套交互骨架：看板 + 卡片 + 状态机 + 写前提醒 + 写后回写。

## 一、核心设计判断

### 1.1 节奏卡不属于要素系统

与伏笔同理：要素管理员的工作方式是"概括、合并、精简"，用在节奏上是灾难——把"第 83 章计划冲突 3、情绪温馨、章末无钩"概括成"中期节奏平缓"，AI 写第 83 章时拿到的信息不足以约束生成行为。

因此节奏卡独立存放在 `rhythm/` 目录，与 `elements/`、`plans/`、`foreshadowing/` 平级，**只对主 Agent 开放，要素管理员不可见**。

### 1.2 节奏卡与计划的同构

两者都是"作者对自己的承诺"：

| 维度 | 计划 | 伏笔 | 节奏卡 |
| :--- | :--- | :--- | :--- |
| 本质 | 作者打算做什么 | 作者欠读者什么 | 作者打算让读者怎么感受 |
| 状态 | 收集箱/计划中/进行中/已完成/已搁置 | 已埋/推进中/已收/已放弃 | 规划中/已写/偏差 |
| 时间感 | 什么时候做 | 什么时候收 | 什么时候该高/该低 |
| 视图 | 看板 | 看板 | 看板 |

UI 复用计划板骨架（看板 + 侧栏详情 + 拖拽），详情面板扩展字段。

### 1.3 节奏卡是失控预防，不是状态登记

调研发现的三种翻车：

| 翻车类型 | 病因 |
| :--- | :--- |
| 流水账 | 连续 5 章主角都在升级、收货、被人夸，没有冲突 |
| 情绪过山车 | 连续 10 章压抑 → 突然一章大高潮 → 又突然日常 |
| 章末无钩 | 每章结尾都是"他躺在床上睡了"，读者留存率掉 |

核心病理：**AI 每次只看"这一章要写什么"，看不到"这一章在整本书的什么位置"。** 它不知道上一章已经高潮过了、下一章该缓一缓；也不知道连续三章都是同一种爽点读者会腻。

所以节奏卡的核心价值不是"记下来"，而是"在写之前告诉 AI 这一章该是什么温度"。

### 1.4 节奏 ≠ 时间线

节奏以**章节号**为度量单位（读者翻页的次数），关心读者情绪曲线；时间线以**故事内时间**为度量单位，关心事件先后与因果。两者独立，但可交叉引用（如"时间跳跃章往往是节奏呼吸口"）。节奏卡不承担时间线功能。

## 二、文件结构

```
我的小说/
├── chapters/
│   ├── 第001章-XXX.txt
│   ├── 第002章-XXX.txt
│   └── ...
├── elements/              ← 要素管理员可整理
├── plans/                 ← 计划（已有）
├── foreshadowing/         ← 伏笔（新增，主 Agent 专属）
├── rhythm/                ← 节奏卡（新增，主 Agent 专属）
│   ├── R-001-第001章节奏.md
│   ├── R-002-第002章节奏.md
│   └── ...
├── prompts/
├── novel.config.json
└── .novel/
```

- 一条节奏卡一个 Markdown 文件，文件名带 ID 前缀（与章节命名风格一致）
- ID 由系统生成，作者不可改；名称可改，文件名同步
- **一章一卡**：节奏卡与章节一一对应，不合并、不拆分

## 三、单条节奏卡格式

### frontmatter

```yaml
---
id: R-083
name: 第083章节奏
status: planned
chapter_ref: 第083章

# 计划值（作者/AI 规划时填写）
planned_conflict: 3
planned_mood: 温馨
planned_hook: 无
planned_payoff: 收获
planned_characters: [主角, 师妹]
planned_note: "大高潮后的喘息章，回家吃饭、整理战利品、闲聊"

# 实际值（写完后回写）
actual_conflict: null
actual_mood: null
actual_hook: null
actual_payoff: null
actual_note: null

# 偏差标记
deviation_flag: false
deviation_note: null
---
```

字段说明：

| 字段 | 必填 | 说明 |
| :--- | :--- | :--- |
| id | 是 | 系统生成，格式 `R-XXX` |
| name | 是 | 作者可改 |
| status | 是 | 见下方"状态机" |
| chapter_ref | 是 | 关联章节标识 |
| planned_conflict | 是 | 计划冲突强度，1~10 |
| planned_mood | 是 | 计划情绪基调，见下方"情绪基调枚举" |
| planned_hook | 是 | 计划章末钩子类型，见下方"钩子类型枚举" |
| planned_payoff | 是 | 计划爽点类型，见下方"爽点类型枚举" |
| planned_characters | 建议 | 计划出场主要角色 |
| planned_note | 建议 | 自然语言补充（"大高潮后的喘息章"） |
| actual_conflict | 写后回写 | 实际冲突强度 |
| actual_mood | 写后回写 | 实际情绪基调 |
| actual_hook | 写后回写 | 实际章末钩子 |
| actual_payoff | 写后回写 | 实际爽点类型 |
| actual_note | 写后回写 | AI 对本章节奏的自评 |
| deviation_flag | 自动 | 计划与实际偏差是否超阈值 |
| deviation_note | 自动 | 偏差说明 |

### 正文

```markdown
## 节奏意图

大高潮（第 82 章悲壮决战）之后必须让读者喘口气。
本章写主角回家吃饭、跟师妹闲聊、整理战利品。
不要战斗，不要冲突升级，不要新悬念。

## 上下文衔接

- 上一章（第 82 章）：冲突 9、悲壮、情感爆发
- 下一章（第 84 章）：计划冲突 4、轻松、悬念

## 作者备注

（自由文本，作者记录任何想法）
```

**节奏意图与上下文衔接必须分开记。** 前者是"本章要什么温度"，后者是"前后章的温度差"——AI 需要同时看到两者才能判断"本章是不是该降温"。

## 四、状态机

### 默认 3 状态（UI 看板列）

| 状态 | 英文 | 含义 |
| :--- | :--- | :--- |
| 规划中 | planned | 本章还没写，节奏卡只有计划值 |
| 已写 | written | 本章已写，实际值已回写，偏差在阈值内 |
| 偏差 | deviated | 实际值与计划值偏差超阈值，需要作者注意 |

### 偏差判定规则

| 维度 | 偏差阈值 | 说明 |
| :--- | :--- | :--- |
| 冲突强度 | 计划与实际差值 ≥ 3 | 计划 3 实际 7 = 偏差 |
| 情绪基调 | 计划与实际不一致 | 计划"温馨"实际"悲壮" = 偏差 |
| 章末钩子 | 计划"无"实际有，或计划有实际"无" | 有无之间的翻转 = 偏差 |
| 爽点类型 | 计划与实际不一致 | 计划"收获"实际"无" = 偏差 |

**可配置**：用户在项目设置里选偏差阈值（默认冲突差值 3）。`deviation_flag` 由系统在回写实际值时自动计算，作者不可手动改。

## 五、枚举值定义

### 情绪基调（mood）

| 值 | 说明 |
| :--- | :--- |
| 压抑 | 主角处于困境，读者感到憋屈 |
| 紧张 | 冲突正在升级，读者屏息 |
| 悲壮 | 有代价的胜利或牺牲 |
| 轻松 | 日常、幽默、无压力 |
| 温馨 | 情感暖色，人际亲密 |
| 悬疑 | 信息不完整，读者好奇 |
| 爽感 | 主角占优，读者畅快 |
| 恐怖 | 威胁迫近，读者不安 |
| 悲伤 | 失去、离别、遗憾 |
| 平静 | 过渡、铺垫、无强烈情绪 |

### 章末钩子类型（hook）

| 值 | 说明 |
| :--- | :--- |
| 悬念 | 提出一个问题，不回答 |
| 危机 | 主角面临新的威胁 |
| 反转 | 读者预期被打破 |
| 情感爆发 | 强烈的情绪冲击 |
| 揭秘 | 部分真相揭露 |
| 无 | 章末收束，无钩子 |

### 爽点类型（payoff）

| 值 | 说明 |
| :--- | :--- |
| 升级 | 主角能力/境界提升 |
| 打脸 | 反派被惩治/轻视者被震慑 |
| 收获 | 获得物品/资源/信息 |
| 情感 | 人际关系推进（友情/爱情/亲情） |
| 揭秘 | 读者获得新的信息优势 |
| 无 | 本章无明确爽点 |

## 六、Agent 工具

### 工具清单（主 Agent 专属，要素管理员不装配）

| 工具 | 用途 | 装配时机 |
| :--- | :--- | :--- |
| RhythmList | 列出/筛选节奏卡（按状态、章节范围） | 始终 |
| RhythmRead | 读单条（含计划值与实际值） | 始终 |
| RhythmCreate | 新建节奏卡 | 规划阶段 |
| RhythmUpdate | 更新计划值或回写实际值 | 写后同步 |
| RhythmDelete | 删除（走回收站） | 作者明确要求 |
| RhythmCheck | 高层：返回"第 N 章的计划节奏 + 前后章节奏" | 写前主动调用 |
| RhythmSync | 高层：通读本章，回写实际值并评估偏差 | 写后主动调用 |
| RhythmCurve | 高层：返回指定章节范围的节奏曲线数据 | 作者查询时 |

### 写前/写后工作流

#### 写第 N 章前

1. Agent 接到"写第 N 章"指令
2. 主动调用 `RhythmCheck(chapter: N)` → 返回：
   - 本章计划节奏（冲突、情绪、钩子、爽点）
   - 上一章实际节奏（如果有）
   - 下一章计划节奏（如果有）
3. 把结果注入规划上下文
4. 写作时提示"本章计划冲突 3、情绪温馨、章末无钩，上一章冲突 9、悲壮——请降温"

#### 写完第 N 章后

1. Agent 调用 `RhythmSync(chapter: N)`
2. AI 通读本章，回写：
   - 实际冲突强度、情绪基调、章末钩子、爽点类型
   - 自然语言自评（"本章实际是低强度温馨日常，符合计划"）
3. 系统自动计算偏差标记
4. 提案以卡片形式给作者审阅，**作者批准后才落盘**

#### 节奏曲线查询

作者问"最近节奏怎么样"时：

1. Agent 调用 `RhythmCurve(range: "最近 20 章")`
2. 返回每章的计划值与实际值列表
3. Agent 用自然语言总结："最近 5 章冲突强度持续 7 以上，建议安排一章低强度呼吸口"

## 七、UI 设计

### 侧边栏

新增"节奏"入口，与"计划""伏笔"平级。

### 看板视图

- **三列**：规划中 / 已写 / 偏差
- 卡片可拖拽改状态（从"规划中"拖到"已写"仅标记状态，不触发实际值回写——回写只能由 RhythmSync 完成）
- **"偏差"列自动高亮**：凡 `deviation_flag = true` 的卡片自动进入此列，不可手动拖出（只能修改实际值后由系统重新判定）

### 卡片展示

每张卡片显示：

- 章节名（如"第 083 章"）
- 计划冲突强度（数字 + 颜色：1~3 绿色、4~6 黄色、7~10 红色）
- 计划情绪基调（标签）
- 计划章末钩子（标签）
- 如果已写：实际值与计划值的对比（一致则绿色勾，偏差则红色警告）

### 详情面板

比计划详情多字段：

- 关联章节（只读显示，不可改）
- 计划值编辑区（冲突强度滑块、情绪/钩子/爽点下拉选择、出场角色多选、节奏意图文本框）
- 实际值展示区（只读，由 RhythmSync 回写）
- 偏差说明（如果有）
- 上下文衔接（上一章/下一章的节奏摘要，只读）
- 作者备注（自由文本）

## 八、与伏笔的协同

节奏卡和伏笔在写作循环里同时工作：

```
写第 N 章前：
  ├── RhythmCheck(N)     → "本章计划冲突 3、温馨、无钩"
  ├── ForeshadowingCheck(N) → "本章可考虑回收 F-007"
  └── 两者合并注入规划上下文

写完第 N 章后：
  ├── RhythmSync(N)      → 回写实际节奏 + 偏差评估
  ├── ForeshadowingSync(N) → 提案伏笔变更
  └── 两者提案合并给作者审阅
```

两个工具链独立运行，但**共享同一个"写前规划上下文注入"和"写后提案审阅"的 UI 入口**。

## 九、与章节文件的关系

节奏卡**不写入章节文件**。章节文件保持纯净（纯 txt），节奏信息只存在于 `rhythm/` 目录。

这与伏笔的设计一致（伏笔也不写入章节文件），但与之前讨论的"节奏长在章节 frontmatter"方案不同——最终选择独立目录，理由是：

1. 章节文件格式不变（纯 txt），不引入 frontmatter 解析复杂度
2. 节奏卡与章节一一对应，通过 `chapter_ref` 字段关联，不污染章节内容
3. 章节侧栏可以显示"本章节奏卡"（实时计算，根据 `chapter_ref` 反查），与伏笔的"本章相关伏笔"同一模式

## 十、代码复用约定

节奏卡与计划、伏笔共享同一套"看板卡片"交互骨架。施工时必须最大化复用已有代码，避免三份平行实现。

### 10.1 复用策略

**节奏卡直接复用伏笔施工时已经泛化好的骨架**（见《[伏笔追踪一等公民化计划](伏笔追踪一等公民化计划.md)》§九）。伏笔施工的第一阶段会把计划模块的通用代码上提到 `core/card-board/`，节奏卡施工时无需再做泛化，直接基于骨架实现业务逻辑。

### 10.2 直接复用的代码

以下代码在伏笔施工时已泛化到 `core/card-board/`，节奏卡直接引用：

| 代码 | 位置 | 用途 |
| :--- | :--- | :--- |
| frontmatter 解析与序列化 | `core/card-board/parser.ts` | 节奏卡 frontmatter 字段比计划多，但解析/序列化机制相同 |
| 同列排序算法 | `core/card-board/ordering.ts` | 节奏卡按章节号排序，复用 order 值计算逻辑 |
| 冲突检测 | `core/card-board/store.ts` | 全文 hash 比对 + 冲突错误 |
| 回收站 | `core/fs/trash.ts` | 已共享 |
| 目录扫描骨架 | `core/card-board/store.ts` | 扫描 `rhythm/` 目录 |
| 前端看板骨架 | `components/card-board/BoardPanel.vue` | 三列看板（规划中/已写/偏差） |
| 前端详情面板骨架 | `components/card-board/DetailPanel.vue` | 扩展节奏卡专属字段 |
| 前端 store 骨架 | `stores/card-board.ts` | 保存/防重/草稿/冲突逻辑 |

### 10.3 节奏卡独立实现的代码

| 代码 | 原因 |
| :--- | :--- |
| 状态枚举（planned/written/deviated） | 与计划五列、伏笔四列完全不同 |
| 计划值/实际值双轨字段 Schema | 节奏卡独有，计划和伏笔都没有 |
| 偏差自动判定逻辑 | 节奏卡独有（冲突差值 ≥ 3、情绪不一致、钩子翻转、爽点不一致） |
| RhythmCheck / Sync / Curve 三个高层工具 | 写前注入、写后回写、节奏曲线查询是节奏卡独有业务 |
| 枚举值校验（情绪/钩子/爽点） | 节奏卡独有的枚举体系 |
| 详情面板的滑块/下拉/对比展示组件 | 节奏卡独有的交互形态 |

### 10.4 与伏笔的协同点

节奏卡和伏笔在写作循环里共享同一个"写前规划上下文注入"和"写后提案审阅"的 UI 入口：

- 写第 N 章前：`RhythmCheck(N)` 和 `ForeshadowingCheck(N)` 的结果合并注入规划上下文
- 写完第 N 章后：`RhythmSync(N)` 和 `ForeshadowingSync(N)` 的提案合并给作者审阅

这意味着施工时需要在 Agent Loop 的写前/写后钩子里**同时装配两个模块的工具**，而不是分两次注入。
