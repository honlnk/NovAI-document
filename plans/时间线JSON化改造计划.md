# 时间线结构化改造设计构想

> 状态：设计构想，方向讨论已完成，尚未进入施工。
>
> 本文记录时间线从 Markdown 要素集合演进为项目级事件账本的产品方向，包括基本对象、顺序模型、专用工具和时间轴交互。具体字段契约、旧项目迁移和验收标准需在正式施工计划中定稿。

## 一、要解决的问题

现有时间线由多篇 Markdown 要素文档组成，适合记录事件经过和后续影响，但故事内时间、持续时长、事件顺序与重叠关系主要依赖自然语言表达，无法稳定支撑连续性检查。

长篇创作需要可靠回答：

- 某个事件在故事世界中何时发生，持续了多久？
- 两个事件谁先谁后，是否同时发生？
- 同一人物是否在不合理的时间内出现在不同地点？
- 战争、旅程、修炼等长期过程与正文中的时间流逝是否一致？
- 当前章节叙述了哪些事件，这些事件与哪些既有事件存在因果联系？
- 回忆、预言和时间穿越内容应放在故事时间轴的什么位置？

改造目标不是单纯把文件扩展名改成 JSON，而是确立事件这一基本对象，让事件及其时间顺序成为可查询、可维护、可校验的项目数据。

## 二、产品定位

时间线是**项目级事件账本**，不再作为一堆并列的 Markdown 要素文档维护。**事件是时间线的基本单位，时间轴是事件账本按照故事内顺序生成的可视化视图**，而不是另一份需要独立维护的数据。

- 时间线数据存放在 `elements/` 根目录，与关系账本平级。
- 第一版使用一个 JSON 大文件，顶层采用有序列表保存时间标记。
- 点事件在列表中占用一个对象；区间事件由成对的开始、结束对象共同表达。
- 故事时间与顺序是事件的定位信息，不另设一层“时间节点”作为事件的父级内容对象。
- 左侧工具栏提供独立图标，点击后打开时间轴弹窗，不进入现有要素列表或要素详情窗口，也不使用右侧边栏承载。
- 作者可以在时间轴上直接维护事件。
- 智能体只能通过专用增删改查工具操作，不直接编辑底层 JSON 文件。
- 事件通过稳定标识引用人物、地点、实体、情节和章节等相关数据，避免复制完整内容。

时间线与关系共享“结构化存储、专用工具、确定性查询、图形化维护”的原则，但两者承担不同职责，不强行合并成同一份数据。

## 三、事件、时间标记与有序列表

### 3.1 列表对象是时间标记

事件是作者理解和查询的逻辑单位，时间标记是列表中的存储与定位单位。两者需要区分：

| 事件形态 | 列表表达 | 时间轴表现 |
| :--- | :--- | :--- |
| 点事件 | 一个时间标记，同时保存事件内容 | 一个点，例如“小张出生” |
| 区间事件 | 一个开始标记与一个结束标记，共同属于同一逻辑事件 | 一个区间，例如“小张学骑自行车” |

区间事件的开始标记保存标题、摘要、参与要素、关联章节等详细内容；结束标记只关联对应的开始标记并标记结束，不复制事件详情。两端各自具有稳定的时间标记标识，同时关联同一个事件标识。

开始与结束不必相邻，两者之间允许插入其他点事件或区间事件，从而表达持续过程中的并行事件与嵌套事件。例如：

| 列表顺序 | 时间标记 | 含义 |
| :--- | :--- | :--- |
| 1 | 小张出生 | 点事件 |
| 2 | 小张学骑自行车·开始 | 区间起点，保存事件详情 |
| 3 | 小张进入小学 | 学骑车期间发生的点事件 |
| 4 | 小张学骑自行车·结束 | 只结束对应区间 |

开始和结束是同一个事件的两个时间标记，不是两个独立事件。查询“小张学骑自行车”应返回一个完整事件及其起止范围；修改或删除区间事件时，也必须维护两端的一致性。

### 3.2 列表顺序表达故事内顺序

列表顺序是事件在时间轴上的基本排序依据，不表达章节顺序，也不要求所有事件具有明确日期。作者可以先确定“甲早于乙”，以后再补充架空纪年、季节或相对时间。

明确时间、历法与纪年是对事件的补充描述，并用于辅助定位和冲突检查，不能由系统据此擅自重排作者确定的列表。若明确时间与列表顺序冲突，应明确提示，而不是静默选择其中之一。

因此，第 100 章才揭示的童年事件可以排在时间轴前部，同时关联第 100 章。历史回忆、多条支线、插叙和倒叙不需要为此建立不同格式的时间线。

### 3.3 成对标记的约束

领域模块统一保证：

- 开始标记必须先于对应结束标记。
- 每个开始标记只能对应一个结束标记，反之亦然。
- 结束标记不得脱离开始标记单独存在。
- 删除区间事件时同时处理两端，不留下半个区间。
- 调整任意一端的位置后重新校验顺序与配对关系。
- 允许区间重叠和嵌套，不把重叠本身误判为时间冲突。

## 四、事件、情节与章节的分工

| 概念 | 回答的问题 | 主要职责 |
| :--- | :--- | :--- |
| 事件 | 故事世界里发生了什么 | 记录可独立查询和引用的事实，以及时间、地点、参与要素和结果 |
| 情节 | 这些事件怎样组成一段故事 | 组织相关事件，保留详细经过、不可省略的细节、情感落点、叙事意义和伏笔 |
| 章节 | 读者在何时、以什么方式读到 | 保存正文，并承载叙述顺序、视角、详略和揭示过程 |

事件可以是一瞬间，也可以是一个持续过程，其边界以能否作为独立事实被查询和引用为准，不需要把人物的每个动作都拆成事件。一段情节可以围绕一个事件展开，也可以组织多个相关事件；同一事件可以同时与主线、支线建立关联，不强制唯一归属于某段情节。

时间线不吞并情节要素。事件账本保存用于定位、排序、关联和连续性判断的事实及必要摘要；情节继续承担叙事展开，章节正文保存读者实际阅读到的内容，三者通过稳定标识关联，而不是复制同一份自然语言文本。

例如，“旧桥决裂”可以是一段情节，其中包含“甲收到伪造的信”“甲赶到旧桥”“乙承认欺骗”“甲乙决裂”等事件。时间轴按故事内顺序展示这些事件，情节记录整场决裂的叙事经过与情感落点，后续章节还可以通过回忆重新叙述其中某个事件。

旧时间线要素如何迁移、保留或逐步退役，需在施工前单独定稿，不能默认一次性转换所有历史文本。

## 五、时间表达模型

小说时间不以现实历法或固定纪年为前提。第一阶段的数据模型需要容纳三种表达：

1. **明确时间**：例如架空纪元的某年、某季节或某日，允许使用小说自己的历法与纪年。
2. **顺序时间**：不知道具体日期，但通过列表顺序确定事件甲早于事件乙。
3. **相对时间**：例如“决战后的第三天”“主角入门前十年”。

时间精度可以是年代、年份、季节、日期或更细粒度，不强迫作者为所有事件编造精确时间。列表负责确定基本先后，明确时间和相对时间补充更具体的语义。

每个事件需要区分：

- **故事内时间**：事件在故事世界中何时发生或处于什么顺序。
- **叙事章节**：读者在第几章读到该事件。

回忆、预言、梦境与时间穿越不能因为章节顺序而被误排到故事时间后端。对预言和梦境，还需区分“被预言或梦到的时间”与“所描述事情可能发生的时间”，不能把未知未来伪装成已经发生的确定事实。

## 六、事件与关系的衔接

时间线拥有故事时间语义；关系通过关联事件获得变化依据，不另建一套互不兼容的时间系统。

例如，时间线登记“甲乙决裂”事件后，关系账本可以用该事件说明旧有盟友关系何时结束、新的敌对关系何时开始。关系的当前状态与变化历史分阶段实现，第一版不强制所有关系都携带完整历史。

事件之间的先后、重叠与因果连接可以引用其他事件；事件与人物、地点、实体的参与关系应优先通过时间线事件的参与字段表达，避免在关系账本中重复登记同一份事实。

关系图谱引用的是逻辑事件，而不是把区间事件的开始、结束标记当成两个独立关系节点。

## 七、存储与修改边界

第一版采用单个大 JSON 文件和顶层有序列表，是有意选择的简单起点。对作者和智能体而言，它表现为一个完整的时间线数据库；底层仍由统一领域模块负责加载、校验和保存。

- 智能体不获得直接写入时间线文件的能力。
- 新增、修改、移动和删除必须经过专用工具，统一检查事件引用、时间字段、列表位置、区间配对和关联章节。
- 作者以时间轴作为主要维护界面，不要求手工编辑 JSON。
- 人工操作与智能体工具复用同一套领域操作，不分别维护写入逻辑。
- 正式施工方案需要覆盖版本校验、并发写入、变更记录、错误恢复和外部修改刷新。
- 数据损坏、非法事件、区间配对错误和失效要素引用应明确呈现，不能静默丢弃整段时间线。

单文件方案在事件增多后可能出现整体覆盖、差异过大和冲突范围扩大的问题。后续可以演进为更细粒度的事件记录存储，但保持面向作者和智能体的数据库式操作接口不变。

通用文件工具必须把事件账本列为受保护数据，禁止模型绕过专用工具直接读写。专用领域服务通过项目文件服务访问本地数据，写入携带预期内容版本；界面不直接操作文件，不能只靠内存状态判断是否可以覆盖磁盘。

## 八、公共地基与代码复用

时间线在关系图谱之后实施。第一阶段先复用关系计划建立并经过验收的公共能力，再增加事件与顺序领域逻辑，不重新建立一套弹窗、保存、引用和变更反馈体系。

| 公共能力 | 时间线的复用方式 | 时间线自行负责的内容 |
| :--- | :--- | :--- |
| 通用模态框与工作区弹窗骨架 | 复用遮罩、容器、标题与操作区、内部详情、消息、滚动和关闭收口 | 时间轴与事件详情的具体内容 |
| 公共编辑与反馈控件 | 复用保存状态、预览／编辑、正文表面、错误、冲突和守护的统一规格 | 事件字段草稿、字段比较与写入操作 |
| 账本加载与保存 | 复用格式版本、内容版本校验、同键串行、关闭收口、恢复与变更通知 | 有序列表、点／区间结构、时间约束和插入位置校验 |
| 稳定引用与对象选择 | 复用按稳定标识定位人物、地点、实体、情节与章节关联数据的基础 | 事件标识、时间标记标识和事件节点解析 |
| 左侧入口与图标 | 沿用动作型入口和受控图标注册，只打开时间轴弹窗 | 不新增分类、中间列表或右侧详情分支 |

关系图的节点连线技术与时间轴的轨道布局没有直接复用必要。前者继续服务关系拓扑，后者按有序时间标记计算点、区间和重叠轨道；两者只共享工作区交互与反馈，不合并成万能图形模型。

公共能力在接入时间线前需要重新检查契约与测试，发现缺口时扩展公共适配器，不在时间线组件中建立旁路。时间线专用语义不得反向渗入关系模块或通用弹窗骨架。

## 九、智能体工具与检索边界

### 9.1 基础工具

| 操作 | 主要作用 |
| :--- | :--- |
| 列出与读取 | 查询事件详情，或读取指定位置附近的时间标记与事件摘要 |
| 新增点事件 | 写入事件内容，并指定插入到哪个时间标记之前或之后 |
| 新增区间事件 | 写入开始标记的详细内容，分别指定开始与结束标记的插入位置 |
| 修改事件 | 修改标题、摘要、明确或相对时间、参与要素、情节和章节关联等内容 |
| 调整顺序 | 将已有时间标记移动到另一个标记之前或之后，并重新校验区间 |
| 删除事件 | 删除点事件，或连同开始、结束标记删除整个区间事件 |

新增与调整顺序是不同操作：前者解决新事件应该放在哪里，后者解决已有事件的位置错误。所有定位都使用时间标记的稳定标识，不向智能体暴露容易随插入、删除而变化的列表下标。

除机械增删改查外，还需要支持面向创作意图的确定性查询：

| 查询意图 | 返回内容 |
| :--- | :--- |
| 查询某时间范围内的事件 | 符合明确时间、相对时间或顺序约束的事件及必要摘要 |
| 查询某章节叙述的事件 | 与章节关联的事件，区分正文当下发生、回忆、预言、梦境等叙述方式 |
| 查询某人物参与的事件 | 按故事内顺序返回相关事件 |
| 查询事件前后文 | 指定标记之前、之后的事件，以及与事件存在因果关联的其他事件 |
| 检查时间连续性 | 返回可由结构化数据明确判断的顺序、区间、重叠和参与冲突 |

### 9.2 由智能体决定插入位置

智能体新增事件时，根据已有事件和创作意图选择插入到哪个时间标记之前或之后，也可以选择列表开头或末尾。新增区间事件时，需要分别决定开始标记与结束标记的位置。

智能体应先读取候选位置前后的局部时间线，再提交插入操作，避免在不了解上下文时盲插。写入时需要识别时间线是否已被其他操作改变，防止基于过期列表把事件插入错误位置。现有信息不足以判断顺序时，应继续查询或请作者确认，而不是编造精确时间。

### 9.3 时间线退出 RAG 索引

**时间线事件账本不进入 RAG（语义检索）索引，确定性时间查询全部通过专用工具完成。** 情节要素继续沿用语义召回，用于取得详细经过、情感落点和叙事意义。

正式施工时需要同步移除现有时间线要素进入语义索引的接入逻辑，清理已有时间线索引记录，并更新相关配置、提示与测试。迁移过渡期不得把同一事件同时作为旧时间线文档和新事件账本重复召回。

## 十、时间轴交互

时间轴按照列表中的故事内顺序展示事件，允许缩放、平移、搜索和按人物、地点、情节或事件类型筛选。时间轴是事件账本的视图，所有查看、编辑和智能体写入都作用于同一份数据。

时间轴与事件详情均在独立弹窗中展示和维护，不复用要素工作区的列表、详情面板或右侧边栏。跳转到章节、情节或其他要素时，才离开时间轴弹窗并打开对应内容。

第一阶段需要支持：

- 将点事件显示为点，将成对标记显示为从开始到结束的区间。
- 展示明确时间、相对时间和仅能确定先后的事件，不虚构不存在的精度。
- 新建、编辑和删除事件，所有修改都直接作用于事件账本，时间轴同步反映结果。
- 查看事件的时间定位、章节关联、参与要素、关联情节和必要摘要。
- 从事件跳转到相关章节、情节或其他参与要素。
- 智能体修改后同步刷新时间轴。
- 对无法排序、配对错误、明确时间与列表顺序矛盾等数据给出明确提示。

### 10.1 重叠事件动态分配轨道

时间轴允许多个区间相互重叠或嵌套。渲染时根据列表位置和区间覆盖范围动态分配轨道：

- 不重叠的区间可以复用同一轨道。
- 部分重叠或相互嵌套的区间分配到不同轨道，避免视觉遮盖。
- 点事件落在对应顺序位置；与其他内容冲突时同样参与布局调整。
- 插入、删除、移动或修改起止位置后重新计算轨道。

轨道编号只是界面布局结果，不写入 JSON，也不参与事件语义和连续性判断。

时间轴首先服务于作者理解与维护，不以制作复杂视觉效果为目标。连续性警告必须来自可解释的数据规则，不让模型凭感觉把猜测显示成确定错误。

## 十一、与现有模块的边界

| 模块 | 职责 |
| :--- | :--- |
| 时间线 | 以事件为基本单位，记录世界里发生了什么、何时发生、以什么顺序发生 |
| 关系 | 记录要素与事件之间已经登记的结构化连接 |
| 情节 | 组织相关事件，记录具体经过、细节和叙事意义，并继续提供语义召回 |
| 伏笔 | 作者欠读者什么，以及何时需要回收 |
| 节奏卡 | 作者希望读者在每一章如何感受 |

故事内时间与读者阅读节奏是两个独立维度。节奏卡继续以章节为度量，不承担时间线功能。

## 十二、后续施工前必须定稿的事项

- 事件标识、时间标记标识、点与区间对象、列表定位和相对时间的字段契约。
- 架空历法、模糊精度、未知时间与时间跨度的统一表达。
- 事件粒度、事件与情节的关联方式，以及事件与章节、人物、地点、实体及关系的引用边界。
- 插入、移动、区间配对和过期位置写入的校验规则。
- 单文件的版本校验、并发保护和损坏恢复策略。
- 现有 Markdown 时间线的迁移、双写或保留策略，以及旧 RAG 索引的清理与回归验收。
- 时间轴对相对顺序、重叠事件、多条支线和动态轨道的具体展示方式。
- 连续性检查的规则范围，以及哪些判断仍需作者或模型审阅。
