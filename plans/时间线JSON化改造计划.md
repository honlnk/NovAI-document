# 时间线结构化改造施工计划

> 状态：施工中（2026-11-22 goal 指令开工）。阶段 1（公共接线）、阶段 2（领域与服务层 + 六工具）、阶段 3（时间轴与详情编辑）已完成。本文解决原设计构想第十二节列出的八项定稿事项，并给出字段契约、模块划分、阶段门禁与验收标准；产品方向与概念分工见下文第一至六节。施工状态、偏差与验收结果见文末施工日志。
>
> 定稿时已确认的前提：**项目尚未对外发布，不考虑旧数据兼容**——旧 Markdown 时间线要素整套退役删除，不提供任何迁移、导入或双写机制。

## 一、要解决的问题

现有时间线由多篇 Markdown 要素文档组成，适合记录事件经过和后续影响，但故事内时间、持续时长、事件顺序与重叠关系主要依赖自然语言表达，无法稳定支撑连续性检查。

长篇创作需要可靠回答：

- 某个事件在故事世界中何时发生，持续了多久？
- 两个事件谁先谁后，是否同时发生？
- 同一人物是否在不合理的时间内出现在不同地点？
- 战争、旅程、修炼等长期过程与正文中的时间流逝是否一致？
- 当前章节叙述了哪些事件，这些事件与哪些既有事件存在因果联系？
- 回忆、预言和时间穿越内容应放在故事时间轴的什么位置？

改造目标不是单纯把文件扩展名改成 JSON，而是确立事件这一基本对象，让事件及其时间顺序成为可查询、可维护、可校验的项目数据。

## 二、产品定位

时间线是**项目级事件账本**，不再作为一堆并列的 Markdown 要素文档维护。**事件是时间线的基本单位，时间轴是事件账本按照故事内顺序生成的可视化视图**，而不是另一份需要独立维护的数据。

- 时间线数据存放在 `elements/` 根目录，与关系账本平级。
- 第一版使用一个 JSON 大文件，顶层采用有序列表保存时间标记。
- 点事件在列表中占用一个对象；区间事件由成对的开始、结束对象共同表达。
- 故事时间与顺序是事件的定位信息，不另设一层"时间节点"作为事件的父级内容对象。
- 左侧工具栏提供独立图标，点击后打开时间轴弹窗，不进入现有要素列表或要素详情窗口，也不使用右侧边栏承载。
- 作者可以在时间轴上直接维护事件。
- 智能体只能通过专用增删改查工具操作，不直接编辑底层 JSON 文件。
- 事件通过稳定标识引用人物、地点、实体、情节和章节等相关数据，避免复制完整内容。

时间线与关系共享"结构化存储、专用工具、确定性查询、图形化维护"的原则，但两者承担不同职责，不强行合并成同一份数据。

## 三、事件、时间标记与有序列表

### 3.1 列表对象是时间标记

事件是作者理解和查询的逻辑单位，时间标记是列表中的存储与定位单位。两者需要区分：

| 事件形态 | 列表表达 | 时间轴表现 |
| :--- | :--- | :--- |
| 点事件 | 一个时间标记，同时保存事件内容 | 一个点，例如"小张出生" |
| 区间事件 | 一个开始标记与一个结束标记，共同属于同一逻辑事件 | 一个区间，例如"小张学骑自行车" |

区间事件的开始标记保存标题、摘要、参与要素、关联章节等详细内容；结束标记只关联对应的开始标记并标记结束，不复制事件详情。两端各自具有稳定的时间标记标识，同时关联同一个事件标识。

开始与结束不必相邻，两者之间允许插入其他点事件或区间事件，从而表达持续过程中的并行事件与嵌套事件。例如：

| 列表顺序 | 时间标记 | 含义 |
| :--- | :--- | :--- |
| 1 | 小张出生 | 点事件 |
| 2 | 小张学骑自行车·开始 | 区间起点，保存事件详情 |
| 3 | 小张进入小学 | 学骑车期间发生的点事件 |
| 4 | 小张学骑自行车·结束 | 只结束对应区间 |

开始和结束是同一个事件的两个时间标记，不是两个独立事件。查询"小张学骑自行车"应返回一个完整事件及其起止范围；修改或删除区间事件时，也必须维护两端的一致性。

### 3.2 列表顺序表达故事内顺序

列表顺序是事件在时间轴上的基本排序依据，不表达章节顺序，也不要求所有事件具有明确日期。作者可以先确定"甲早于乙"，以后再补充架空纪年、季节或相对时间。

明确时间、历法与纪年是对事件的补充描述，并用于辅助定位和冲突检查，不能由系统据此擅自重排作者确定的列表。若明确时间与列表顺序冲突，应明确提示，而不是静默选择其中之一。

因此，第 100 章才揭示的童年事件可以排在时间轴前部，同时关联第 100 章。历史回忆、多条支线、插叙和倒叙不需要为此建立不同格式的时间线。

### 3.3 成对标记的约束

领域模块统一保证：

- 开始标记必须先于对应结束标记。
- 每个开始标记只能对应一个结束标记，反之亦然。
- 结束标记不得脱离开始标记单独存在。
- 删除区间事件时同时处理两端，不留下半个区间。
- 调整任意一端的位置后重新校验顺序与配对关系。
- 允许区间重叠和嵌套，不把重叠本身误判为时间冲突。

## 四、事件、情节与章节的分工

| 概念 | 回答的问题 | 主要职责 |
| :--- | :--- | :--- |
| 事件 | 故事世界里发生了什么 | 记录可独立查询和引用的事实，以及时间、地点、参与要素和结果 |
| 情节 | 这些事件怎样组成一段故事 | 组织相关事件，保留详细经过、不可省略的细节、情感落点、叙事意义和伏笔 |
| 章节 | 读者在何时、以什么方式读到 | 保存正文，并承载叙述顺序、视角、详略和揭示过程 |

事件可以是一瞬间，也可以是一个持续过程，其边界以能否作为独立事实被查询和引用为准，不需要把人物的每个动作都拆成事件。一段情节可以围绕一个事件展开，也可以组织多个相关事件；同一事件可以同时与主线、支线建立关联，不强制唯一归属于某段情节。

时间线不吞并情节要素。事件账本保存用于定位、排序、关联和连续性判断的事实及必要摘要；情节继续承担叙事展开，章节正文保存读者实际阅读到的内容，三者通过稳定标识关联，而不是复制同一份自然语言文本。

例如，"旧桥决裂"可以是一段情节，其中包含"甲收到伪造的信""甲赶到旧桥""乙承认欺骗""甲乙决裂"等事件。时间轴按故事内顺序展示这些事件，情节记录整场决裂的叙事经过与情感落点，后续章节还可以通过回忆重新叙述其中某个事件。

## 五、时间表达模型

小说时间不以现实历法或固定纪年为前提。数据模型需要容纳三种表达：

1. **明确时间**：例如架空纪元的某年、某季节或某日，允许使用小说自己的历法与纪年。
2. **顺序时间**：不知道具体日期，但通过列表顺序确定事件甲早于事件乙。
3. **相对时间**：例如"决战后的第三天""主角入门前十年"。

时间精度可以是年代、年份、季节、日期或更细粒度，不强迫作者为所有事件编造精确时间。列表负责确定基本先后，明确时间和相对时间补充更具体的语义。

每个事件需要区分：

- **故事内时间**：事件在故事世界中何时发生或处于什么顺序。
- **叙事章节**：读者在第几章读到该事件。

回忆、预言、梦境与时间穿越不能因为章节顺序而被误排到故事时间后端。对预言和梦境，还需区分"被预言或梦到的时间"与"所描述事情可能发生的时间"，不能把未知未来伪装成已经发生的确定事实。

## 六、事件与关系的衔接

时间线拥有故事时间语义；关系通过关联事件获得变化依据，不另建一套互不兼容的时间系统。

例如，时间线登记"甲乙决裂"事件后，关系账本可以用该事件说明旧有盟友关系何时结束、新的敌对关系何时开始。关系的当前状态与变化历史分阶段实现，本计划不强制任何关系携带历史。

事件之间的先后、重叠与因果连接可以引用其他事件；事件与人物、地点、实体的参与关系应优先通过时间线事件的参与字段表达，避免在关系账本中重复登记同一份事实。

关系图谱引用的是逻辑事件，而不是把区间事件的开始、结束标记当成两个独立关系节点。

## 七、八项定稿决策

对应原设计构想第十二节的顺序：

| # | 事项 | 决策 | 要点 |
| :-- | :--- | :--- | :--- |
| 1 | 字段契约（事件标识、时间标记标识、点/区间对象、列表定位、相对时间） | **事件与标记分离，标记挂事件详情** | 事件标识 `EVT-` + 10 位小写字母数字，时间标记标识 `TM-` + 10 位；账本顶层为标记有序列表，点标记携带事件详情，区间开始标记携带详情、结束标记只回指。全部定位走稳定标识，不暴露列表下标。契约见第八节。 |
| 2 | 架空历法、模糊精度、未知时间与时间跨度的统一表达 | **结构化三态 + 自由文本历法** | 明确时间为「历法自由文本 + 数值段」结构（年必填，季节/月/日可选），系统不理解历法语义、不做历法换算；相对时间为「锚事件标识 + 偏移量 + 单位 + 方位」结构；两者皆可空（纯顺序时间）。跨度只由区间起止表达，不单独存时长字段。 |

| 4 | 插入、移动、区间配对和过期位置写入的校验规则 | **六条领域校验 + 账本级版本校验** | 写入前校验：锚标记存在、区间开始先于结束、一一配对、锚点不得落在本区间内部、事件引用合法（人物等五类 + 事件类型限定）、章节引用可解析。所有结构写入携带账本内容哈希，不匹配即冲突，不自动合并。 |
| 5 | 单文件的版本校验、并发保护和损坏恢复策略 | **沿用关系图谱账本体系** | 域内写锁串行化一切写入（UI 与工具共用一条链）；JSON 账本原语负责哈希版本与损坏错误；损坏态 UI 只读呈现原始内容 + 副本入回收站重新初始化，工具教学式报错不自动重置；非法条目隔离不丢弃，隔离期间写入阻止直至清理。 |
| 6 | 现有 Markdown 时间线的迁移、双写或保留策略，以及旧 RAG 索引的清理与回归验收 | **整套退役删除，零迁移零双写** | 项目未上线，不做任何兼容：旧「时间线」要素类型、目录、模板、索引接入、目录披露、界面分类全部删除；RAG 索引范围收窄为仅情节，旧索引记录随首次重建清空（账本服务首次激活时自动触发一次全量重建）；提示词同步改写。见第十一节替代表。 |
| 7 | 时间轴对相对顺序、重叠事件、多条支线和动态轨道的展示方式 | **单轴顺序 + 重叠分轨 + 自绘 SVG** | 一根故事内顺序轴，标记按列表顺序等距落位；区间画为开始→结束的横带，重叠/嵌套区间动态分轨，不重叠复用同轨；点事件落在顺序位置；明确时间以角标显示，相对时间以锚事件关联显示；多支线不做泳道，靠筛选（按人物/情节/类型）阅读；轨道编号只是布局结果不写入账本。不引入日期比例尺。 |
| 8 | 连续性检查的规则范围 | **不做检查器，交给 AI 判断** | 不提供连续性检查工具，不把「顺序与明确时间矛盾」「同人短时跨地」等判定写死进代码。账本只保证结构合法（配对、引用可解析、顺序约束），语义层面的连续性由主智能体读取事件数据后自行判断并与作者讨论；界面不呈现系统级连续性告警。 |

## 八、数据契约

### 8.1 标识

- 事件标识：`EVT-` + 10 位小写字母数字，域内创建时生成，永久稳定。
- 时间标记标识：`TM-` + 10 位，域内创建时生成，永久稳定。
- 要素引用沿用 `ELM-` 标识与懒分配写回（关系图谱既有机制）：事件引用某要素时，若该要素尚无标识，先校验引用合法性再分配写回，写回的要素文件进变更账本。
- 章节引用沿用「全本章号位置」语义（章节目录服务）：改名不影响关联；删后同号重建展示位置恢复但标注无法确认是否原章节；重复章号待消歧不自动选择。

### 8.2 账本文件

`elements/timeline.json`：

```json
{
  "version": 1,
  "markers": [
    {
      "id": "TM-a1b2c3d4e5",
      "kind": "point",
      "eventId": "EVT-x1y2z3w4v5",
      "event": {
        "title": "小张出生",
        "summary": "……",
        "storyTime": { "calendar": "苍穹历", "year": 102, "season": "春" },
        "relativeTime": null,
        "participants": [{ "kind": "element", "id": "ELM-……", "role": "主角" }],
        "plotIds": ["ELM-……"],
        "chapters": [{ "chapterNumber": 3, "mode": "current" }],
        "causedBy": [],
        "createdAt": "……",
        "updatedAt": "……"
      }
    },
    {
      "id": "TM-b2c3d4e5f6",
      "kind": "start",
      "eventId": "EVT-r1s2t3u4v5",
      "event": {
        "title": "小张学骑自行车",
        "summary": "……",
        "storyTime": null,
        "relativeTime": { "anchorEventId": "EVT-x1y2z3w4v5", "offset": 6, "unit": "year", "direction": "after" },
        "participants": [],
        "plotIds": [],
        "chapters": [{ "chapterNumber": 8, "mode": "current" }],
        "causedBy": ["EVT-x1y2z3w4v5"],
        "createdAt": "……",
        "updatedAt": "……"
      }
    },
    { "id": "TM-c3d4e5f6g7", "kind": "end", "eventId": "EVT-r1s2t3u4v5", "startId": "TM-b2c3d4e5f6" }
  ]
}
```

**标记对象**：

| 字段 | 必填 | 约束 |
| :-- | :-- | :-- |
| `id` | 是 | `TM-` 前缀，域内唯一 |
| `kind` | 是 | `point` / `start` / `end` 三值 |
| `eventId` | 是 | `EVT-` 前缀；同一事件的开始/结束标记共享同一 eventId |
| `event` | point/start 必填，end 禁止 | 事件详情对象，结束标记不携带 |
| `startId` | end 必填，其余禁止 | 回指本区间开始标记的 `TM-` 标识 |

**事件详情对象**：

| 字段 | 必填 | 约束 |
| :-- | :-- | :-- |
| `title` | 是 | 非空短文本 |
| `summary` | 否 | 自然语言摘要，允许空串 |
| `storyTime` | 否（可 null） | 明确时间：`calendar`（自由文本历法名）、`year`（数值，可负）、`season`/`month`/`day`（可选）。系统不理解历法语义，不换算、不排序 |
| `relativeTime` | 否（可 null） | 相对时间：`anchorEventId`（锚事件标识）、`offset`（数值）、`unit`（day/month/year/era 等短词）、`direction`（before/after）。锚事件删除后此字段进入失效提示，不自动清除 |
| `participants` | 否 | `{ kind: 'element', id, role? }` 列表；引用类型限人物、地点、实体、世界观四类（情节走 `plotIds`，事件互引走 `causedBy`） |
| `plotIds` | 否 | 关联情节的 `ELM-` 标识列表；同一事件可关联多段情节，不强制唯一归属 |
| `chapters` | 否 | `{ chapterNumber, mode }` 列表，`mode` 为 `current`（正文当下）/ `recall`（回忆）/ `prophecy`（预言）/ `dream`（梦境）；同一事件可挂多章（如正文当下在第 3 章、第 100 章回忆重述） |
| `causedBy` | 否 | 因果前驱的事件标识列表（指逻辑事件而非标记） |
| `createdAt` / `updatedAt` | 是 | ISO 时间戳，域内维护 |

`storyTime` 与 `relativeTime` 可同时填写（如「决战后第三天」即苍穹历 102 年），互不校验一致性；两者皆空即纯顺序时间，合法且常见。

### 8.3 损坏与非法数据

- **整文件损坏**（JSON 解析失败、根结构不是对象、`version` 不识别）：进入损坏态——UI 只读呈现原始内容并提供「重新初始化」出口（先把原文件副本存入 `.novel/trash/timeline-<时间戳>.json` 再写空账本）；智能体工具返回教学式错误引导告知作者，不自动重置。
- **单条非法**（字段缺失、配对破坏、引用格式坏、id 重复）：保留在文件中不丢弃，加载时进入 issue 列表，时间轴与检查面板呈现，可在弹窗中逐条删除修复；存在隔离条目期间一切结构写入阻止（坐标类纯展示写入除外——时间轴无坐标状态，故等同于全阻止）。
- **结构性约束不破**：结束标记孤立、开始标记无结束、区间倒置等一律按非法条目隔离处理，绝不在载入时自动修补。

## 九、模块划分

### 9.1 公共地基（复用关系图谱，零新建）

| 能力 | 复用对象 | 本计划接入方式 |

### 9.2 时间线领域模块

`core/timeline/store.ts` + `core/services/timeline-service.ts`：

- **载入**：`loadTimelineLedger`——文件不存在视为空账本（首次写入才建文件）；结构性损坏抛损坏错误；非法条目隔离。
- **CRUD**：创建点事件（指定锚标记前/后或列表首尾）、创建区间事件（分别指定两端插入位置）、更新事件详情、移动标记（重新校验配对与顺序）、删除事件（区间两端同删）。
- **查询**：按时间范围（明确时间可比较时）、按章节（含叙述方式过滤）、按参与要素、事件前后文（指定标记之前/之后 N 条 + 因果链）。
- **校验**：第八节决策 4 的六条 + 事件引用类型限定 + 章节引用经章节目录服务核对。
- **级联**：删除要素时清理引用该要素的参与者/情节条目（DeleteFile 链路，对齐关系图谱级联先例，结果带级联计数）；删除事件时清理其他事件 `causedBy`/`relativeTime` 中指向它的引用（`causedBy` 直接移除，`relativeTime` 置失效提示不自动清除）。
- **变更通知**：模块级事件（ui/agent 双来源），时间轴据此刷新，对齐关系图谱。

### 9.3 智能体工具

主 Agent 专属六个基础工具，要素管理员不装配（对齐伏笔/节奏/关系先例）：

| 工具 | 读写 | 作用 |
| :-- | :-- | :-- |
| TimelineList | 读 | 列出事件（可按参与要素、情节、章节、时间范围过滤）；输出截断 50 条 + 总数与指引 |
| TimelineRead | 读 | 单事件详情（区间事件返回完整起止范围）；或指定标记前后 N 条的局部时间线 |

## 十三、边界与暂缓（尾巴清单）

- **关系变化历史**：关系端点可引用事件后，「某关系何时开始/结束」的第一版表达就是在描述里写事件名，不做结构化的关系历史字段。
- **软连续性告警**：不做。语义连续性（瞬移、时长合理与否）完全交给模型阅读事件数据后判断，界面零系统告警。
- **多支线泳道**：不做。多支线靠筛选阅读，单轴即全部事件。
- **历法换算与排序**：`calendar` 仅展示用，系统永不按明确时间重排列表；跨历法比较不支持。
- **时间轴小地图/概览导航**：不做，缩放平移即可。
- **事件批量操作**（批量删除、批量改关联）：不做。
- **要素管理员直聊中的事件登记**：不装配时间线工具，事件登记统一走主 Agent。
- **rag 索引弹窗迁移到 WorkspaceModal**：不在本计划范围。
