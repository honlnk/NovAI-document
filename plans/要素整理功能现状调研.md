## 一、整体架构：一条「用户意图 → 主 Agent → 园丁子代理」的委派链

要素整理的核心设计是**委派**：用户不直接驱动园丁，而是驱动主 Agent，主 Agent 再通过 `DelegateToGardener` 工具把任务委派给一个独立的园丁子代理。

```
用户 ──输入──→ 主 Agent（主对话）
                │ 识别到 GARDENER_TASK_PROMPT，或自主判断「该整理了」
                ▼
        DelegateToGardener 工具调用（task 自包含 + scope 可选）
                ▼
        园丁子代理（独立 LLM 循环，全新上下文）
                │ 工具白名单 + elements/ 路径闸
                ▼
        写回 elements/**/*.md + 固定结构汇报
```

**最关键的设计决策**：园丁**看不到主对话**。所有上下文必须通过 `task` 参数自包含传入。这保证园丁每次以全新上下文运行，不受对话历史污染，也便于压缩和审计。

## 二、园丁子智能体（gardener）

实现核心在 `packages/core/src/core/agent/gardener.ts`（316 行）。它是「一次性、每次全新上下文」的子代理，遵循《要素园丁子代理设计》v3。

### 1. 提示词栈：只有两层

园丁的 system prompt 由 `buildGardenerSystemPrompt`（gardener.ts:42-53）组装，**仅两层**：

| 层 | 内容 | 来源 |
| :-- | :-- | :-- |
| 第 1 层 | `GARDENER_PERSONA` 角色铁律 | 硬编码（gardener.ts:17-33） |
| 第 2 层 | `prompts/ELEMENT.md` 全文（本书要素规范） | 运行时 `readElementSchema` 读盘 |

提示词家族其余文件（`system.md` / `NovAI.md` / `prompts/outlines/`）**一律不进园丁上下文**（gardener.ts:9-14 注释）：那些是主 Agent 的写作人格，园丁要的是纯粹的要素维护工。

ELEMENT.md 缺失时不阻塞运行，附兜底层 `SCHEMA_MISSING_NOTE`（gardener.ts:36）。

**persona 铁律四条**：
- 从不修改 `chapters/` 正文与 `prompts/` 任何文件
- 只能写入 `elements/` 下的文件，其余一切只读
- 合并同名/近名要素保留旧文件全部事实，存疑不合并，列入汇报
- 不删除、不重命名任何文件；确需的列入汇报交用户

### 2. 工具白名单 + 路径闸：运行层强制，不依赖模型自觉

**白名单**（gardener.ts:59-65）：

```
ListDirectory, FindFiles, ReadFile, RagSearch, CreateFile, EditFile
```

可写工具只有 `CreateFile` / `EditFile`（gardener.ts:56）。**没有** DeleteFile / RenameFile / GetFileChangeHistory / Web 工具 / 委派工具——保守设计，删/改名列入汇报交用户（gardener.ts:58 注释）。

**路径闸** `guardElementsScope`（gardener.ts:88-103）：把两个可写工具的 `validateInput` 包一层，强制 `path` 必须以 `elements/` 开头（大小写不敏感），否则抛错回灌给模型。这是**运行层强制**——模型越界请求只会收到失败结果，不会真的写出去，不靠模型自觉。

`createGardenerTools`（gardener.ts:71-85）从全量工具表按白名单过滤，白名单引用了未注册工具会直接抛错（防御）。

### 3. 配置覆盖：按次定格，动态继承

`mergeGardenerOverrides`（gardener.ts:121-133）合成园丁本次运行的配置：

- `config.gardener.llm` 覆盖 → 整组展开（端点/密钥/模型名/temperature）
- `config.gardener.permissionPreset` 覆盖 → 写进 `settings.permissionPreset`，权限判定链无感知地双向生效（放宽与收紧都正确）
- 未覆盖项 → **动态继承主配置当时值**
- 合成结果**不落盘**，仅本次运行内存存在——按次定格（D5），运行中主配置变更不影响本次

曾否决的方案：把覆盖注入做在 `confirm` 闭包里——判 allow 时不会走到 confirm，那样只能放宽不能收紧（D1），故改为快照注入。

### 4. 运行循环：复用主 Agent 的 query()

`runGardener`（gardener.ts:143-201）跑的是与主 Agent **同一个 `query()` 函数**——同压缩阈值、同 `agentMaxTurns` 安全阀，零 Loop 改造，深度固定 1 层。区别只在：

- `view` 是全新 ModelView（system = persona + ELEMENT.md，user = 「整理任务：{task}」+「整理范围：{scope 或整个 elements/}」）
- `tools` 是白名单过滤后的工具面
- `onEvent` 把内层 `tool-call` / `tool-result` 事件打上 `agent: 'gardener'` 标签透传给上层（gardener.ts:185-187），同时累计 `toolCallCount`
- `signal` / `confirm` 由调用方闭包注入透传

### 5. 产出：固定结构汇报

persona 规定任务结束时输出四段式 Markdown：

```
## 改动文件清单      （每个文件一句话说明改了什么）
## 合并与迁移说明    （合并进哪里、依据是什么）
## 存疑事项          （需用户拍板的疑似重复/冲突；无则写「无」）
## 建议删除          （建议手动删除/改名的文件及理由；无则写「无」）
```

`runGardener` 从最后一条 assistant 消息提取汇报（gardener.ts:191-200），空则兜底「（子智能体未产出汇报）」、被中止则兜底「（要素整理任务被停止，未产出完整汇报）」。

### 6. DelegateToGardener 工具（主 Agent 侧）

`createDelegateToGardenerTool`（gardener.ts:226-315）是挂在主 Agent 工具面的委派入口：

- **`isReadOnly: true`**（gardener.ts:239）：本工具不直接写文件，写确认全部发生在园丁内层工具上，与主 Agent 共用同一条确认链
- **`isConcurrencySafe: false`**（gardener.ts:240）：长任务，串行
- **确认打标**（gardener.ts:232-235）：内层写确认带 `agentLabel: '要素整理'`，UI 上能区分是主 Agent 还是园丁在请求写文件
- **入参校验**（gardener.ts:270-281）：`task` 必填非空（子代理看不到对话，须自包含），`scope` 可选
- **工具描述含触发信号与频率节制**（gardener.ts:245-249）：列出该委派的信号（新要素连续出现、状态/关系显著变化、设定前后矛盾、用户提到「对不上/重复/记混了」）与不该委派的情形（改动轻微、无实质变化、本会话已整理过）；并要求「主动整理前先建议、经用户同意后再调用，用户明确要求（含 /整理要素）时直接委派」
- **summarizeInput / summarizeOutput / formatResult**（gardener.ts:295-313）：给聊天区工具行与结果展示用的摘要与格式化

## 三、/整理要素 斜杠指令

### 1. 命令注册：纯文本补全器

`SLASH_COMMANDS`（slash-commands.ts:25-38）注册 `/整理要素`（id `gardener`，icon 🌿）。设计哲学写在 slash-commands.ts:4-10 注释：**斜杠菜单是纯命令补全器**——选中后把命令文本填入输入框（尾部带空格），命令是纯文本，可编辑可删除，行为与普通文字一致。旧 `/提取要素` 已于 2026-10 退役（slash-commands.ts:24 注释）。

### 2. 两阶段机制：替换发生在「发送时」，不是「选中时」

这是斜杠指令最核心、也最容易误解的机制。

**阶段 1 · 选中命令 → 落的只是命令文本本身**（ChatPanel.vue:516-526 `handleSlashCommandSelect`）：

```typescript
composer.replaceTokenBeforeCaret(SLASH_COMMAND_RE, slashCommandDraftText(command.label))
// slashCommandDraftText 返回 "/整理要素 " —— 标签 + 一个空格（slash-commands.ts:41-43）
```

选中后输入框里出现的就是 `/整理要素 ` 这几个字符加一个空格，光标停在后面等用户补参数。**这一刻内置的 `GARDENER_TASK_PROMPT` 并没有进输入框**，用户看不见它。

**阶段 2 · 点击发送 → 前缀拦截，此刻才替换**（ChatPanel.vue:287）：

```typescript
const message = expandSlashCommand(draftText)
```

`expandSlashCommand`（slash-commands.ts:57-73）的逻辑：

- 看草稿**首行**是否以某个已注册命令开头（`/整理要素` 或 `/整理要素 xxxx`）
- 命中 → 把命令部分替换为 `GARDENER_TASK_PROMPT` 全文，命令后用户敲的参数原样保留，用 `\n\n` 拼在 prompt 后；首行之后的其余行原样拼回
- 未命中（命令不在行首，如写在段落中间）→ 原样发送，不替换

```
用户在输入框看到的：            实际发给 LLM 的：
┌──────────────────────┐      ┌────────────────────────────┐
│ /整理要素 第12章新人物 │  →   │ 请立即调用 DelegateToGardener │
└──────────────────────┘      │ 工具……（GARDENER_TASK_PROMPT 全文）│
                              │                            │
                              │ 第12章新人物                │
                              └────────────────────────────┘
```

### 3. 为什么这样设计（而不是选中即塞 prompt 全文）

- **裸命令文本不构成有效指令**（slash-commands.ts:9 注释）：`/整理要素` 这几个字发给 LLM 它不知道该干嘛，必须换成含「请立即调用 DelegateToGardener」的 `GARDENER_TASK_PROMPT` 全文，才能保证主 Agent 正确委派，工程质量不丢
- **但选中即塞全文会让输入框被一大段工程指令占满**：用户想补的参数得写在其后，体验糟，还可能误删半截。故做成「输入框里始终是干净短命令，发送那一刻才展开」
- **发送失败填回原草稿**（ChatPanel.vue:299-303）：`sendMessage` 失败时恢复的是 `draftText`（用户看到的 `/整理要素 第12章新人物`），不是展开后的 prompt 全文，避免用户输入框里突然冒出陌生大段文本

### 4. 配套：TextRef 高亮

`/整理要素` 在输入框里会被 Lexical 的 `TextRefNode` 着色（《输入框富文本化施工计划》W3），`scanTextRefs` 把已注册斜杠命令 label 作为词表判定，视觉上与普通文字区分。

## 四、GARDENER_TASK_PROMPT（驱动 prompt 全文）

来自 gardener.ts:204-210，是写给**主 Agent** 的指令（不是给用户、也不是直接给园丁）：

```
请立即调用 DelegateToGardener 工具，把本次要素整理任务委派给要素整理子智能体执行，不要自己直接修改要素文件。

对 task 的要求（子智能体看不到本对话，必须自包含）：
- 整理整个 elements/ 要素库：核对同名与近名条目合并、frontmatter 规范（tags 去重、relatedChapters 取并集、lastUpdatedChapter 取最新）、正文按模板小节归位、按规范补写素材间链接。
- 子智能体会自己读写文件并对写入操作请求确认；存疑事项它会列进汇报。

收到汇报后，向用户转述要点：改了哪些文件、合并了什么、哪些存疑事项需要用户拍板、是否有建议删除的文件。
```

**三段结构**：

| 段落 | 作用 |
| :-- | :-- |
| 第一句「请立即调用…不要自己直接修改」 | 行为指令：命令主 Agent 必须委派，禁止自己动手 |
| 「对 task 的要求」 | 参数构造指南：怎么填 `task`（自包含）+ 默认整理范围（合并同名、frontmatter 规范、模板归位、补链接） |
| 「收到汇报后…」 | 结果转述指令：园丁跑完后主 Agent 把汇报要点翻译给用户 |

**拼接规则**：裸命令只发 prompt 本身；命令后带参数则 `prompt + \n\n + 用户参数.trim()`。

**易混淆点**：`GARDENER_TASK_PROMPT` 与园丁实际看到的提示词**不是同一个**。链路是——

```
用户输入 → GARDENER_TASK_PROMPT（给主 Agent）
            ↓ 主 Agent 调 DelegateToGardener(task)
        园丁 system = GARDENER_PERSONA + ELEMENT.md
        园丁 user   = 「整理任务：{task}」+「整理范围：{scope}」
```

## 五、命令入口：两个模式、五个触发点

斜杠指令只是其中一个入口。完整入口分**「当前会话」**与**「新会话」**两个模式：

| 入口 | 位置 | 目标会话 | 是否开参数弹窗 |
| :-- | :-- | :-- | :-- |
| `/整理要素` 斜杠命令 | 输入框 SlashCommandMenu | 当前会话 | 否（命令文本落输入框，发送时替换） |
| ChatPanel 工具栏「🌿 整理要素」 | ChatPanel.vue:855 | 当前会话 | 是（锚定弹层 target=current） |
| 全局 `Ctrl/Cmd+Shift+G` | keyboard.ts:37 | 当前会话 | 否（裸发 GARDENER_TASK_PROMPT） |
| ActivityBar 叶子图标**单击** | ActivityBar.vue:49 | 新会话 | 是（居中模态 target=new） |
| ActivityBar 叶子图标**双击** | ActivityBar.vue:127 | 新会话 | 否（裸发） |

**本调研聚焦斜杠指令入口**；参数弹窗（GardenerTaskDialog）属另一形态，仅在此登记其拼装逻辑与斜杠指令的差异。

## 六、参数弹窗（对比形态，简要登记）

`gardener-task.ts` 是无组件挂载的纯逻辑状态机（照 reasoning-collapse 模式抽出，便于 node 环境纯逻辑测试）。

**三类参数**（`buildGardenerTaskMessage`，gardener-task.ts:34-50）：
1. 自由文本 `text.trim()`
2. 快捷选项 `presetPrompts` 逐条（存 `.novai/gardener-presets.json`）
3. 章节范围 → 拼成 `涉及章节：第10章、第12章`

拼装：以 `GARDENER_TASK_PROMPT` 为 base，各段 `\n\n` 分隔；空参数时只有 base，与裸发一致。

**确认按钮动态文案**（gardener-task.ts:86）：无任何输入/勾选 →「直接整理」；有任一 →「确认发送」。

**与斜杠指令的关键差异**：弹窗是**发送前**就把 `GARDENER_TASK_PROMPT` 和参数拼好整段发给 `chatStore.sendMessage`，**不走 `expandSlashCommand` 前缀拦截**；斜杠指令是发送时才做前缀替换。

## 八、现状观察（仅记录，不构成改进决议）

调研中注意到的若干现状，留作后续改动的参考，**本轮不做任何改动决议**：

1. **两条拼装路径并存**：斜杠指令走「发送时前缀拦截」，参数弹窗走「发送前整段拼装」。同一份 `GARDENER_TASK_PROMPT` 经两条不同路径进入发送链路，行为一致但实现分叉。
2. **园丁提示词为早期两层方案**：persona + ELEMENT.md 硬编码两层拼接，无工具使用规则段。这与主 Agent 经《Agent 提示词分层与越权修复计划》重构后的分层方案存在代差——此点已在《要素管理子智能体升级讨论记录》中立项讨论（提示词拼装升级为主 Agent 同款），本文不重复展开。
3. **委派完全依赖主 Agent 自觉**：`DelegateToGardener` 是否被调用取决于主 Agent 对 `GARDENER_TASK_PROMPT` 或工具描述中触发信号的响应，无硬节流闸（Phase 2 已明确不做，视真机另批）。
