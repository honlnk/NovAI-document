## 记录时间

## 文档性质

本文档是**讨论记录**，不是施工计划。它记录了 2026-10-07 关于「要素管理子智能体」（原「园丁」）升级方向的讨论结论，以及 2026-10-08 的最终决策，作为后续立施工计划的输入。

**本轮施工范围已收敛**：仅调整提示词拼装 + 工具权限（放开 RenameFile）+ 彻底改名。ELEMENT.md 内容、主动建议机制、触发方式均不在本轮范围。

## 背景

### 当前实现的问题

园丁子智能体的提示词拼装还是早期版本（2026-09-25 Phase 1 落地时的方案），与主 Agent 的提示词分层重构（2026-10-02 W1-W4）脱节：

| 维度 | 主 Agent（新方案） | 园丁（当前） |
| :--- | :--- | :--- |
| system 结构 | 身份 + 项目结构 + 工具规则 + (system.md 后置) | persona + ELEMENT.md 硬编码两层拼接 |
| 工具使用规则 | 有（14 条，逐工具说明） | ❌ 完全没有 |
| 可变内容注入 | NovAI.md / 大纲走 user-role `<system-reminder>` | ELEMENT.md 塞进 system |
| 条件注入 | system.md 未修改不注入、NovAI.md digest 按需注入 | ❌ 无（恒全量注入） |
| 身份声明 | `你是 NovAI，使用 {model} 模型驱动的小说创作 AI 智能体` | `你是小说要素库的园丁`（无 NovAI 归属、无模型名） |

### 参考系调研

2026-10-07 对 dsh 和 ZCode 的子智能体提示词机制做了深度调研：

**dsh 方案**：子智能体和主智能体**公用一套** `SystemPrompt` 装配服务，子 agent 通过 scope 链追加/覆写。工具使用规则通过两条通道下发：①工具 schema 的 description；②跨工具的 system-prompt section（`tool:*`，函数式 text，条件不满足返回空串自动剔除）。

**ZCode 方案**：主智能体单独实现，所有子智能体**公用一个** `SubagentContextBuilder`。每个子智能体是一个「profile」（内置 Explore / general-purpose / 自定义 markdown），profile 声明 agentPrompt、tools 白名单、injectAgentsMd 等。工具说明不镜像进 system，由 model request 的 tools 字段承载；角色级工具约束内嵌在 profile 的 agentPrompt 里。有独立的 `Subagent Notes` 段（所有子智能体共享的硬规则）。

**关键发现**：dsh 和 ZCode 的子智能体提示词都比 NovAI 的园丁**丰富得多**——它们都有工具使用规则、环境信息、通用规则等段落，而园丁只有 persona + ELEMENT.md 两层。

## 讨论结论

### 一、提示词拼装方案：升级为主 Agent 同款

**结论**：园丁的提示词拼装应升级为主 Agent 同样的拼装逻辑，不再使用「md 文件内容塞进 system」的早期方案。

**理由**：
- 主 Agent 的拼装方案（W1-W4 重构后的）已经证明了它的价值：system 只讲「身份 + 项目结构 + 工具规则」，可变内容走 user-role `<system-reminder>` 按需注入，条件注入（未修改不注入、digest 去重）
- 目前没见哪个成熟的 Harness 项目还把 md 文件内容塞进 system

### 二、dsh vs ZCode 的子智能体方案选择（已拍板）

**结论**：参考 ZCode 的装配思路（`SubagentContextBuilder` + profile 声明式工具白名单），但**不做 ZCode 的 Markdown Profile 自定义机制**。

**理由**：
1. **显式优于隐式**——ZCode 的 profile 机制把「子智能体是什么、能用什么工具」显式声明，比 dsh 的 scope 链覆写更容易理解和维护
2. **更适合扩展场景**——后期可能还会有更多的专业功能的子智能体出现，可能需要配置不同的权限，profile 声明正好是为这个设计的
3. **与主 Agent 的边界更清晰**——子智能体完全跳过主 Agent 的 identity / Dynamic Behavior / Session Guidance 等段，避免不必要的复杂度
4. **不需要用户自定义**——NovAI 的子智能体是产品内置角色，不开放用户自定义 markdown profile，因此 ZCode 的「自定义 profile」机制（`.zcode/agents/*.md` 扫描）不引入，只取 profile 的**声明式思想**（内置常量声明每个子智能体的身份、工具白名单、路径闸）

### 三、工具描述：参考 ZCode 的工具权限配置

**结论**：不同子智能体配置不同的工具使用权限，参考 ZCode 的实现。

**ZCode 的实现**：
- `EXPLORE_AGENT_ALLOWED_TOOLS` / `EXPLORE_AGENT_EMBEDDED_SEARCH_ALLOWED_TOOLS`（profile 声明式白名单）
- `resolveSubagentToolAllowlist` 计算 profile.tools ∩ parent.tools ∩ disallow rules
- `filterSubagentChildToolNames` 过滤递归工具（防止子智能体再起子智能体）

**落地方向**：
- 园丁当前的工具白名单（`GARDENER_TOOL_WHITELIST`）保留，但改为 profile 声明式
- 未来新增子智能体时，每个 profile 声明自己的工具白名单
- 运行层强制（`guardElementsScope` 路径闸）保留，但改为 profile 可配置的路径前缀

### 四、身份信息：补全 NovAI 子智能体定位

**结论**：身份信息应讲明「是 NovAI 的一个子智能体，专门用来管理要素模块的」，并包含模型名。

**参考主 Agent**（`prompt.ts:19-22`）：
```typescript
const identity = model
  ? `你是 NovAI，一个使用 ${model} 模型驱动的小说创作 AI 智能体。`
  : '你是 NovAI，一个小说创作 AI 智能体。'
```

**写法**（名称随「园丁 → 要素管理员」改名敲定）：
```typescript
const identity = model
  ? `你是 NovAI 要素管理员，一个使用 ${model} 模型驱动的子智能体，专门负责管理小说项目的要素库（elements/ 目录）。`
  : '你是 NovAI 要素管理员，一个子智能体，专门负责管理小说项目的要素库（elements/ 目录）。'
```

### 五、环境信息：主 Agent 也没有，要素管理员不需要

**结论**：要素管理员不需要环境信息段（cwd / git / platform / shell / osVersion）。

**理由**：
- 主 Agent 确实没有环境信息段（dsh 和 ZCode 有，但 NovAI 的主 Agent 没有）
- 要素管理员只操作 `elements/` 目录，不需要知道 cwd / git 状态 / 平台信息
- 如果未来需要，可以后续补

### 六、铁律部分：改为 Subagent Notes 段

**结论**：参考 ZCode 的 Subagent Notes，把铁律从「一大段提示词写死在代码中」改为独立的段，便于扩展。

**ZCode 的实现**（`subagent/system-prompt.ts:10-19`）：
```typescript
export function buildSubagentCommonNotes(): string {
  return [
    "Notes:",
    "- Agent threads always have their cwd reset between bash calls, ...",
    // ...
  ].join("\n");
}
```

**落地方向**：
把「铁律」从 GARDENER_PERSONA 中抽出来，改为独立的 `buildElementManagerNotes()` 函数（随改名）：

```typescript
export function buildElementManagerNotes(): string {
  return [
    "Notes:",
    "- 你只能写入 elements/ 下的文件；其余一切只读。",
    "- 合并同名/近名要素时保留旧文件全部事实；存疑不合并，列入汇报交用户拍板。",
    "- 你可以重命名 elements/ 下的要素文件；不删除任何文件，确需删除的列入汇报交用户处理。",
    "- 从不修改 chapters/ 正文，也不修改 prompts/ 下的任何文件。",
  ].join("\n");
}
```

这样未来新增子智能体时，每个子智能体可以有自己的 `buildXxxNotes()` 函数。

### 七、角色级工具约束 vs ELEMENT.md

**结论**：角色级工具约束和 ELEMENT.md 是两个不同的东西，不冲突。

- **角色级工具约束**：内嵌在 profile 的 `agentPrompt` 里，告诉模型「这个角色该用什么工具、不该用什么工具」（例如 Explore 的「Use Glob for broad file pattern matching」「NEVER use Bash for: mkdir, touch, rm, cp, mv」）
- **ELEMENT.md**：要素库的**工作规范**（六类目录职责、命名规范、frontmatter 维护规范、链接约定、模板结构说明）

两者不冲突：
- 工具约束是**操作层面**的「怎么用工具」
- ELEMENT.md 是**业务层面**的「要素库该怎么管理」

### 八、ELEMENT.md 注入位置：与 NovAI.md 同级

**结论**：ELEMENT.md 应该和 NovAI.md 一样，注入在 system 之后的第一条 user 角色 `<system-reminder>` 中，因为它俩在一个智能体中是有同样的地位的。但 ELEMENT.md 不需要「不修改就不注入」的条件判断，默认直接注入即可。

**落地方向**：
参考 `buildNovaiReminder`（`prompt.ts:109-114`）写一个 `buildElementReminder`：

```typescript
export function buildElementReminder(content: string): string {
  return `<system-reminder>\n以下是本书要素规范（prompts/ELEMENT.md），作为工作守则。\n\n${content.trim()}\n</system-reminder>`;
}
```

### 九、功能定位升级：从「整理」到「管理」

**核心洞察**：
> 我想要的其实不是「整理」而是「管理」。我要的是一个专门「管理」要素的智能体。

**这是一次重要的功能定位调整**，影响的不只是提示词，还有整个功能的设计。

#### 「整理」vs「管理」的区别

| 维度 | 整理（当前） | 管理（目标） |
| :--- | :--- | :--- |
| 触发方式 | 用户主动触发（/整理要素） | 用户触发 + 主 Agent 主动委派 + 可能自动触发 |
| 任务范围 | 合并重复、规范 frontmatter、补写链接 | 上述 + 新增要素、重命名要素、跨要素关系维护（删除要素不开放，走汇报「建议删除」交用户处理） |
| 工具权限 | 无 DeleteFile/RenameFile | 有 RenameFile，无 DeleteFile |
| 主动性 | 被动（用户说什么做什么） | 主动（发现要素库问题主动建议/处理） |
| 与主 Agent 的关系 | 主 Agent 委派任务 | 主 Agent 委派 + 子智能体主动汇报 |

#### 关于 LLM WIKI 的抽象

这个功能是对 **LLM WIKI** 的抽象实现：

- 在传统的 LLM WIKI 工作环境中，都是由一个 Claude Code 这样的 Agent 管理着一个工作区
- 这个工作区就是「笔记」本身，而工作区中的 AGENTS.md/CLAUDE.md 就是 LLM WIKI 的 Schema——**任务范围也是写在这份 Schema 里的**
- 在 NovAI 中，这个 Schema 被抽象实现成了 ELEMENT.md，因此「要素管理员能管什么、不能管什么」本质上是 ELEMENT.md 的内容问题
- 这个智能体严格意义上来讲并不是「整理」这一套笔记，而是「管理」这一套笔记

> 关于定位升级的实现路径：**本轮只做提示词拼装升级**，定位升级如何通过提示词内容体现（职责描述怎么写、任务范围怎么限定），属于 ELEMENT.md 这个 Schema 的内容问题，留待下一轮专门处理。

这意味着：
- 要素管理员的职责不只是「整理」，而是**维护整个要素库的一致性、完整性、可检索性**
- 它应该像 LLM WIKI 的管理员一样，发现要素库的问题（重复、冲突、缺失、过时），并提出或执行解决方案

#### 本轮已收敛的决策（2026-10-08）

| 决策点 | 结论 | 说明 |
| :--- | :--- | :--- |
| 改名 | ✅ **园丁 → 要素管理员，彻底改名** | 代码、UI、文档全面替换，不留旧名痕迹，防止两个名字在后续维护中互相打架 |
| 工具权限 | ✅ **放开 RenameFile，不放 DeleteFile** | RenameFile 加入白名单并过 elements/ 路径闸；DeleteFile 维持不开放，删除需求走汇报「建议删除」 |
| ELEMENT.md 内容 | ✅ **本轮不动** | 任务范围如何写属于 ELEMENT.md 的内容问题（LLM WIKI Schema），本轮仅升级提示词拼装 |
| 主动建议机制 | ✅ **本轮不做** | 保持现有的被动机制（用户触发 + 主 Agent 委派），「巡检/主动汇报」留待后续计划 |
| 触发方式 | ✅ **本轮不动** | 现有的 5 个入口（ActivityBar / 工具栏 / 快捷键 / 斜杠命令 / 委派工具）全部保持，仅随改名调整文案 |

#### 留待后续计划的方向

- ELEMENT.md 内容升级（「园丁工作守则」→「要素管理守则」，按 LLM WIKI Schema 定位重新组织）
- DeleteFile 是否放开
- 主动建议机制（巡检/主动汇报怎么做）
- 汇报格式扩展、触发方式扩展

## 本轮范围收敛（2026-10-08）

讨论最后，本轮工作的边界被明确收敛——这是**讨论结论**，不是施工清单；具体的任务拆解、波次划分、验收门禁会另立施工计划文档。

### 做什么

1. 提示词拼装升级为「主 Agent 同款 + ZCode 式 Notes 段」：身份段（含模型名）+ 项目结构 + 工具使用规则 + Notes 段，ELEMENT.md 走 user-role `<system-reminder>` 恒注入
2. 工具白名单改为 profile 声明式（内置常量，不做用户自定义），放开 RenameFile（过 elements/ 路径闸）
3. 彻底改名：园丁/gardener → 要素管理员/element-manager，代码 + UI + 文档全面替换；斜杠命令 /整理要素 → /管理要素（存量用户习惯通过 UI 入口文案自然过渡，不做命令别名）

### 不做什么（本轮明确排除）

1. **ELEMENT.md 内容**不动——「园丁工作守则」改写、任务范围的写法，都属于 ELEMENT.md 这个 LLM WIKI Schema 的内容问题，留给下一轮
2. **主动建议机制**不做——保持现有的被动机制（用户触发 + 主 Agent 委派）
3. **触发方式**不动——5 个入口（ActivityBar 单击/双击、ChatPanel 工具栏、Ctrl/Cmd+Shift+G、/斜杠命令、委派工具）全部保持现有机制，仅随改名调整文案
4. **DeleteFile 不放开**——删除需求继续走汇报「建议删除」交用户手动处理
