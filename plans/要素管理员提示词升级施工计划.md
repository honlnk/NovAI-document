# 要素管理员提示词升级施工计划

## 元信息

- **立项日期**：2026-10-08
- **上游文档**：[要素管理子智能体升级讨论记录](要素管理子智能体升级讨论记录.md)（讨论记录，五项决策已拍板）
- **计划性质**：施工计划——讨论记录已定稿方向，本计划把方向拆成可执行、可验收的波次
- **预估波次**：4 波（W1 改名 → W2 提示词拼装 → W3 RenameFile 放开 → W4 真机回归）

## 背景与目标

园丁子智能体的提示词拼装还是 Phase 1（2026-09-25）的两层硬编码方案（persona + ELEMENT.md 塞进 system），与主 Agent 的 W1-W4 分层重构（2026-10-02）脱节：没有工具使用规则、没有项目结构段、身份缺 NovAI 归属与模型名、ELEMENT.md 注入位置不对。

本计划把子智能体的提示词拼装升级为「主 Agent 同款 + ZCode 式 Notes 段」，同时完成两件已拍板的事：

1. **彻底改名**：园丁/gardener → 要素管理员/element-manager，代码 + UI + 文档全面替换，不留旧名痕迹
2. **放开 RenameFile**：加入白名单并过 elements/ 路径闸（fromPath/toPath 双向校验）；DeleteFile 不放开

## 范围

### 做

1. 提示词拼装升级：身份段（含模型名）+ 项目结构 + 工具使用规则 + Notes 段；ELEMENT.md 走 user-role `<system-reminder>` 恒注入
2. 工具白名单改为 profile 声明式（内置常量声明，不做用户自定义 profile 机制）
3. 放开 RenameFile（elements/ 路径闸扩展为 fromPath/toPath 双向校验）
4. 彻底改名：园丁 → 要素管理员，覆盖代码、UI、文档、斜杠命令（/整理要素 → /管理要素）、委派工具（DelegateToGardener → DelegateToElementManager）
5. 存量兼容：老项目 novel.config.json 的 `gardener` 配置块迁移为 `elementManager`；`.novai/gardener-presets.json` 迁移为 `.novai/element-manager-presets.json`

### 不做（本期明确排除）

1. **ELEMENT.md 内容不动**——「园丁工作守则」改写为「要素管理守则」、任务范围的写法，都属于 ELEMENT.md 这个 LLM WIKI Schema 的内容问题，留待下一轮。本轮仅把默认模板里的角色名「园丁」替换为「要素管理员」（语义一字不改），存量项目的 ELEMENT.md 是用户文件，完全不动
2. **主动建议机制不做**——保持现有的被动机制（用户触发 + 主 Agent 委派）
3. **触发方式不动**——5 个入口（ActivityBar 单击/双击、ChatPanel 工具栏、Ctrl/Cmd+Shift+G、/斜杠命令、委派工具）全部保持现有机制，仅随改名调整文案与命令名
4. **DeleteFile 不放开**——删除需求继续走汇报「建议删除」交用户手动处理
5. **汇报格式四段结构不动**——改动文件清单 / 合并与迁移说明 / 存疑事项 / 建议删除，仅「合并与迁移说明」一栏的措辞扩为重命名说明（见 W2）
6. **不做用户自定义子智能体 profile**——profile 声明式是内置常量，不引入 ZCode 的 `.zcode/agents/*.md` 扫描机制
7. **斜杠命令不做别名兼容**——/整理要素 直接退役，/管理要素 上岗，不留双命令并存期（存量用户习惯通过 UI 入口文案自然过渡）

## 决策记录

### D1：改名策略——彻底替换，配置做迁移

`config.gardener` 是可选块，老项目若用户开过园丁覆盖配置则已落盘。改名为 `elementManager` 时，在 `normalizeProjectConfig` 里做读取迁移：老字段 `gardener` 存在且新字段 `elementManager` 不存在时，值原样映射；两者都存在时以新字段为准。写回时只写新字段。`.novai/gardener-presets.json` 同理：读取时先试新文件名，不存在再回退老文件名；写回只写新文件名。老文件不主动删（用户数据，留着无害）。

**理由**：gardener 块是可选的、无块 = 全继承主配置，迁移成本极低；presets 文件是项目级隐藏配置，双文件名读取兜底零风险。彻底改名不留旧名痕迹，防止后续维护时两个名字互相打架。

### D2：ELEMENT.md 恒注入，无 digest 去重

主 Agent 的 NovAI.md 有 digest 按需注入（内容变化才重新注入），因为主 Agent 是长会话、多轮复用同一 ModelView。要素管理员是**一次性运行、每次全新 ModelView**（runGardener 语义），不存在「同一会话里内容变了要更新」的场景，恒注入即可，不需要 digest 机制。

**理由**：一次性上下文没有去重需求，digest 只会增加无意义的复杂度。

### D3：ELEMENT.md 无「未修改不注入」条件

主 Agent 的 system.md 有「未修改默认模板不注入」判断（`isUnmodifiedTemplate` 三模板字节比较），因为 system.md 是**全局基调**，默认模板内容是「没内容」的占位。ELEMENT.md 不同——默认模板本身就是完整的工作守则（六类目录职责、命名规范、frontmatter 规范、链接约定、工作守则、模板结构），**未修改 ≠ 无内容**，恒注入。

**理由**：ELEMENT.md 的默认模板就是有效守则，不是占位符。

### D4：工具使用规则按白名单裁剪，不整抄主 Agent

主 Agent 的 14 条工具规则（`prompt.ts:49-64`）覆盖全部工具（含 Web 系、KnowledgeLookup、DeleteFile、章节编号规则等）。要素管理员的规则段只写白名单内的 7 个工具（ListDirectory / FindFiles / ReadFile / RagSearch / CreateFile / EditFile / RenameFile），删掉无关条目：

- 删：WebSearch / WebFetch / KnowledgeLookup（白名单外）
- 删：DeleteFile（不开放）
- 删：章节编号规则（「新建章节必须写入 chapters/*.txt、编号 = 现有最大编号 + 1」——要素管理员不写章节）
- 保留：spill 说明（ReadFile 超限截断、spill 取回指引——要素管理员读长文件时同样会撞到）
- 保留：path 相对路径规则、EditFile oldText 规则、CreateFile 已存在失败规则、ListDirectory/FindFiles/RagSearch 用法
- 改写：CreateFile 规则里的「章节 content 必须是纯文本正文」删去，只留要素文件相关部分

### D5：RenameFile 路径闸双向校验

现有 `guardElementsScope` 只校验单 `path` 字段（`gardener.ts:88-103`）。RenameFile 入参是 `fromPath`/`toPath` 两个路径（`types.ts:189`），路径闸需扩展：对 RenameFile 同时校验两个路径都在 `elements/` 下，任一不在则拒绝。

**理由**：只校验 fromPath 会把文件挪出 elements/；只校验 toPath 会把外部文件挪进来。

### D6：汇报格式措辞微调

「合并与迁移说明」一栏的说明文字从「哪些条目被合并进哪里、依据是什么」扩为「哪些条目被合并进哪里、依据是什么；重命名了哪些文件、理由是什么」。四段结构（改动文件清单 / 合并与迁移说明 / 存疑事项 / 建议删除）不动。

### D7：斜杠命令改名不做别名

/整理要素 直接改为 /管理要素，不留别名兼容期。`SlashCommandId` 的 `'gardener'` 改为 `'element-manager'`，label、description、icon 同步更新（icon 🌿 是否换待定，施工时选一个不打架的 emoji，如 📚）。`SLASH_COMMAND_EXPANSIONS` 的 command 映射同步改。

**理由**：斜杠命令是输入辅助，不是持久化数据；老用户看到 UI 入口文案变成「管理要素」自然过渡。留别名 = 双份维护。

### D8：profile 声明式是内置常量，不开放用户自定义

参考 ZCode 的 profile 思想（显式声明每个子智能体的身份、工具白名单、路径闸），但只作为**代码组织方式**（内置常量/配置对象），不引入 ZCode 的 markdown profile 扫描机制（`.zcode/agents/*.md`）。NovAI 的子智能体是产品内置角色，不开放用户自定义。

**理由**：讨论记录拍板——「不需要 Zcode 那种 Markdown Profile 因为我们不需要让用户自定义子智能体」。

## 风险与备注

1. **改名面大但风险低**：改名是机械替换，测试网（gardener.test.ts / slash-commands.test.ts / keyboard.test.ts / chat-render.test.ts / project-fs.test.ts / defaults.test.ts 等）会兜住遗漏。最大风险是**漏改某处 UI 文案**导致用户看到新旧两个名字——W4 真机回归逐项过文案。
2. **存量配置迁移**：老项目若无 gardener 块（无块 = 全继承主配置），迁移逻辑不触发，零影响；有块的项目读取时自动映射，用户无感。
3. **委派工具改名对主 Agent 的影响**：DelegateToGardener → DelegateToElementManager 后，主 Agent 的工具描述中出现新名字。主 Agent 的 system prompt 中没有直接引用「园丁」或「DelegateToGardener」字样（工具描述由 schema 承载），无需额外改动。但 `prompt.ts` 项目结构段的「ELEMENT.md 是要素库整理规范」需同步改为「管理规范」（W2 第 11 项已覆盖）。
4. **icon 选择**：🌿（园丁）需要换成一个不与现有 emoji 冲突的。施工时从 📚 / 📖 / 🗂️ / 📋 中选一个，在 W1 交付说明中记录选了哪个。
