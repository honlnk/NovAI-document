# 0007 - 要素召回机制重构：从 RAG 单通道到渐进式披露

## 状态

- 日期：2026-10-23
- 状态：已落地（2026-10-23 四波施工完毕，门禁与真机验证结论见[施工计划文末施工日志](../plans/要素召回渐进式披露施工计划.md#偏差与施工日志)）
- 关联计划：`docs/plans/要素召回渐进式披露施工计划.md`

## 背景

### 现状

要素（characters / locations / entities / plots / timeline / worldbuilding）当前的召回**只有一条通道**：LLM 在主 Agent 循环里自主调用 `RagSearch` 工具，走 Orama 向量检索，结果作为 tool message 回灌。框架层不主动向模型暴露任何要素信息。

### 问题

1. **召回不可靠**：RAG 是概率性召回，写设定类内容需要确定性。模型可能没意识到要调 RagSearch，或者 query 措辞不当导致漏召回，产生设定矛盾。
2. **RAG 语料过宽**：当前 `elements/**/*.md` 全量入索引，但 plots/timeline 之外的四类（characters / locations / entities / worldbuilding）**总量小、结构稳定**，本不需要向量检索。
3. **embedding 维度/模型 mismatch 会静默失败**：维度不匹配时返回空召回兜底，模型感知不到，继续写。

### 数据特性

| 类别 | 增长速度 | 召回不确定性容忍度 | 语义模糊查询频率 |
| :--- | :--- | :--- | :--- |
| characters | 慢 | **不能容忍**（写错角色设定是质量事故） | 低 |
| locations | 慢 | 不能容忍 | 低 |
| entities | 慢 | 不能容忍 | 低 |
| worldbuilding | 慢 | 不能容忍 | 低 |
| plots | **快**（章节级增长） | 可容忍 | 高（"之前主角失恋那段"） |
| timeline | 快 | 可容忍 | 高 |

chapters/*.txt **不参与召回**，这是既有事实，本决策不改变。

## 参考系：dsh 的 Skill 渐进式披露

`deepseek-harness`（`packages/skill/`）的 skill 系统是成熟的两层披露实现：

- **L1 目录**：一份 `<system-reminder>` 格式的 user 消息，包含所有 skill 的 `name + description` 清单，紧跟 system prompt 注入；digest 驱动，变化时原位替换而非堆积
- **L2 加载**：`skill({ name })` 工具，模型按需调用，工具结果返回完整 skill 内容
- **L3 附件**：references/scripts/assets 不自动注入，模型拿到 base 目录后自己用 read 工具 resolve

**关键架构决策**（dsh 已验证）：

- 目录消息是 **user 角色**（虽然内容叫 `<system-reminder>`），不是 system——保住 prompt cache 前缀命中
- **digest 只覆盖数据**（entries 数组的 sha256），不覆盖渲染文本——模板改版不触发重发
- **body 不参与版本追踪**（dsh 原话 "Bodies are not versioned"）——skill 稳定，所以不需要
- **没有向量检索、没有 embedding、没有自动预选**——纯靠 description 写得好 + router skill 模式兜底

关键源码位置：
- `packages/skill/skill/src/index.ts:56-92, 170-214` —— 注册表 + 渲染
- `packages/skill/tool-skill/src/index.ts:215-253, 256-313` —— catalog listener + digest diff
- `packages/skill/tool-skill/src/index.ts:82-163` —— skill tool 定义

## 决策

### 决策一：四类稳定要素改走渐进式披露，RAG 收窄到 plots/timeline

| 类别 | 召回策略 | 理由 |
| :--- | :--- | :--- |
| characters / locations / entities / worldbuilding | **渐进式披露**（目录 reminder + LoadElements 工具） | 量小、结构稳定、需要确定性召回 |
| plots / timeline | **保留 RAG**（RagSearch 工具） | 量大、语义模糊查询多 |
| chapters/*.txt | 不参与召回 | 既有事实，不变 |

RAG 索引范围从"所有要素"收窄到 `elements/plots/**/*.md` + `elements/timeline/**/*.md`。

### 决策二：目录只放稳定信息，不做版本追踪、不做变更推送

目录行格式：

```
- [角色] 林晚 — 冷静克制的外科医生，隐藏身份是前特工
- [地点] 临江医院 — 故事主舞台，地下三层有秘密实验室
```

只含 `type + name + summary`。**不含** `lastUpdatedChapter`、内容 hash、mtime 等任何"版本标记"。

**理由**：用户明确指出，版本号几乎每章都在变，digest 会频繁失效导致目录 reminder 频繁原位替换，进而让 prompt cache 前缀全崩——按原价的 token 成本会失控。

**边界约定**：
- 稳定信息（身份、定义、核心特征）→ 流向目录的 summary
- 变化信息（状态、位置、关系、伤势）→ 流向历史消息（模型自己写的章节正文、element-manager 工具调用结果、用户对话）
- 模型通过历史消息追踪人物状态变化，不需要从要素文件重新加载"当前状态"

element-manager 写 summary 时**应该遵守**：summary 只写稳定身份定义，不写会随章节变化的状态字段。

### 决策三：目录注入复用 `syncNovaiReminder` 的同构模式

目录消息结构与现有 `NovAI.md` reminder 完全同构：

- 角色：user
- 位置：紧跟 system prompt（index 1），先于全部历史
- 格式：`<system-reminder>` 包裹的 Markdown 清单
- 更新：digest 判定变化 → 原位替换（`replaceMessage`），不堆积
- 压缩：会被 compaction 吞掉，但下一次请求前 digest 检查会发现缺失，重新插入

这是 `model-view.ts:70-81` 注释里已经预留的设计：「紧跟 system、先于全部历史；压缩选区从 index 1 起，reminder 被吞后由 digest 机制重插」。

### 决策四：LoadElements 工具支持批量加载

工具签名：

```ts
LoadElements({ names: string[] }) → ElementContent[]
```

**为什么不是 dsh 的单条加载**：dsh 的 skill 是"指令"，一次任务通常只需一份；NovAI 的要素是"数据"，同一场景涉及多个角色是常态。批量一次给齐比 N 次串行 tool call 省 token、降延迟。

### 决策五：本决策不做的事

明确不做，避免 scope creep：

- ❌ `@要素名` 手势（需要维护词表给 text-ref，工作量中等，且当前 slash 命令体系已够用）
- ❌ 变更主动推送（方案三，token 成本失控）
- ❌ 版本号/内容 hash 进目录（方案二，digest 不稳定）
- ❌ 要素 body 的"过期检测"或"重新加载提醒"
- ❌ Router skill 模式（要素规模到几百条再考虑）
- ❌ 对 element-manager 子智能体工作流的改动（它继续按现有方式整理要素）

## 后果

### 正面

- 召回可靠性从概率性提升到确定性（模型看得见目录）
- RAG 索引规模下降一个数量级，向量检索质量提升
- prompt cache 命中率提升（目录稳定 + user 角色不破坏 system 前缀）
- 为后续"要素 @ 引用"等显式入口留了扩展位

### 负面 / 风险

- **要素目录长度不可控**：群像剧 200 个角色 × 80 字符 = 16KB token。本决策**不处理**，只定上限假设"要素总量 < 约 150 条"，超过再做分级（按 type 分桶 / 按相关章节排序）。
- **element-manager 写 summary 的质量变成关键路径**：如果它把"当前状态"写进 summary，目录 digest 就会频繁失效。需要在它的提示词里明确"summary 只写稳定身份定义"。
- **模型可能不主动调 LoadElements**：要在 system prompt 里把"看到目录里相关要素就先 LoadElements 再写"这条规则写清楚。

### 迁移

RAG 索引重建：施工完成后，已有项目的索引需要重建一次（把 elements 下非 plots/timeline 的文档清出索引）。这是用户手动触发的动作，UI 已有"重建索引"入口。
