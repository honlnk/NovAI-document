## 决策一：时间线 = 项目级事件账本，不再是要素文档

时间线从「多篇 Markdown 要素文档」改为项目级 JSON 账本 `elements/timeline.json`：

- 事件是基本对象（点事件 / 区间事件），带有序标记列表；区间两端标记一一配对，允许重叠与嵌套。
- 时间三态：明确历法时间（仅展示）、相对时间（锚事件 + 偏移）、纯顺序（默认）。**系统永不按明确时间重排作者确定的列表**——顺序是作者意图的权威表达，明确时间只是补充描述。
- 账本与关系账本同体系：域内写锁、内容哈希版本校验、非法条目隔离不丢弃、损坏态只读 + 副本入回收站重新初始化、受保护路径（通用文件工具教学式报错）。
- 事件删除的级联语义：causedBy 引用自动清除、以它为端点的关系自动删除、相对时间锚**保留**并进失效提示（引用可推断的自动改，涉及作者意图的不擅自改）；删除被引用要素时清理事件里的参与者/情节引用但不删事件。

**理由**：故事内时序（谁先谁后、持续多久、是否重叠）需要可查询的结构化数据，自然语言 Markdown 无法稳定支撑；而「事件」与「要素」（人物、地点等实体性设定）生命周期与操作模型完全不同，硬塞进要素目录让两侧都别扭。

## 决策二：时间线退出语义索引

时间线事件**不做向量索引**，从 RAG 语义召回范围移出，改由六个时间线工具（List / Read / CreatePoint / CreateSpan / Update / Delete）确定性查询。

- 索引范围收窄为 `elements/plots/` 单前缀；全量重建清扫旧时间线索引残留。
- 时序问题的提问形态（「A 和 B 谁先」「这段持续多久」）适合结构化查询，不适合语义近似检索；账本数据量小，全量读取无压力。

**理由**：延续 0007 的分层召回原则——能用确定性通道的数据不进概率性通道。事件的标题/摘要是给作者看的短文本，语义召回命中率低而误召回代价高（模型拿错误时序写正文）。

## 决策三：不做系统级连续性检查器

不建「人物瞬移、时长不合理」之类的系统级连续性告警引擎；连续性判断交给模型阅读事件数据后自行推理，界面零系统告警。领域层只做**结构性检查**（配对、顺序、引用存在性、章号解析），语义合理性不出规则。

**理由**：连续性错误的高度依赖叙事上下文（梦境/回忆/时间穿越都是合法的「不一致」），规则引擎误报率会高到作者训练性忽略告警。模型推理 + 对话澄清的通道已经存在且更准确。

## 决策四：旧 Markdown 时间线零迁移退役

项目未对外发布，旧时间线要素**整套删除，不提供迁移、导入或双写机制**：ElementType 收窄为四类、要素目录五分类（人物/地点/其他实体/情节/设定）、`elements/timeline/` 目录从模板与索引范围移除。同时解锁关系账本预留的 `kind: 'event'` 事件端点（EVT- 标识），事件删除时关系级联清理。

**理由**：旧时间线数据在测试项目中为空目录，写迁移代码的收益为零；保留兼容层会让「事件 vs 要素」的双轨语义长期并存，每处接线都要考虑两套真相。
